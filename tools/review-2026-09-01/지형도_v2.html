GB10(DGX Spark) 코드 병행 검토

서버를 GB10에 올린다는 전제 · hub/main 29919788(클라 5.83.0) + GB10 실측 2026-09-02

판정

「올릴 수 있다」는 이미 사실이다 — 09-02 실측에서 제품 서버가 GB10에서 11시간 넘게 돌고 있었다. 서버 코드는 통합메모리를 안다(unifiedmem.ts 한 곳 판정 → localengine·preflight가 씀). 남은 것은 「고객 배치의 서버 후보로 삼는가」라는 결정이다: 계획서(전-7 하단)는 실측 38.3 vs 118.5 tok/s로 「큰 기계=Pro」 길을 닫고 값어치를 용량으로 못박았다. 코드에 남은 틈은 셋 — 스왑을 예산에 넣지 않음 · 티어 표에 통합메모리 갈래가 없음(121GB가 pro 상한을 넘어 어색하게 잡힘) · 비로그인 셸 PATH에 node 없음.

확정한 사실 — 출처 있는 것만

  • 기계promaxgb10-1d0a · Ubuntu 24.04.4 · aarch64 · CPU 20 · 메모리 121GB · 디스크 1.9TB(265GB 사용) · CUDA 13.0 / 드라이버 580.173.02 (gb10-probe.txt 09-02)
  • nvidia-smi메모리 칸 전부 [N/A] — name,memory.total · memory.free · utilization,used,total 3종 모두. 표에도 「Not Supported」 (08-11 채취값과 일치)
  • 가동 중제품 서버 node dist/index.js :4000(11h32m, /api/health ok · schema 50) · llama-server :8081 bge-m3 · :8080 Qwen3.8-Flash-Next Q3_K_XL 분할 GGUF 59.6GB · :8090 qwen3-coder-30b-a3b 21GB(절감 도구)
  • 메모리 상태사용 96GB · MemAvailable 26GB · 스왑 7/15GB 사용 중 — 모델 3개 상주 시 여유가 적다
  • 네이티브better-sqlite3 · better-sqlite3-multiple-ciphers · @lancedb/lancedb · onnxruntime-node — 4종 모두 aarch64 로드 OK · llama-server aarch64 빌드(llama.cpp-next)
  • 계획서전-7 하단: GB10 편입 완료 · 원격 GPU 선택지 · 7.6B Q5@16K 38.3 tok/s vs RTX 3090 118.5 → 값어치는 속도가 아니라 용량 (계획서 62·70·77~79행)
변경안우선무엇을 바꾸나계획서크기
스왑을 메모리 예산에P1통합메모리 갈래의 getFreeVramMb가 MemAvailable만 본다 — 스왑이 차오르면 tok/s가 급락하므로 SwapFree·스왑 사용률을 함께 읽어 여유를 깎거나 경고를 낸다전-7 하드웨어 갈래작음
티어 표에 통합메모리 갈래P1GIJO_TIERS는 VRAM 급(10/24/48GB)만 안다 — 121GB 통합메모리는 pro 상한을 넘어 잡힌다. 「통합메모리 대용량」 표시와 상주 개수 기준을 따로 둔다(계획서 「큰 기계=Pro 아님」과 맞게)전-7 · 사용자 결정 §5-③중간
비로그인 셸 PATHP2node가 ~/.local/bin에만 있어 ssh gb10 'bash -s'로 부르는 스크립트는 「node 없음」이 된다 — 배포·탐침 스크립트는 bash -lc 또는 절대경로후-1 운영 안정작음
gb10 저장소 뒤처짐P2~/gijo-as가 hub/main보다 6커밋 뒤(915a71fd) — 도는 서버는 그 빌드다. git push gb10 main 뒤 재기동 절차를 인계 명령에 고정후-1작음

GB10 실장비 실측 체크리스트 — 이 순서대로

  1. 읽기 전용 탐침 — ssh gb10 'bash -lc "bash -s"' < tools/review-2026-09-01/gb10-probe.sh ✓ 09-02 완료(로그인 셸로)
  2. 티어 화면 문구 — 설정 → 구동 티어에 「NVIDIA GB10 · 통합메모리 121GB(CPU와 공유)」가 뜨는지(「GPU를 찾지 못했습니다」가 나오면 FAIL)
  3. 자가진단 — preflight GPU 항목 pass + 같은 문구. 티어 화면과 모순 없어야 한다(08-11 사고 재발 검사)
  4. 스왑 부하 — 모델 3개 상주 상태에서 32K 문맥 요청 → tok/s와 스왑 사용량을 같이 기록(운영 부하 없는 시간에)
  5. tok/s 재측정 — 7.6B Q5@16K로 08-11(38.3)과 같은 조건, 그리고 Qwen3.8-Flash-Next 실사용 조건
  6. 재배포 절차 — git push gb10 main → 빌드 → 재기동 → /api/health, 한 번에 도는지

정직하게 밝힐 한계

  • 속도 미측정09-02는 읽기 전용만 했다 — 운영 중인 서버에 부하를 주지 않기 위해. tok/s는 계획서 08-11 실측을 인용
  • 6커밋 차본 코드는 hub/main 최신, 도는 서버는 6커밋 전 빌드
  • 워크플로 3갈래GB10검토 워크플로(조사→3갈래→검증→종합)는 1차 실행이 사용량 한도로 0건, 2차 실행 결과를 이 절에 합친다
  • 고객 배치 여부「GB10을 고객 서버 후보로」는 사용자 결정 — 이 절은 그 결정의 재료다
origin(GitHub)을 허브에 맞췄다 — 2026-09-02. 클라우드(09-01) 검토는 origin/main f1bfd98(08-09) 코드를 봤고, 그래서 「GB10은 계획서에 없다」·「nvidia-smi [N/A]를 GPU 없음으로 읽는다」는 전제가 낡았었다. win에서 git push origin main(846커밋)으로 맞춘 뒤 hub/main 29919788 기준으로 다시 봤다 — unifiedmem.ts가 통합메모리 갈래를 이미 풀었고, 계획서 전-7에 편입이 이미 적혀 있다.

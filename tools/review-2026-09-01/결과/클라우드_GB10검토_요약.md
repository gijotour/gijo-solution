## 1. 판정
결론부터: 지금 코드로도 GB10(DGX Spark, ARM64 Linux·통합메모리 128GB)에 서버를 올릴 수는 있다 — 단, 그 전에 llama-server를 GB10 전용(sm_121, `-DCMAKE_CUDA_ARCHITECTURES=121a-real`)으로 다시 빌드해야 한다. 배포 가이드 §3.7.2의 `=86`(RTX 3090용) 빌드를 그대로 따르면 채팅·임베딩이 GPU에서 뜨지 않으므로 이것이 유일한 P0다. 그 다음 벽은 「틀린 판정」이다: GB10의 nvidia-smi는 메모리 값을 `[N/A]`로 주기 때문에 localengine.ts가 128GB를 통째로 못 읽어 개수 상한 폴백으로 돌고, 설정 화면은 「NVIDIA GPU 없음 — 미지원 환경」이라고 거짓말을 하며, tools/model-benchmark.mjs는 「총 VRAM NaNGB · Pro」를 찍는다 — Mac Phase 1이 넣은 darwin 분기와 같은 층위의 「통합메모리 NVIDIA」 분기(/proc/meminfo MemAvailable 기반)가 필요하다. 티어 사다리는 Pro(32GB급·32K)에서 끝나 128GB의 실익(동시 사용자 슬롯 --parallel·2모델 상주·학습 병행)을 담을 자리가 없고, needMb의 고정 5000MB 오버헤드는 32B 이상에서 KV 캐시를 절반 이하로 봐 통합메모리에선 OS·DB까지 밀어낼 수 있다. 운영 쪽은 DB 저장 암호화의 기계 봉인(os.arch 포함)이 x64→arm64 이식에서 반드시 깨지므로 종이 복구 열쇠 없이는 데이터 이식이 불가하고, 배포·재시작 도구(deploy-prod.ps1·/GIJOAS배포)가 전부 WSL·Mac만 알아 GB10용 경로를 새로 둬야 한다. 마지막으로 정직하게 적을 것: GB10은 「더 빠른 3090」이 아니라 「4배 큰, 절반 속도의 3090」이다(14B Q4 단일 생성 26 vs 56 t/s, 대역폭 273 vs 936GB/s). 모델을 키우기(32B·MoE) 전에는 평가 게이트를 GB10에서 다시 통과해야 하고, 게이트에 속도 축이 없어 감속이 조용히 통과되는 것도 같이 막아야 한다.

## 2. 이식 작업량(Phase 1 Mac 이식과 비교)
Phase 1(Mac 이식)은 4개 파일(localengine darwin 분기·preflight Metal·build-server-dist prune·client/package.json mac 타깃)을 Windows에서 하루 남짓에 끝냈고 실측은 Mac에서 따로 했다. GB10은 같은 성격의 「GPU 감지 분기」(제안 2)만 놓고 보면 Phase 1과 거의 같은 크기(1~2일 — gpumem 유틸 + preflight + 티어 라우트 + settings.html 라벨 + vitest 스텁)지만, Phase 1에 없던 항목이 네 겹 더 붙는다: ① 빌드·설치 절차(sm_121 재빌드·Node 22·arm64 프리빌드·에어갭 반입물 — 코드보다 문서·검증이 큼, 1~2일) ② 티어 구조 변경(unified 티어·parallel 슬롯·KV 기반 needMb — GijoTierSpec 유니온·티어 API 검증·settings 화면·벤치 도구·시험까지 한 묶음, 2~3일) ③ 운영 도구(deploy-linux.sh·슬래시 명령 분기·migrate-data 일반화·DB 열쇠 재봉인 절차, 1~2일) ④ 평가 게이트 latency 축과 GB10 기준선(1일). 합치면 코드·문서 작업만 Phase 1의 약 3~4배(5~8일)이고, 여기에 실장비 실측(빌드→tok/s→LoRA→게이트→학습 스택 aarch64)이 최소 2~3일 더 든다. 실장비 없이 미리 할 수 있는 것은 제안 2·4·5·7(스텁 시험으로 검증 가능)이며, 제안 1·3·8·9는 실측 수치가 있어야 기본값을 정할 수 있다. 학습 스택(bitsandbytes aarch64·mergekit)은 확인 필요 항목이라 최악의 경우 `--no-4bit` 분기 개발이 추가된다. 근거: node_modules 미설치라 전부 소스·lock·문서 읽기 기반 추정이며, 실행·시험은 돌리지 못했다.

## 3. 계획서와의 관계 (사용자 결정 필요)
GB10(DGX Spark) 서버 이식은 『GIJO_AS_시장경쟁력_전중후_계획서.md』 3~5절 어디에도 없는 작업입니다. 가장 가까운 항목은 **후-4 에어갭 에디션**(폐쇄망 하드웨어 옵션으로 ARM·통합메모리 장비를 추가하는 일)이고, 부분적으로 **후-1 GA**(자가진단·백업·운영 절차 완결), **중-3/중-4**(모델을 키우기 전 게이트 통과·학습 병행), **전-6**(속도 수치를 정직하게 — 3090보다 느림), **중-5**(N2SF 배치 가이드에 GB10 사양 행)와 닿아 있습니다. 반면 「전」(파일럿 전 증거 만들기)에 끼울 근거는 파일럿 후보(전-5) 고객이 GB10을 요구하지 않는 한 없습니다. CLAUDE.md 규칙(계획서에 없는 큰 작업은 관계를 먼저 묻는다)에 따라 착수 전에 여쭙습니다: (a) 이 작업을 계획서에 「후-7 통합메모리 대용량 장비(DGX Spark GB10) 지원」 같은 신규 항목으로 넣을지, 아니면 후-4 에어갭 에디션의 하위 작업으로 둘지, (b) 우선순위를 「후」(6~12개월)로 둘지 앞당길지 — 앞당기려면 파일럿 고객 요구나 GB10 실장비 확보가 근거가 되어야 합니다, (c) 이번에 제안한 10건 중 실장비 없이 미리 할 수 있는 2·4·5·7(GPU 감지 분기·벤치 도구·데이터 이식 일반화·배포 스크립트)만 먼저 진행할지. 결정은 사용자 몫이며, 저는 「GB10이 실제로 확보되기 전에는 코드 변경을 시작하지 않고 계획서 항목 신설과 실측 체크리스트 준비까지만」을 권합니다.

### P-1-build · llama.cpp를 GB10 전용(sm_121·CUDA 13)으로 빌드하는 설치 절차 신설 — 배포 가이드 §3.8 「네이티브 Linux 서버(DGX Spark)」
- **우선** P0 · **크기** M · **계획서** 신규(계획서 반영 필요) — 관계: 후-4 에어갭 에디션(GPU 서버 사양 다변화)·중-5 N2SF 배치 가이드
- **문제**: 배포 가이드 §3.7.1~3.7.2는 RTX 3090·x86 WSL 전제다: CUDA 리포지토리가 `wsl-ubuntu/x86_64`(126행)이고 빌드 플래그가 `-DCMAKE_CUDA_ARCHITECTURES=86`(137행)이라, GB10(arm64 DGX OS, sm_121)에서 그대로 따르면 x86 리포 단계에서 막히고 86 빌드는 GB10 GPU 커널 동작 보장이 없다(PTX JIT 여부는 facts에 없음 — 확인 필요). 이 바이너리 없이는 채팅 LLM·bge-m3 임베딩이 GPU에서 뜨지 않아 챗봇·RAG가 첫 기동부터 죽는다. 또 유닛의 `/usr/lib/wsl/lib`(172행)·`.wslconfig`·portproxy·작업 스케줄러(204~207행)는 GB10에 무의미하고, 코드가 부르는 lsof·pgrep·sshpass(localengine.ts 479·587행, hardeningscan.ts 104행)가 DGX OS에 기본 포함인지는 확인 필요.
- **변경**: GIJO_AS_배포_가이드.md에 §3.8 신설(요청 시 문서 갱신): (1) 사전 탑재 확인 `nvidia-smi`·`nvcc --version`(CUDA 13.0 — DGX OS 기본 탑재라 `cuda-toolkit-13-3` 설치 단계 건너뜀)·`free -h`(약 120GiB 정상, nvidia-smi 메모리 열 N/A는 iGPU 설계상 정상임을 명기) (2) `sudo apt install -y build-essential cmake python3.12-venv lsof procps openssh-client sshpass rsync curl fonts-nanum fonts-noto-cjk` (3) Node 22 (4) NVIDIA 공식 플레이북 플래그로 빌드 `cmake -B build -DGGML_NATIVE=ON -DGGML_CUDA=ON -DGGML_CURL=ON -DCMAKE_CUDA_ARCHITECTURES=121a-real -DCMAKE_BUILD_TYPE=Release && cmake --build build --config Release --target llama-server llama-quantize -j` → `build/bin/llama-server --list-devices`에 CUDA0(GB10) 확인 (5) systemd 유닛에서 `/usr/lib/wsl/lib` 제거, 선택 항목으로 `ExecStartPre=+/bin/sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'`(기본 주석 처리 — 재시작마다 페이지캐시를 비우는 부작용 안내) (6) `sudo ufw status` 확인 후 4000/tcp 사내망 허용(DGX OS 기본 방화벽 상태는 확인 필요) (7) `systemctl enable --now` + 재부팅 테스트. 141행 표에 「DGX Spark/GB10 = 121a-real」 행, §2.1 하드웨어 표에 「DGX Spark 128GB(통합)」 행 추가. preflight.ts에 「외부 명령 존재(which lsof pgrep ssh)」 warn 항목 1개 추가. llamabin.ts(11행)·스폰 인자 `-ngl -1`(localengine.ts 381행)·`GIJO_LLAMA_SERVER_PATH` env는 수정 불필요.
- **확인 방법(GB10 실측)**: GB10 실장비: ① `nvcc --version` 13.0 이상 · `uname -m` aarch64 ② `build/bin/llama-server --list-devices`에 CUDA0(GB10) 표시 ③ 임베딩 서버(8081, ctx/batch/ubatch 8192 명시) 기동 → 512토큰 초과 한글 입력 `/embeddings` 200(HTTP500 함정 재현 여부) ④ Qwen3-14B Q4 로드 → 짧은 생성 1회 tok/s 기록(20~30 t/s대 기대) ⑤ 같은 모델에 `--lora` 어댑터 적용 상태로 생성 1회 — 오류·품질 이상 없는지(sm_121 LoRA는 보고 없음) ⑥ `/api/admin/preflight`에서 llama-server pass·외부 명령 항목 pass ⑦ 재부팅 후 `systemctl status gijo-as` active·health 200
- **위험**: 낮음 — 문서·설치 절차 위주라 기존 WSL 운영엔 영향 없음. 단 121a-real 빌드가 llama.cpp 최신 커밋에서만 유효할 수 있어 커밋 고정 필요. drop_caches는 root 권한이라 유닛 실행줄 `+` 접두어 사용 시 보안 검토 한 번.

### P-2-gpumem · 통합메모리 NVIDIA GPU 감지 분기 — `server/src/util/gpumem.ts` 한 곳에 모아 localengine·preflight·티어 API·화면 문구가 128GB를 실수치로 보게 한다

- **문제**: GB10의 nvidia-smi는 memory.used/free를 `[N/A]` 문자열로 준다(NVIDIA KB 5775, iGPU 설계상 동작). 코드는 nvidia-smi가 '있다'고 보되 값은 NaN이 되어: getFreeVramMb(localengine.ts 191~194행)가 null → makeRoomFor(283행)가 '개수 상한 폴백'으로 조용히 전환돼 128GB 예산이 통째로 무시되고, getGpuUsage(226·232행)가 available:false → 티어 라우트(895행)가 「NVIDIA GPU를 찾지 못했습니다 — 미지원 환경」을 응답 → settings.html 1417행 「NVIDIA GPU 없음」·1429행 「판정 불가」, dashboard.html 380행 GPU 막대 사라짐. 채팅은 잘 되는데 화면이 거짓말하는, 이 제품이 가장 경계하는 고장이다. preflight.ts 26행은 `[N/A]`를 detail에 그대로 실어 pass하고, hang 감시 경고(652·758행)는 'WSL2 GPU 추정'을 네이티브 리눅스에도 붙인다.

- **문제**: GB10의 큰 가치는 128GB로 14B 학습을 넉넉히 돌리는 것인데, trainenv.ts 52행 필수 의존성에 bitsandbytes(4bit)가 있고 finetune_qlora14b.py 109행은 nf4를 고정으로 켠다 — bitsandbytes aarch64 CUDA 휠 유무는 facts에 없어 확인 필요이며, 없으면 probeTrainDeps가 실패해 원클릭 학습 루프가 GB10에서 한 번도 못 돈다. merge.ts 93행은 화면(merge.html 「실행 명령(GPU 머신)」)에 표시되는 수동 명령에 pythonbin.ts 11행이 금지한 `python` 맨이름을 쓴다 — Ubuntu 24.04엔 `python`이 없어 venv 미활성 셸에서 막힌다(WSL·GB10 공통 안내문 결함, 서버 실행 코드는 아님). pauseInferenceEngines(localengine.ts 815~821행, finetune.ts 76행, learnloop.ts 567행)는 'GPU 1대·24GB 독점' 전제로 학습 전 채팅·RAG를 전부 내리는데, 128GB에선 14B 추론(~14GB)+bge(~2GB)+14B QLoRA를 얹어도 들어가(facts: gpt-oss-120b QLoRA도 68GB) 「학습하면서 서비스 유지」라는 GB10의 이점을 코드가 스스로 막는다 — 다만 대역폭 공유라 학습 중 응답 저하는 실측 필요.

- **확인 방법(GB10 실측)**: GB10 실장비: ① `venv-train/bin/python -c 'import torch;print(torch.cuda.is_available(), torch.cuda.get_device_capability())'` → True, (12,1) ② `pip install bitsandbytes` aarch64 성공 여부 기록(확인 필요 항목 해소) ③ `probeTrainDeps()` 전 항목 pass 또는 `--no-4bit` 경로로 pass ④ `finetune_qlora14b.py --smoke` 완료, 피크 메모리 `free -h`로 기록 ⑤ 학습 중 채팅 요청 tok/s(유지 모드) vs 평시 tok/s — 하락폭으로 GIJO_TRAIN_KEEP_INFERENCE 기본값 결정 ⑥ 학습 산출 어댑터를 `--lora`로 적재 → 평가 게이트 3축(제안 8) ⑦ merge.html 표시 명령을 venv 미활성 셸에서 복사 실행 → `python: command not found` 없음 ⑧ `mergePreflight()` pass, mergekit 병합 1회 → convert_hf_to_gguf 성공

· GIJO 서버 프로세스군(Node+better-sqlite3+LanceDB 인덱스 상주+Playwright 리포트 렌더 순간 부하): **약 4~6GiB 가정** — 3090 운영에선 시스템 RAM에 있어 VRAM 산정에 안 들어갔지만 통합메모리에선 같은 풀을 쓴다(현 산정식엔 없는 항목). 「확인 필요」.
· 임베딩 bge-m3(ctx/batch/ubatch 8192 고정, localengine.ts:558): **1.5~2GiB** (GIJO_AS_VRAM_티어_구동_가이드라인.md §2 산정식 그대로).

· 안전 여유: 가이드라인 §4 원칙 「VRAM의 70~80%까지만 계획 점유」를 통합메모리에도 적용 → 최소 10%(≈12GiB).
[결과]

  낙관(여유 5%): 117.8 − 4 − 4 − 1.5 − 6 ≈ **102GiB**

**티어 제안**: [현 구조] `GIJO_TIERS`(localengine.ts:83-86)는 (maxLoadedModels, ctxSize, overheadMb) 3값 묶음이고, `recommendTier(totalMb)`(102-104)는 `<16000→lite, <28000→standard, 그 외→pro`다. 티어 API(882-897)는 `getGpuUsage().memTotalMb`를 넣는다.
[GB10을 기존 Pro로 두면 생기는 낭비·오판 3가지]
① 애초에 Pro까지 못 간다 — GB10의 nvidia-smi는 memory.used/free를 `[N/A]`로 주므로(facts §3) `getGpuUsage`가 `available:false`(232줄)를 돌려주고 티어 API는 「NVIDIA GPU를 찾지 못했습니다 … 미지원 환경」(895줄)을 낸다. 사람이 수동으로 Pro를 골라도 `makeRoomFor`는 `getFreeVramMb()===null`(284줄)이라 개수 상한 폴백으로만 돈다.
② 억지로 Pro로 보면 「채팅 LLM 3개·32K·오버헤드 5000MB」 = 14B×3 ≈ 48GB만 계획 점유 → 가용 90~95GB 중 약 45GB가 영원히 빈다. 게다가 pool은 modelId 키(347·393줄)라 같은 14B를 3개 띄울 수도 없다 — 가이드라인의 「14B 2인스턴스」(19줄)는 코드에 없다.
③ overheadMb 5000은 14B·32K용이다. 32B(KV ≈8GB) 이상을 올리면 필요량을 절반 이하로 보고, 통합메모리에선 그 오차가 GPU 실패가 아니라 OS·DB·서버 프로세스까지 밀어내는 메모리 압박이 된다.
[제안 — 새 티어 1개 + 판정 입력 교체]
(1) `GIJO_TIERS`에 4번째 항목 추가: `{ id: "unified", label: "Unified(대용량 통합메모리)", vramLabel: "96GB+ 통합메모리", maxLoadedModels: 2, ctxSize: 40960, overheadMb: 12000, parallel: 4, desc: "14B 1개를 --parallel 4로 · 40K — 동시 4명, 또는 32B/120B-MoE 1개" }`. 근거: GB10의 병목은 용량이 아니라 대역폭(273GB/s)이므로 「모델 수」를 늘리는 대신 **한 프로세스 안의 동시 슬롯(--parallel)과 컨텍스트**를 늘리는 것이 맞다(llama.cpp는 슬롯을 묶어 디코드하므로 프로세스 여러 개보다 대역폭 효율이 낫다 — 다만 슬롯당 t/s 감소폭은 실측 필요). `확인용칸()`(713-716줄)이 이미 `--parallel 2`를 붙이므로 티어에 `parallel` 필드를 두고 그 함수가 티어값을 읽게 하면 된다. ctxSize 40960은 Qwen3-14B native(modelquirks.ts:161)와 일치 — 그 이상은 rope 스케일링이 필요해 별도 검증(G3-04).
(2) `recommendTier`에 통합메모리 분기: `unified ? (totalMb >= 96000 ? "unified" : totalMb >= 28000 ? "pro" : …)`. 입력은 nvidia-smi 대신 `/proc/meminfo`의 `MemTotal`/`MemAvailable`(facts: llama-swap·vLLM 커뮤니티 표준)로 — mac 분기(189·213줄)가 `os.freemem()/os.totalmem()`을 쓰는 것과 같은 자리에 `IS_LINUX_UMA` 분기를 세운다. UMA 판정은 `nvidia-smi --query-gpu=name,memory.total`의 memory.total이 숫자가 아니거나 name에 "GB10"이 있을 때(확인 필요: memory.total까지 N/A인지는 open question).
(3) 기존 Pro는 그대로 두되 desc를 가이드라인(14B 2인스턴스)과 맞춘다(G3-11). Pro를 「32GB급 전용 GPU」로, Unified를 「통합메모리 96GB+」로 분리하면 M1 Max 32GB(mac)는 계속 standard/pro 판정을 받고 GB10만 새 티어로 간다.
[동시 사용자 관점 결론] 「큰 모델 1개」와 「14B 여러 인스턴스」는 GB10에서 둘 다 정답이 아니다 — 14B 1프로세스 + --parallel 4(KV 40K 기준 ≈6.5GB, 총 ≈18GB)가 동시 4명을 받으면서도 가용량의 20%만 쓴다. 남는 70GB는 「모델 교체 없이 두 번째 모델 상주」(예: 30B-A3B를 분석 에이전트 전용으로 게이트 통과 후)나 「LoRA 학습 루프(중-4)를 운영 모델과 동시에」에 쓰는 것이 실익이다. 72B급은 4~6 t/s라 동시 사용자가 늘수록 더 나빠지므로 대화형엔 배제.

**정직하게 밝힐 한계**
- 【속도】 14B Q4 단일 응답은 RTX 3090보다 약 2배 느리다(facts: 14B Q4_K_M 3090 56.1 t/s vs DGX Spark 26.4 t/s; 대역폭 936 vs 273GB/s = 3.4배 차이). 모델 선택 가이드 59줄의 「초당 15~20토큰」·가이드라인 8줄의 「설명(CVE) 4.8초」는 3090 실측이며, GB10에선 8~13 t/s·8~10초대로 적어야 한다(동일 빌드·동일 GGUF 직접 대조 자료는 없어 실측 필요).
- 【용량 ≠ 속도】 128GB로 70B급을 「올릴 수는」 있지만 4~7 t/s(실측 2.7 보고도 있음)라 대화형 제품으로는 성립하지 않는다 — 가이드라인 §7이 CPU-only(2~5 t/s)를 「실사용 불가」로 못 박은 것과 같은 구간. 큰 모델을 팔지 말고 「동시 사용자·긴 문맥·학습 병행」을 팔아야 한다.
- 【평가 게이트 미통과 상태】 GB10에서 모델을 바꾸면(32B·MoE 등) 라우팅 66/66·안전 9/9·한국어 24/24·견고성 71점 기준선(tools/evalgate/baseline.json, 2026-08-09 Qwen3-14B 기준)은 전부 무효다. 게이트를 GB10 서버(GIJO_SERVER_URL)로 돌려 통과하기 전엔 어떤 모델도 「채택」이 아니다(계획서 중-3).
- 【CUDA 13·sm_121 전용 빌드】 배포 가이드 §3.7.2의 `-DCMAKE_CUDA_ARCHITECTURES=86` 빌드는 GB10에서 동작하지 않는다. 121a-real + CUDA 13.0(기본 탑재) 빌드가 필요하고, x86 바이너리·컨테이너는 exec format error(facts 부록 a). LoRA(--lora) 적용이 sm_121 빌드에서 정상인지는 보고가 없어 확인 필요.
- 【nvidia-smi 메모리 미보고】 GB10에선 nvidia-smi가 메모리 사용량을 「Not Supported / [N/A]」로 준다(NVIDIA KB 5775, 설계상 동작). 현 제품의 VRAM 예산·티어 자동판정·model-benchmark 도구가 전부 이 값에 의존하므로 코드 분기 없이는 「미지원 환경」으로 판정된다.
- 【발열·클럭】 GPU 클럭이 721MHz 등에 고정되는 포럼 보고가 있어(facts 부록 b) 성능 편차가 있을 수 있고, 커널 6.17에서 pp가 향상됐다는 보고(부록 c)처럼 DGX OS 버전에 따라 수치가 달라진다 — 영업 수치는 실기 실측치만 쓴다.
- 【ARM 생태계】 DGX OS는 Ubuntu 24.04 aarch64다. better-sqlite3(-multiple-ciphers) 12.11.1은 Node 22/24 linux-arm64 프리빌드가 있으나 Node 20은 없어 소스 빌드가 필요하고, onnxruntime-node는 arm64 CPU EP만, Chrome 채널은 arm64 불가(Chromium은 가능). Windows NSIS 클라이언트는 그대로 쓰되 GB10 올인원(Linux arm64 Electron)은 linux 타깃이 아직 없다.
- 【가격·수급】 Founders Edition US$3,999 → 2026-02 US$4,699로 인상(메모리 수급난). 국내 정가·리드타임은 확인 필요. 3090 1장(중고 시세) 대비 5~6배 비용으로 「단일 응답은 더 느린」 장비라는 점을 견적서에 숨기면 안 된다(전-6 정직 경계).
- 【통합메모리의 양날】 페이지캐시·OS·DB·Node 서버가 LLM과 같은 풀을 쓴다. 3090에선 시스템 RAM에 있던 4~6GB가 GB10에선 LLM 예산에서 빠진다. 대형 GGUF 로드 전 drop_caches가 공식 플레이북에 등장할 만큼 운영 손질이 필요하다.

## 6. 사용자에게 물을 것
- GB10(DGX Spark)이 실제로 확보돼 있습니까, 도입 예정입니까, 아니면 검토만입니까? 실장비 유무에 따라 제안 1·3·8·9(실측 없이는 기본값을 못 정함)는 착수 자체가 달라집니다.
- 배치는 「GB10 = 서버(GPU 머신), 클라이언트는 Windows 그대로(분산 모드)」로 이해했습니다 — 맞습니까? GB10에서 Electron까지 도는 올인원(Linux arm64)까지 원하시면 제안 10이 살아납니다.
- GB10을 RTX 3090 WSL을 **대체**하는 운영 서버로 쓸 생각입니까, 아니면 3090은 운영으로 두고 GB10은 학습·대형 모델 검증용 **2번째 GPU 머신**입니까? 후자면 DB 이식(제안 5)·배포 경로(제안 7)의 범위가 달라집니다.
- 모델을 키울 계획이 있습니까(Qwen3-32B 약 10 t/s로 느림 / Qwen3-30B-A3B MoE 약 89 t/s / gpt-oss-120b 약 35 t/s)? 아니면 14B를 유지하고 「동시 사용자 슬롯·2모델 상주·학습 병행」만 노립니까? 이 답이 제안 3의 unified 티어 기본값(parallel·ctx·maxLoadedModels)을 정합니다.
- 티어 판정의 「총 VRAM」을 어느 값으로 볼지 정책 결정이 필요합니다 — /proc/meminfo MemTotal(약 120GiB) / CUDA 보고 121.7GiB / 커뮤니티 크래시 임계 117.8GiB 중 하나에 안전 여유(10~15%)를 뺀 값을 제안합니다.
- 운영 DB의 「저장 암호화 복구 열쇠」가 지금 실제로 종이로 보관돼 있습니까? 없으면 GB10 이식 전에 재발급이 선행돼야 하고, 열쇠 없이는 이식이 불가합니다.
- Node 22로 표준을 올릴 때 기존 WSL 운영도 22로 맞출까요(better-sqlite3 계열 ABI 결속 때문에 두 머신 버전이 갈라지면 node_modules 반입물이 호환되지 않습니다)?
- 계획서 반영 방식: 「후-7 GB10 지원」 신규 항목으로 넣을지, 후-4 에어갭 에디션의 하위 작업으로 둘지, 우선순위는 「후」 그대로인지 앞당길지 결정해 주십시오.
- GB10에 git hub remote(WireGuard 피어 추가)를 등록해 Mac에서 ssh로 배포를 트리거하는 구조(제안 7)로 가도 됩니까? 공동작업 규칙상 제임스는 운영 접근 불가이므로 GB10도 같은 규칙을 적용하는 것으로 이해했습니다.
- GB10 관련 문서 갱신(배포 가이드 §3.8·티어 가이드라인 §7·모델 선택 가이드 속도 행)은 요청 시에만 하는 규칙입니다 — 이번 보고와 함께 갱신을 원하십니까?

## 8. 조사에서 못 닫은 질문
- nvidia-smi가 GB10에서 memory.total까지 [N/A]인지(used/free는 확실) 그리고 `nvidia-smi -q`·NVML nvmlDeviceGetMemoryInfo가 어떤 값을 주는지 — NVIDIA 포럼·KB 원문(egress 차단)을 직접 못 읽어 문장 인용 불가. 실기 `nvidia-smi --query-gpu=name,memory.total,memory.used,memory.free,utilization.gpu --format=csv`로 확인 필요.
- Qwen3-14B Q4 dense의 DGX Spark llama.cpp 실측치는 직접 자료가 없음(Ministral 14B Q4_K_M 26.4 t/s로 대체). 우리 운영 모델(Qwen3-14B Q4 + LoRA 어댑터)을 같은 llama.cpp 빌드로 3090·GB10에서 llama-bench 대조 필요.
- llama-server의 LoRA 어댑터(--lora) 적용이 sm_121/CUDA 13 빌드에서 성능·정확도 이상 없이 동작하는지 — 보고 없음, 확인 필요.
- CUDA가 보는 GPU 총 메모리(약 121.7GiB)와 free -h total(약 120GiB), 크래시 임계(약 117.8GiB) 중 어느 값을 티어 판정의 '총 VRAM'으로 쓸지 — 정책 결정 필요(예: MemAvailable 기반 + 안전 여유 10%).
- GGML_CUDA_ENABLE_UNIFIED_MEMORY=1의 득실(로드 시간 단축 vs 메모리 이상 보고)이 상충 — 실측으로 결정.

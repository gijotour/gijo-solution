## 비고 — 뜨지 않은 칸의 원인 (server.log 원문)

이번 라운드 0점의 **대부분은 모델 품질이 아니라 구조적 상한**이다. 하네스·설정 잘못이 아니며 `--ctx`를 올려도 풀리지 않는다.

**⁽¹⁾ 학습 컨텍스트 32K — needle_64k 원리상 불가** (`midm-2.0-mini-2.3b`, `exaone-3.5-32b`, `exaone-3.5-2.4b`)

```
W llama_context: n_ctx_seq (65536) > n_ctx_train (32768) -- possible training context overflow
I srv    load_model: initializing, n_slots = 1, n_ctx_slot = 32768, kv_unified = 'false'
E srv    send_error: error: request (53563 tokens) exceeds the available context size (32768 tokens)
```

(midm은 같은 과제가 46,247토큰으로 잡혀 동일하게 400.) rope 스케일링을 억지로 걸어 점수를 만들지 않았다 — 그건 실측이 아니다.

→ **needle_64k를 뺀 5과제 평균**: midm 0.65 · exaone-3.5-32b **0.78** · exaone-3.5-2.4b 0.52

**⁽²⁾ 학습 컨텍스트 8K — needle 16k/32k/64k 3개 전멸** (`varco-8b`)

```
W llama_context: n_ctx_seq (65536) > n_ctx_train (8192) -- possible training context overflow
W srv    load_model: the slot context (65536) exceeds the training context of the model (8192) - capping
I srv    load_model: initializing, n_slots = 1, n_ctx_slot = 8192, kv_unified = 'false'
E srv    send_error: error: request (16494 tokens) exceeds the available context size (8192 tokens)
```

Llama-3.1 **구조**지만 학습 문맥은 8192다 — 「8B니까 128K 되겠지」라는 추정을 로그가 깨뜨렸다. 각 요청이 50~80ms만에 400으로 즉사.

→ **8K 이내 과제만 보면** 어려운 평균 0.52(참고치, 표에는 넣지 않음)

**⁽³⁾ 이 하네스로 평가 불가 — 문법 샘플러 실패 + ctx 4096** (`solar-pro-22b`)

```
W llama_context: n_ctx_seq (32768) > n_ctx_train (4096) -- possible training context overflow
I srv    load_model: initializing, n_slots = 1, n_ctx_slot = 4096, kv_unified = 'false'
E common_sampler_init: error initializing grammar sampler for grammar:
E srv    send_error: task id = 0, error: Failed to initialize samplers: std::exception
```

적재는 성공했으나 **13과제 전부 0점 — 답을 한 글자도 못 받았다.** 채점기가 낮게 준 게 아니라 요청 자체가 전부 실패했다.

- `json_schema` 강제 과제 → 위 문법 샘플러 오류로 HTTP **400**.
- 스키마 없는 서술형 2건(`report_draft`·`report_fix`) → 62초를 다 쓰고 HTTP **500** `The model produced output that does not match the expected peg-native format`.
- needle 3종 → ctx 4096 초과로 400 (16k 과제가 **37,308토큰**, 32k가 **75,998**, 64k가 **151,414**).
- `models.json` 비고의 「GGUF가 llama 구조로 변환됨 · tokenizer.ggml.pre 없음」이 여기서 실제로 터진 것으로 보인다.
- **덤으로 드러난 것 — 한국어 토크나이저가 매우 비효율적**: 같은 지문을 다른 모델이 약 32K 토큰으로 읽는데 solar는 **75,998토큰**(약 50,000자)을 썼다. 약 0.66자/토큰으로 Qwen 계열 대비 **2.3~2.4배**를 더 먹는다. ctx 문제가 없었더라도 한국어 장문에 불리하다.
- **속도**: 요청이 전부 실패해 하네스의 `prefillTps`/`genTps`는 `undefined`다(지어내지 않았다). 생성 속도만은 실패한 생성 도중 서버가 스스로 찍었다 — `tg = 14.41 ~ 14.72 t/s`. 표의 14.4는 그 하한이다. **프리필은 보고하지 않는다** — 유효한 측정이 하나도 없다.
- **판정**: 후보에서 빼거나, 굳이 재려면 **스키마 없는 별도 규약 + ctx 4096 전제**로 다시 설계해야 한다. 그건 다른 시험이지 이 시험이 아니다.

**⁽⁴⁾ 형식 미준수로 인한 0점 — 능력 아님** (`exaone-3.5-2.4b` priority_6)

상위 3 순서는 V2>V3>V4로 **맞혔으나**, 답에 자산명을 덧붙여 `V1` 토큰이 사라져 채점기가 미끼 배제 판정을 못 했다. 0.00은 「순서를 틀렸다」가 아니라 「형식을 안 지켰다」로 읽어야 한다.

**⁽⁵⁾** `qwen3.8-27b` 행은 3회차와 **같은 ctx 65536** 조건의 `results-27b/summary.md` 값이다.

### 이번 라운드의 구조적 관찰

5종 중 **4종이 컨텍스트 상한에서 걸렸다**(4K 1개 · 8K 1개 · 32K 3개). 한국어 특화 모델은 대체로 학습 문맥이 짧다. **needle_64k를 통과한 모델은 지금까지 `qwen3.8-27b`와 `gpt-oss-20b` 둘뿐**이며, 3회차 5종 중에는 **하나도 없다.**

그리고 **ti_trap은 5종 전원 0.00**이다. 정답 2건은 대체로 맞히지만 함정(버전 경계·제품명 유사·메이저 차이)을 물어 오탐이 난다. 전 라운드를 통틀어 ti_trap에 0점 아닌 점수를 낸 모델은 `qwen3.8-27b`(0.50) **하나뿐**이다.

### scan — 긴 문맥 회수

- **신규 후보 없음.** 5종 전부 needle_64k 0점이고, 그중 varco·solar는 32K도 못 읽는다.
- 유지 판단: **`qwen3.8-27b`(0.92)**, 속도가 필요하면 **`gpt-oss-20b`(0.81, 생성 74 tok/s)**. 둘 다 Apache-2.0.

### ti — 함정 걸러내기(절제)

- **신규 후보 전멸(5종 전원 0.00).** 이 역할은 「맞히기」가 아니라 「**해당 없음이라 말하기**」인데, 소형·중형 한국어 모델은 이걸 못 한다.
- 유지 판단: `qwen3.8-27b`(0.50)가 유일한 비-0점이지만 그것도 절반이다. **이 역할은 모델 교체가 아니라 코드(버전 비교 로직)로 푸는 것이 맞다** — 「7B에 프롬프트 규칙 더해 행동 교정하지 말 것」의 전형적인 사례로 보인다.

### analysis — 우선순위 정렬

- **`exaone-3.5-32b`가 priority_6 1.00**으로 5종 중 유일하게 통과했다(쉬운 priority_rank도 1.00). 다만 **비상업**이라 출하 불가이고, 생성 10.3 tok/s로 사람이 기다리기 느리다.

- 유지 판단: 기존 `qwen3-14b`·`gpt-oss-20b`·`qwen3.8-27b`가 전부 1.00. **교체 이유 없음.**

### report — 서식 채우기

- **여기가 이번 라운드의 유일한 실질 소득이다.**
- **`midm-2.0-mini-2.3b`(MIT)**: `report_draft` 1.00 · `report_fix` 1.00 · `scan_extract` 1.00 · `tool_select` 1.00, 한국어 산문 100%·한자 0, **생성 98.2 tok/s · 적재 4s · 1.33GiB**.

- varco 0.77(기한 사실 본문 미반영)·exaone-32b 0.92(6절 중 5절)로 오히려 큰 모델이 낮다.

- 시험 서버는 **8093 하나·한 번에 한 모델**. 하네스가 스스로 띄우고 내렸다.
- 종료 후 확인: `pgrep -fa "^\S*llama-server -m"` → 제품 **8080**(Qwen3.8-Flash-Next)·**8081**(bge-m3) **두 줄만**. `curl localhost:8093/health` → exit 7(연결 안 됨). 8080·8081 `/health` 모두 `{"status":"ok"}`.
- `free -g`: 총 121GB / 사용 65GB / 가용 55GB — 시작 시점으로 복귀.
- ⚠ 실행 중 최대치는 `exaone-3.5-32b` 2회차에서 **108GB 사용 / 13GB 가용**이었다. **32B + 32K KV + 상주 제품 2개가 통합메모리 121GB의 거의 한계다.** 다음 라운드에서 32B 이상을 더 큰 ctx로 돌린다면 제품 노드와 충돌할 수 있다.
- GPU 메모리는 **재지 못했다** — gb10은 통합메모리라 `nvidia-smi`가 `[N/A]`를 준다. 판단은 `server.log`와 `free -g`로만 했다.

## 알려진 부작용·함정 (다음 사람 주의)

1. **`summary.md`는 `--only`로 돌린 모델만 담아 덮어쓴다.** 3회차 중 실행자가 바뀔 때마다 표가 한 줄로 줄었다. 원자료(모델별 `.json`)는 유실 없고, 중간 백업이 `summary.midm.md`·`summary.before-solar.md`·`summary.before-exaone32b.md`로 남아 있다. **통합 표가 필요하면 `.json`들로 다시 만들어야 한다**(이 보고서가 그렇게 만든 것이다).
2. **`pgrep -f "node run.mjs ..."`로 완료를 기다리면 그 `bash -c` 자기 명령줄이 패턴에 걸려 영원히 안 끝난다**(실제로 600초 타임아웃 발생). 지시서의 `pkill` 앵커 경고와 같은 부류다. 대기는 `ps -C node`나 로그의 「끝 —」 문자열로 판정할 것.
3. 지시서의 하네스 경로가 틀렸다(위 머리 참조).

## gb10 이용 내역

- **무엇에 썼나**: 이 작업 전체가 gb10 실측이다. `llama.cpp-next` 바이너리로 후보 5종을 8093에 하나씩 띄워 13과제(쉬움 7 + 어려움 6)씩 총 65회 채점, `server.log`에서 컨텍스트 클램프 원문 수집. 집계는 gb10 위에서 `node -e` 한 줄로 돌려 `.json` 원문을 세션으로 끌어오지 않았다(그 자체가 토큰 절약).
- **무엇을 돌려받았나**: 과제별 결정적 점수 · llama.cpp `timings` 실측 tok/s · 모델별 `n_ctx_train` 실제값 · 실패 원인 로그 원문.
- **값을 했나 — 했다.** 이 라운드 0점의 대부분이 「모델이 못한다」가 아니라 「**모델의 학습 문맥이 4K/8K/32K다**」였는데, 이건 gb10에서 **실제로 띄워 로그를 보지 않으면 알 수 없는 사실**이다. 로그를 안 봤으면 varco를 「8B인데 긴 문서를 못 읽는 나쁜 모델」로, solar를 「전부 틀리는 모델」로 **잘못 결론 낼 뻔했다.**
- **못 한 것**: GPU 메모리 점유 실측(통합메모리 `[N/A]`). `local-digest.mjs` 발췌는 안 썼다 — 이번에 읽은 파일이 전부 30~40줄 발췌(하네스 머리 주석·`models.json` 5줄·`summary.md`)라 800줄 기준에 안 걸렸고, 발췌를 부르는 편이 더 비쌌다.

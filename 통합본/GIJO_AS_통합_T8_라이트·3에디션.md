## 1. 에디션은 셋이고, 가르는 잣대는 「기능」이다

- 고객 안내 기준: **라이트·스탠다드·프로 세 가지**이며 「기계가 얼마나 큰가」가 아니라 **무엇을 할 수 있는가**로 나눈다 (knowledge/GIJO_AS_에디션_안내_고객용.md:3, :9~11).
- 이 원칙은 사장님 결정이다 — 「등급은 기능으로 가른다. VRAM은 정의가 아니라 **가이드**」 (GIJO_AS_제품_기능등급_가이드_2026-08-13.md:6~9).
- 등급표·화면·영업자료가 서로 갈릴 때는 이 원칙이 이긴다 (같은 파일:9).
- 최소 사양은 안내일 뿐이고, 가격·도입 조건은 문서가 아니라 영업 담당이 답한다 (knowledge/GIJO_AS_에디션_안내_고객용.md:14, :18).

**코드가 가진 등급값**(단일 출처 `server/src/engine/localengine.ts`)

| 등급 | 최소 VRAM | 문맥 | 상주 모델 |
|---|---|---|---|
| Lite (일부 기능 제약) | 10GB급 | 8K | 1 (localengine.ts:127) |
| Standard | 24GB급 | 32K | 1 (localengine.ts:128) |
| Pro | 48GB급 | 32K | 2 (localengine.ts:136) |
| Max (관제용) | 사양 확정 전 · **고를 수 없음**(planned) | 32K(자리표) | 3(자리표) (localengine.ts:143) |

▸ Max 행의 32K·3은 실측이 아니라 **Pro와 같은 모델을 전제한 자리표**다 — 사양이 정해지면 채운다고 코드가 적어 뒀다 (localengine.ts:137~144).

- ⚠ **프로는 지금 스탠다드와 엔진 동작이 같다** — 「A/B·검증 병행」은 코드에 없고, 모델을 몇 개 올릴지는 등급이 아니라 남은 VRAM이 정한다(2026-08-18 정직 표기, localengine.ts:129~136). 로그인 화면도 같은 문장을 쓴다 (client/src/renderer/pages/login.html:242, :608).
- 로그인 화면의 3택(🏢 표준·🚀 프로·🪶 라이트)에서 **라이트는 「고르는 모드」가 아니라 안내다** — 데이터 폴더가 갈리고 별도 설치본을 받아야 한다 (login.html:245~253, :592~596, :279~281 무료 다운로드 카드).
- 예전엔 「라이트·표준 2에디션」(GIJO_AS_제품_라인업_판매가이드.md:13, 2026-08-10 개정)이었고, 그전엔 Lite/Standard/Pro를 **모델 개수**로 나눈 7B 시절 3티어였다(같은 파일:16~19).

## 2. 라이트가 지금 무엇인가 — 화면 둘, 도구 열여섯

- 정체성: **담당자의 개인 보안 지식 조수** — 회사 데이터를 다루는 제품이 아니라 보안 지식·문서·규정에 근거 있는 답을 혼자 쓰는 PC에서 준다 (GIJO_AS_라이트_사양_2026-08-10.md:12~13).
- 기능 목록을 정하는 잣대: **데이터가 없는 도구는 넣어도 「없습니다」만 답한다** (같은 파일:30).
- **현재 메뉴는 「🧠 내 지식」·「📓 내 문서」 둘 + ⚙ 설정**이다 (client/src/renderer/pages/lite-screens.json:3~33, 설정 :37~124). 2026-08-22 사장님 결정 「라이트에는 내 문서 기능만. 프로에서 필요한 기능은 하나씩 요청해서 맛보기로 넣는다」로, 나머지 화면은 지우지 않고 `_메뉴에서_내린것`에 보관돼 있다 — 배열에서 옮기면 되살아난다 (같은 파일:126).
- 그래서 라이트는 「축소판」이 아니라 **입구**다 (lite-screens.json:126). 고객 안내도 같은 말로 적혀 있다 — 「고장이 아닙니다」 (GIJO_AS_Lite_설치안내서_2026-08-13.md:120~124).
- 「내 문서」는 새로 짠 화면이 아니라 **프로의 `mydocs.html?edition=lite`를 그대로 쓴다** — 한 벌 더 만들면 포크가 되기 때문 (lite-screens.json:20~31).
- 설정은 2026-08-31부터 사이드바 아래가 아니라 **상단바 ⚙**다 (client/src/renderer/pages/lite-app.html:64~65, :104~106).
- 도구는 **16개**다: search·explain·remediation·ontology_query · knowledge_status·recent_documents·doc_duplicates · watch_folder(목록·추가·제거) · add_task·complete_task·reopen_task·work_session_status · run_hardening_scan · law_lookup (server/src/lite/lite-tools.json:17~37).
  - `law_lookup`은 **기본 꺼짐**이고, 꺼져 있어도 번들 규제 문서로 법규 질문에 답한다 (lite-tools.json:37).
  - `run_hardening_scan`은 **사람이 입력한 대상만** — 대역 스캔 금지 (lite-tools.json:35).
- 도구를 줄이는 이유는 VRAM이 아니라 **ctx 8192 안의 자리와 프리필 시간**이다 — **77개** 카탈로그가 7,984토큰인데 라이트 문맥이 8,192다 (lite-tools.json:7). ⚠ 같은 값을 GIJO_AS_라이트_사양_2026-08-10.md:57은 「78개」로 적는다 — 두 문서의 숫자가 어긋나 있다(전체 도구 수는 78, lite-tools.json:5).
- **가드레일은 「최소 기능」에서 뺄 수 없다** — 7.6B 맨몸 견고성 36점이 담당자 PC에 그대로 드러나고 봐 줄 사람이 없다 (GIJO_AS_라이트_사양_2026-08-10.md:86~101). 다만 제품 경로 전체로 재면 7.6B와 14B가 **같은 92점·뚫림 2**이고, 남는 둘은 모델이 아니라 「자료·지시 분리층」의 문제다 (같은 파일:149~172).
- 예전엔 도구 8개·화면 5개(사양서:34~40, :80~82) → 도구 13개·화면 9개(GIJO_AS_Lite_계획서_2026-08-12.md:130, lite-screens.json 초안)였다. `lite-tools.json:3~6`의 「13개·4,056자」는 2026-08-12 실측값 그대로다. 설치안내서(2026-08-13판:121)도 아직 옛 이름 「AI에게 물어보기」로 적는다.

## 3. 출하 구성 — 임베딩만 동봉, 챗 모델은 고객이 등록

2026-08-13에 셋을 한 장으로 묶어 결재를 올렸고(GIJO_AS_라이트_출하_결정서_2026-08-13.md:121~127), 사장님 지시 「전부 진행, 문제가 있으면 추천안으로」로 셋 다 채택·집행됐다 (같은 파일:138~146).

| | 결정 | 근거 |
|---|---|---|
| ⓑ llama-server | **동봉한다** (mac=Metal, win=CUDA) | 없으면 화면만 보이고 대화가 안 된다 (출하_결정서:20~32) |
| ⓐ 대상 사양 | **10GB 이상** | 화면 그리는 8GB 카드는 94%로 돈다 (출하_결정서:59~73) |
| ⓒ 모델 | **임베딩(bge-m3)만 동봉 · 챗 LLM은 고객 등록** | 2026-08-13 사장님 재결정으로 「전부 동봉」을 뒤집음, dmg 6.2GB → 약 1.3GB (출하_결정서:166~172) |

- 코드가 그대로다: 동봉 실행부는 win `llama-cuda` / mac `llama-metal` (server/src/lite/env.ts:38~44), 챗 모델은 안 싣고 임베딩만 쓰기 폴더로 한 번 복사한다 (env.ts:55~67, :69~71).
- 빌드 산출물도 같다 — `extraResources`에 `bge-m3`, win에 `llama-cuda`+`python-dist`, mac에 `llama-metal` (client/electron-builder.lite.json).
- Windows는 **exe 하나로 끝난다** — CUDA·파이썬·런타임이 전부 설치본 안에 있고, 서버는 이 PC의 **7445 포트**에서 돈다 (GIJO_AS_Lite_설치안내서_2026-08-13.md:104~105, :119). 최신 배포본은 `GIJO AS Lite Setup 1.4.0.exe` 1,616MB이며 SHA256 대조를 안내한다 (같은 파일:110~114, client/release-lite/에 실물 존재 — 1,694,761,091바이트).
- 챗 모델 등록은 두 길 — **파일(gguf, 폐쇄망·권장)** 또는 **받기(HF, 7~8B만)** (설치안내서:38~49, :125~131).
- 라이트 모델을 HF로 배포할 수 있다: `gijo-main-orchestrator`의 베이스가 Qwen2.5-7B(Apache 2.0)라 업로드에 걸림돌이 없고, 그래도 **비공개+토큰**을 권한다. `merged-lily` 계열은 계보 불명확이라 올리지 않는다 (출하_결정서:184~197).
- 첫 실행 관문이 「모델 등록」이므로 대시보드·설정이 그 자리를 연다 — 2026-08-13 스모크에서 등록→대화→화면 전부 관통을 확인했다 (GIJO_AS_라이트_스모크_2026-08-13.md:6~29).

## 4. 왜 10GB인가 — 실측이 답한 것, 그리고 틀렸던 이유

- 결정: **10GB급 · ctx 8192**(2026-08-12 사장님) — 8GB는 산수가 안 맞았다 (GIJO_AS_Lite_계획서_2026-08-12.md:26, :147~154).
- 「도구를 줄여 프롬프트를 91% 줄인 것이 8GB의 근거」는 **틀린 근거였다** — llama.cpp는 KV 캐시를 `--ctx-size`만큼 미리 잡아 카탈로그 길이와 무관하다 (계획서:15~19, 라이트_사양:49~54).
- 실측: 채팅 @ctx 8192 **CUDA 5.58GiB**(계획서:424~427) · **Metal 4.27GiB**(계획서:460~461), 임베딩 bge-m3 **1.25GiB**(표값 2.5의 절반, 계획서:455).
  ⚠ Metal 값은 출처끼리 갈린다 — 계획서:392~393은 `--parallel 2`를 **안 붙인** 4.27을 「라이트가 쓰는 것」이라 하고, localengine.ts:178~179는 `--parallel 2`를 **붙인** 5.59를 「제품 인자 그대로」라 부른다. CUDA에서는 둘 차이가 0.01GiB로 잡음이었다(계획서:424~427).
- 그런데 **아무도 안 세던 화면 몫 ~0.7GiB**가 있다 — 8GB 카드가 모니터를 물면 5.58+1.25+0.70 = 7.53GiB로 총량의 94%다 (계획서:487~493, 출하_결정서:43~61).
- ▶ **원래 10GB 판정은 옳았는데 이유가 틀렸었다**: 막던 것은 부풀린 임베딩 표값이 아니라 화면 몫이다 (출하_결정서:63~65).
- 코드 티어값은 보수적으로 둔 상태다 — `TIER_COST.lite` cuda 5.9 / metal 5.8(gb10 5.77·max 5.59 실측 + 여유, localengine.ts:184), `EMBED_COST.cuda`는 **아직 2.5**(localengine.ts:191), 여유계수 0.95(localengine.ts:197).
- 라이트 측정은 **gb10에서 하지 않는다**(통합메모리라 RSS·nvidia-smi 둘 다 틀린 자) — 3090(win)이 맡는다 (CLAUDE.md:148). 32GB 기계에서 10GB 구성을 흉내 내 재는 것도 함정이다 — 세 번 재서 세 번 다 무효였다 (계획서:325~338).

**모델** — 지금 권장 챗 모델은 `gijo-main-orchestrator`(7.6B) 유지다.
- Qwen3-8B는 게이트 총점이 같고(30/33) 정리본 값 보존에서 크게 지며(95% vs 50%), 실패할 때 **없는 문서 대장을 지어냈다** (GIJO_AS_라이트_모델후보_실측_2026-08-13.md:21~48).
- EXAONE-3.5는 비상업 라이선스라 제외, 14B는 라이트 등급에서 10.2GB라 물리적으로 안 들어간다 (같은 파일:11~12).
- 「기능이 온전히 가능한 모델은 14B이고 그건 24GB 기계」 — 즉 모델 문제가 아니라 **등급 문제**다 (같은 파일:50~52). 라이트를 24GB에 깔면 **기능 수는 그대로고 답 품질만** 좋아진다(라우팅 29→31) (기능등급_가이드:59~62). ⚠ 그 가이드는 기능 수를 13개로 적지만(가이드:26, :62) **코드는 지금 16개**다(lite-tools.json:17~37) — 가이드가 2026-08-12 값에 멈춰 있다.
- 이 표는 닫힌 결론이 아니라 **대장**이다 — 새 후보가 나오면 「라이선스 먼저 → 공식 저장소 → 출하 구성 그대로 → 게이트 33·정리본·RSS → 실패의 모양」 절차로 재서 줄을 더한다 (모델후보_실측:66~81).

## 5. 코드가 에디션을 가르는 자리 (라이트 작업의 지도)

라이트는 **빼기로 만들고, 빼는 방식은 분기 코드가 아니라 목록(데이터)**이며, 화면은 `lite-*` 새 파일로 둔다 (GIJO_AS_Lite_작업경계_2026-08-12.md:12~17, :63~73). 그때 뚫기로 한 「구멍 넷」(작업경계:77~97)은 지금 전부 코드에 있다(④는 아래 표, ②는 screenguide.ts:1109~1122의 `lite` 인자·`LITE_OVERVIEW`).

| 자리 | 코드 |
|---|---|
| 에디션 판별 | env → 빌드 고정 → userData 저장값 순, 라이트 전용 배포본은 잠긴다 (client/src/main.ts:463~469, :438~450) |
| 진입점 | 라이트는 `dist/lite/index.js`로 서버를 띄운다 (main.ts:155) |
| 포트 | 라이트 7445 · 스탠다드/프로 7446(프로는 별도 빌드가 아니라 런타임 티어라 포트를 가를 실익이 없다) (main.ts:35~53, server/src/lite/env.ts:95) |
| 도구 고르기 | `setToolAllowlist`/`isToolAllowed`, 걸려 있으면 「제한 에디션」 신호 (server/src/engine/agenttools/registry.ts:2149~2171, 카탈로그만 거른다 :2143~2145) |
| 등급 바닥값 | 라이트는 ctx 8192·동시 1개로 시작(화면에서 고른 등급이 이긴다) (env.ts:73~85) |
| 빌드 타깃 | `npm run dist:lite` → `electron-builder.lite.json` (client/package.json:13) |
| 셸 축 분리 | 에디션(lite/standard)과 셸 모드(standard/pro)는 다른 축이고, 라이트는 프로 셸을 못 쓴다 (main.ts:492~493, :513) |

- 작업 분담은 바뀌었다: **라이트 에디션 작업도 `win`이 한다**(2026-08-20 사장님, 2026-08-13 「라이트는 max 전담」을 대체), `max`는 dmg·Metal 실기 검증이 메인 (CLAUDE.md:53~55). 라이트 결함의 뿌리가 공용 파일이면 win이 고친다 (CLAUDE.md:56~57).

## 6. 버전·게시 — 라이트는 독자 번호, Drive 수동, 지금 막혀 있다

- **표준·프로는 한 배포본이라 번호를 나누지 않고**(`client/package.json` 5.83.0 · main.ts:41~45), **라이트는 `electron-builder.lite.json`의 독자 semver**(현재 1.4.0)다 — 2026-08-14 결정, 감시 시험이 두 번호가 다른지 지킨다 (GIJO_AS_버전관리_기준.md:5~11).
- 라이트는 자동 업데이트가 아니라 **Drive 수동 교체**이고, 파일명·안내서가 이 번호를 쓴다 (버전관리_기준.md:11).
- 배포 채널이 에디션별로 갈렸다 — 마이그레이션 `client-releases-edition-2026-08-23`, `edition`별 최신판·파일명 분리 (server/src/engine/clientrelease.ts:50, :95~127). 라이트 사용자가 업데이트를 물었을 때 **프로 설치본이 내려와 라이트 설치를 갈아치웠을 자리**를 막는다(release-lite/에 `Lite Setup 5.17.0`·`5.18.1~3`이 실재해 판 번호가 겹칠 수 있었다) (GIJO_AS_MAC_인계_대기.md:151~153).
- ⛔ **라이트 게시는 막혀 있다** — 빌드는 됐는데(1,616MB) 서버 업로드 한계가 500MB다 (MAC_인계_대기:157~166, clientrelease.ts:212). 세 갈래(스트리밍 업로드 / 짐 덜기 / 채널 밖 USB 전달)가 사장님 판단 대기다.
- ⚠ 버전관리 기준의 **에디션 게시 대장이 낡았다** — 표 값은 표준 5.46.0·Lite 1.1.11(버전관리_기준.md:52~53)인데 코드는 5.83.0·1.4.0이다. 「게시마다 이 표를 같이 고친다」는 규칙(같은 파일:47)이 지켜지지 않았다.

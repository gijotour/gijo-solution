① 왜 이 안인가 · 다른 길을 왜 안 골랐나

채택안 — 화면을 고르면 캔버스(옆 604~804px)가 아니라 별도 창이 뜬다. 본창은 body.chat-home(app.html:66-76)이 영구히 유지되어 대화가 늘 폭 100%다. 이미 배포된 프로 셸의 캔버스-옆 배치(app.html:198 .work.console-side)는 이 시안에서 한 번도 켜지지 않는다 — 새 CSS 상태를 만드는 게 아니라 이미 있는 idle 상태를 상시화하는 쪽이라 구현 위험이 낮다(실측 아님, 코드 구조로 판단).

결재판이 가려지는 문제 — 이전 시안(mockups/프로_대화창메인)이 기각한 바로 그 자리

그 시안은 "캔버스를 풀스크린 모달로 띄운다"를 기각했다: "대화(결재판 포함)가 완전히 뒤로 가려진다." 이 시안도 같은 위험이 있다 — 팝업 창이 여러 개 뜨면 본창(대화)이 다른 창들 뒤에 가려질 수 있다. 세 갈래를 직접 검토했다:

갈래내용판정근거
A. 승인이 오면 팝업이 물러난다결재판 도착 시 팝업 창들을 자동으로 최소화하거나 본창을 강제로 맨 앞으로기각 사람이 읽던 창을 말없이 치우는 것 — "탭이 말없이 닫히는" 사고(app.html:493-504 주석)와 같은 패턴. Windows는 애초에 다른 프로세스가 SetForegroundWindow로 자기 창을 강제로 앞세우는 것을 제한한다(위키백과 "Focus stealing" — 아래 조사 인용). 강제로 되지도 않고, 된다 해도 나쁜 습관이다.
B. 승인 카드를 팝업 위에도 복제해서 띄운다모든 열린 팝업 창에 결재판을 토스트로 복제기각 승인 상태(값 수정·승인·취소)가 원본(대화)과 복제본(팝업 토스트) 두 곳에 있으면 반드시 어긋난다 — 이 저장소가 반복해 겪은 "같은 것을 여러 곳에 적으면 어긋난다"(CLAUDE.md)를 결재판이라는 가장 위험한 자리에서 재현하는 꼴이다.
C. 본창은 스스로를 앞세우지 않고 "봐 달라"고만 알린다Electron BrowserWindow.flashFrame(true)로 작업표시줄 아이콘을 깜빡인다(강제 포커스 아님) + 결재판은 오직 본창 안에서만 존재(원본 하나)채택 Electron 공식 문서: "창이 주의가 필요하지만 지금 포커스가 없다는 것을 알리려 창을 깜빡인다"(아래 조사 인용) — Windows의 포커스 강탈 제한과 정확히 같은 방향이다. 그리고 이 시안 특유의 강점: 대화가 다른 OS 창이라, 자기 자신의 내용(캔버스) 뒤에 가려질 수 없다 — 이전 시안이 겪은 "같은 창 안에서 캔버스가 대화를 밀어낸다"는 유형의 문제 자체가 구조적으로 없다. 남는 위험은 "다른 창들 뒤에 깔린다"뿐이고, 그건 OS의 표준 알림 관례(작업표시줄 깜빡임)로 이미 풀려 있는 문제다.

⚠ flashFrame은 오늘 client/src/main.ts에 없다(grep 결과 0건) — 이 시안이 채택한 해법을 실제로 쓰려면 새로 붙여야 한다(작은 추가, 아래 ③에서 정직하게 밝힘). 데모에서는 본창 테두리 pulse + 토스트로 그 효과를 흉내 냈다 — 실제 작업표시줄 깜빡임은 브라우저 탭 안에서 재현할 수 없기 때문이다.

왜 "화면이 대화를 나눠 갖는" 오늘 배치를 버리나

사장님 지시①이 명확하다 — "나눠서 보이는것보단". 오늘의 캔버스-옆 배치(604~804px + 380px)는 본질적으로 "나눠 보이는" 것이고, 이 시안은 그걸 "따로 뜨는" 것으로 바꾼다. 이미 있는 팝업 통로 넷(사장님 지시②·⑤, main.ts에서 직접 확인)을 그대로 쓰는 것도 여기서 나온다 — 새 창 종류를 만들 필요가 없다.

② 정직하게 조사해 밝힌 기술 난제 — "화면에서 고른 것"이 대화로 안 돌아온다

화면(iframe/탭) 쪽 코드는 전부 자신이 iframe 안에 있다고 가정하고 window.top 또는 window.parent로 셸에 말을 건다. 별도 창(BrowserWindow)에서는 window.top === window 자기 자신이라 이 메시지가 아무 데도 안 닿는다 — 코드가 이미 그 사실을 알고 있다:

  • grouphub.js:103 — window.top.postMessage({type:"gijo:view"},"*") 뒤에 주석 "셸 밖이면 없던 일로"라고 스스로 적어 뒀다.
  • map-view.js:118 — 아예 이름 && window.top !== window로 막고 보낸다 (별도 창일 땐 시도조차 안 한다).
  • scopefilter.js:103, assets.html:140/171/251, dashboard.html:555/591, sessions.html:365, console.js:304 — 전부 같은 패턴(window.top/window.parent postMessage)을 쓴다. 예외가 없다.

Electron 공식 자료로도 재확인했다(아래 조사 인용) — BrowserWindow는 렌더러가 여러 개의 독립된 프로세스라 window.opener도 없고, 창끼리 직접 postMessage를 주고받는 길이 없다. 반드시 메인 프로세스(ipcMain/ipcRenderer)를 거쳐야 한다.

더 정밀하게 보면 난제가 두 겹이다 — 뭉뚱그려 "안 된다"고 하지 않고 실제로 갈라서 확인했다:

겹무엇오늘 상태근거(파일:줄)
얕은 겹 — "지금 어느 화면 얘기중" (맥락 알약) 팝업 창이 포커스를 받으면 그 라벨이 대화 맥락 알약(.cs-ctx)에 뜨는가 도킹 상태에서는 안 됨 — IPC 자체는 이미 있다 (shell:popoutFocus가 실제로 쏜다) main.ts:839 focus 이벤트 발신 → app.html:873-879 onPopoutContext가 받아 setCtx(label) 호출 → 그런데 app.html:564-575 setCtx()는 그 label을 도킹 상태에서는 그냥 버린다(팝업일 때만 쓰는 if(popped …) 분기 안에만 있음) → 대신 window.gijoConsoleSyncCtx()를 불러 console.js:1225-1230 readCtxFromShell()이 window.gijoTabs.activeScreen()(=활성 탭)을 다시 읽는다. 팝업은 탭이 아니므로 무시된다.
깊은 겹 — "이 항목을 골랐다" (📌 칩) 팝업 안에서 목록 행을 클릭하면 대화에 선택 칩이 붙는가 전혀 안 됨 — 중계할 IPC 채널 자체가 없음 위 코드 목록 전부(window.top.postMessage(gijo:select/view/scope)) + preload.ts:142-183·238-242를 전수 확인 — select/view/scope를 나르는 ipcRenderer 채널이 하나도 없다(focus/tab/closed 셋만 있음).

얕은 겹은 작은 수정이다(이미 도착한 IPC를 도킹 상태에서도 반영하도록 readCtxFromShell을 고치면 된다). 깊은 겹은 새 배관이 필요하다 (console:context와 같은 모양으로 select/view/scope용 IPC 채널을 새로 만들고, 10곳 넘는 화면의 window.top.postMessage 호출부를 "별도 창이면 IPC로, iframe이면 postMessage로" 갈래 짓는 헬퍼가 필요하다). 이 시안(정지+실동작 데모)은 둘 다 만들지 않는다 — 데모의 "선택 되먹임" 버튼은 기본적으로 "오늘은 안 됩니다"를 그대로 보여주고, "예상 미리보기" 체크박스를 켰을 때만 구현됐다면 이렇게 보인다를 따로 보여준다 (가짜로 되는 척하지 않는다).

맥락 자체가 사라지는 문제도 있다 — 오늘 부팅(app.html:906-908)은 항상 open("dashboard.html","대시보드")로 탭을 하나 열고 시작한다. 이 시안대로 화면 열기를 전부 팝업으로 돌리면 탭이 원천적으로 안 생기므로, 이 첫 탭도 다시 생각해야 한다 — 대시보드를 뭘로 대신할지는 이 시안의 범위 밖이라 정하지 않는다(아래 ⑦에 남김).

③ 무엇을 포기했나

  • 같은 창 안에서 화면과 대화를 동시에 보기 — 오늘의 캔버스-옆(64.8%+30.6%)이 주는 "한눈에 같이 보인다"는 감각을 포기한다. 대신 실제 창 두 개를 나란히 놓을 수 있다(모니터가 넓으면 오히려 더 크게 볼 수 있다) — 그러나 그건 담당자가 직접 창을 배치해야 하는 수고다.
  • 선택 되먹임(📌 칩)의 즉시 동작 — ②에서 밝혔듯 오늘 코드로는 안 된다. 이 시안 자체는 그 배관을 새로 만들지 않는다(범위 밖으로 명시).
  • 부팅 시 대시보드 자동 오픈 — 탭이 없어지므로 이 관행도 다시 정해야 한다(⑦에 남김).
  • "⧉ 창으로"·"▥ 옆으로"·"모두 닫기" 세 버튼의 존재 이유 — 탭·캔버스 개념이 없어지면 이 셋은 의미를 잃는다(레일 🗔로 흡수 제안, ④ 참고) — 단, 이건 코드 변경 제안이지 오늘 이미 없어진 것은 아니다.
  • 대화창을 별도 창으로 빼는 기능(console:popout)의 필요성 — 이 시안에서는 본창 자체가 이미 "대화 전용 창"이라 그 창을 또 빼낼 이유가 옅어진다. 지우자는 제안은 아니다(다른 셸에서는 여전히 쓰인다) — 프로 셸에서는 버튼을 안 보이는 정도로 충분할 수 있다는 관찰만 남긴다.

#재는 것접는 기준
1동시에 열려 있는 팝업 창 개수(실사용 평균)평균 3개를 넘게 상시 유지되면(작업표시줄이 이미 붐빈다는 뜻) — 캡·자동정리 정책이 별도로 필요, 그래도 안 줄면 "창 대신 다시 패널"로 되돌리는 것 검토
2gijo:select/view/scope 되먹임(②의 "깊은 겹") 배관을 실제로 만들 필요가 체감되는지실사용에서 "화면에서 고른 걸 그대로 지시에 쓰는" 빈도가 낮고 대부분 타이핑으로 재지시하면 — 그 배관은 안 만들어도 된다(만드는 비용 자체를 아낌)
3결재판 도착을 알아채는 데 걸리는 시간(flashFrame 구현 후 실측) 기존 캔버스-옆 방식(즉시 시야 안)보다 평균 인지 지연이 뚜렷이 늘면(예: 10초 초과) — "구조적으로 안 가려진다"는 이 시안의 핵심 주장이 체감으로는 "못 알아챈다"와 다를 게 없다는 뜻 → 접는다
4여러 화면을 나란히 비교하는 빈도(오늘의 탭 8개 관례가 여전히 쓰이는지) 실측 결과 오히려 늘면(진짜 창이라 배치가 자유로워서) 긍정 신호, 반대로 "창 열고 옮기는" 수고 때문에 줄면 — 캔버스-옆 배치를 다시 검토
5표준·라이트 셸과의 이질감(전환 시 학습비용)프로 전환 사용자의 불만이 뚜렷하면 — 이 시안을 프로 전용으로 계속 격리할지, 접을지 재검토
6동시에 열린 팝업들의 메모리 실측(각각 완전한 렌더러 프로세스라 탭(iframe)보다 무겁다)5개 동시 상황에서 관측 메모리가 오늘 탭 8개 상황보다 유의하게 높으면 — 권장 상한을 더 낮추거나 재고

⑦ 구현 시 더 정해야 할 것(이 시안이 답을 안 낸 것 — 정직 표기)

설계 전 조사 — 표준·모범사례

  • Electron 공식 문서, "Inter-Process Communication" — https://www.electronjs.org/docs/latest/tutorial/ipc — 렌더러(창)끼리는 직접 통신 경로가 없고 메인 프로세스를 거쳐야 한다. 적용: ②의 "깊은 겹" 판단(별도 창은 postMessage로 셸에 못 닿는다)을 코드 조사에 더해 공식 문서로 재확인.
  • Electron GitHub 이슈 #7193, "IPC from renderer to renderer" — https://github.com/electron/electron/issues/7193 — renderer-renderer 직접 통신이 지원되지 않고 메인 프로세스를 경유하는 프록시 패턴이 표준 해법으로 논의됨. 적용: 이 시안의 ⑦(select/view/scope IPC를 console:context와 같은 모양으로 새로 만든다)이 바로 이 프록시 패턴이다 — 새 방식을 지어내지 않고 이미 검증된 관례를 따른다.
  • Electron 공식 문서, "Windows Taskbar"(flashFrame) — https://www.electronjs.org/docs/latest/tutorial/windows-taskbar — "창이 주의가 필요하지만 포커스가 없을 때 작업표시줄 버튼을 깜빡인다." 적용: ①의 채택 갈래(C)가 그대로 이 API를 가리킨다 — 강제 포커스가 아니라 "봐 달라"는 요청.
  • 위키백과, "Focus stealing" — https://en.wikipedia.org/wiki/Focus_stealing — 다른 프로세스가 사용자 동의 없이 자기 창을 강제로 앞세우는 것은 널리 알려진 안티패턴이며 현대 OS(Windows 포함)는 이를 제한한다. 적용: ①에서 갈래 A("팝업이 물러난다")를 기각하는 직접 근거.
  • Nielsen Norman Group, "Opening Links in New Browser Windows and Tabs" — https://www.nngroup.com/articles/new-browser-windows-and-tabs/ — 새 창은 사용자를 방향감 상실시키고("새 창이 열린 걸 못 알아챈다"), 인지 부하를 늘리며, 뒤로가기를 못 쓰게 한다. 적용: 이 위험을 그대로 인정하고, 이미 있는 열린 창 목록(🗔, app.html:279-283)을 레일로 승격해 "방향감 상실" 위험을 낮추는 상시 안전망으로 삼았다(사용자가 뭘 열어놨는지 항상 한 곳에서 확인 가능) — 조사가 지적한 문제에 이미 있는 제품 부품으로 정면 대응.
  • Microsoft Learn, "Windows Application Development - Best Practices" — https://learn.microsoft.com/en-us/windows/apps/get-started/best-practices — Windows 11 사용자는 "최신 멀티윈도우 워크플로와 셸 통합 지점"을 기대하며, Snap Layout(1/2·1/3·1/4 화면 배치)이 표준 기대치다. 적용: 여러 화면을 별도 창으로 다루는 것이 Windows에서는 이례적인 패턴이 아니라 플랫폼이 이미 지원을 전제하는 패턴이라는 근거로 삼았다 — 다만 이 조사가 다중 창을 권장한다고 해서 NN/g가 지적한 방향감 상실 위험이 사라지는 것은 아니므로, 위 NN/g 대응(열린 창 목록)은 그대로 유지한다.
  • (계승) Hatchworks, "Agent UX Patterns" — https://hatchworks.com/blog/ai-agents/agent-ux-patterns/ — "체크포인트 게이트"(승인이 로깅되고 무엇이 바뀌는지 보여줌) 패턴은 이전 시안이 이미 확인했고, 이 시안은 결재판이 물리적으로 다른 창에 가려질 수 있다는 새로운 위험에 대해 같은 조사를 다시 적용했다 (①의 표).

사용법(눌러서 확인)

  1. 시연 컨트롤에서 "① 발견·수집"을 눌러 본다 — 팝업 창이 뜨고, 본창(대화)의 폭은 바뀌지 않는다(이게 이 시안의 핵심).
  2. 이어서 "⑤ 보고"·"설정"도 열어 본다 — 팝업이 쌓인다. 레일의 🗔를 눌러 열린 창 목록에서 아무거나 골라 맨 앞으로 가져와 본다("다시 부르면 focus"의 시연).
  3. 팝업들이 본창을 가리도록 겹쳐 본 다음(끌어서 옮기면 됨) "🗂 결재판 도착 시뮬레이션"을 누른다 — 본창 테두리가 pulse하고 토스트가 뜬다(작업표시줄 깜빡임의 대역, ① 갈래 C).
  4. 발견·수집 팝업 안에서 목록 행 옆 "선택" 버튼을 눌러 본다 — 기본 상태에서는 "오늘은 안 됩니다"가 그대로 뜬다. 시연 바의 "선택 되먹임 — 구현됐다면" 체크박스를 켜고 다시 눌러 차이를 확인한다.
  5. "가상 시나리오: 팝업이 막히면"을 켜 본다 — 대화가 사라지고 화면이 본창 안에서 전체를 차지한다("🗨 대화 다시 보기"로 되돌아온다). 이건 사장님 지시③을 위한 가정 데모이고, 오늘 코드로는 이 경로가 실제로 필요한 화면이 없다(②·⑤ 참고).

②왜 이 안인가 · 원형에서 무엇을 버렸나

채택안 — chat-home(tabs.length===0)일 때만 console.js의 .cs-empty 안쪽 내용을 "인사말(시간대별) → 정직 한 줄(유지) → 질문 칩 2~3개 → 구분 라벨 → 메뉴 칩 ⓪~⑤"로 바꾸고, .cs-body를 입력창 바로 위 붙임(오늘 규칙)에서 세로 중앙 정렬로 바꾼다. chat-home이 아니면(표준 셸, 또는 프로에서 화면이 도킹된 뒤) 지금 문구가 한 글자도 안 바뀐 채 그대로 나온다 — 새 문구는 완전히 새 조건(chat-home) 뒤에만 존재한다.

원형(Claude Desktop 홈, 사장님 스크린샷)에서 버린 것 — 가장 중요한 결정:

  • 중앙의 큰 입력창을 새로 만들지 않는다. 원형은 입력창이 화면에 하나뿐이라 그것이 곧 중앙에 있어도 된다. 우리 콘솔은 .cs-dock(진짜 입력창, ＋·전송 포함)이 이미 화면 맨 아래에 상시로 존재한다(app.html:264-267, 표준·프로 공통). 히어로 안에 또 하나의 입력처럼 생긴 상자를 두면 "둘 중 어디에 쳐야 하나"가 생긴다 — 사용자 확립 원칙 "지시는 대화창에서만"(하나의 창구)을 이 화면 안에서 스스로 어기는 셈이다. 대신 히어로를 .cs-body 안에서 세로 중앙에 두면, chat-home에서는 그 아래로 .cs-dock 한 칸만 남으므로 시선이 자연히 그 실제 입력창으로 떨어진다 — 입력창이 하나라는 사실은 그대로 두고 "가운데 있는 것처럼 보이는 효과"만 얻는다.
  • 모델 선택·마이크·모드 토글을 옮기지 않는다 — 근거는 ④.
  • 제안 카드(원형은 그리드형 큰 카드 4장)를 작은 칩으로 낮췄다. 우리 메뉴 칩은 6개(⓪~⑤)라 원형의 4카드보다 많다 — 큰 카드로 그리면 세로 총합이 부풀어(⑦) 세로 모니터(내부폭 1024)에서 칩이 두 번 줄바꿈할 위험이 커진다. 칩(pill)은 이미 console.js 전역에서 쓰는 부품 (.cs-chip 계열)이라 재사용이기도 하다(새 부품 언어를 만들지 않음).

검토하고 기각한 다른 두 길:

  • 대시보드를 chat-home 기본 화면으로 되살린다 — 기각. 프로 셸은 2026-08-18 "화면은 부를 때만 온다"를 이미 승인했다(대시보드 탭 상시 유지는 그 결정의 정반대다). 되돌리는 게 아니라 그 결정 안에서 빈 순간을 채우는 것이 이 시안의 범위다.
  • 히어로를 항상(도킹 중에도) 보여준다 — 기각. ⑤에서 코드로 확인했듯 도킹은 tabs.push를 거쳐 chat-home을 끈다. 화면이 이미 옆에 열려 700px 좁은 콘솔에서 22px 큰 인사말+6칩을 또 띄우면 그 좁은 칸의 태반을 인사말이 먹는다 — "빈 상태에서만"이라는 지시 문구를 글자 그대로 지켰다.

④옮기지 않는 것(원칙)

원형 요소왜 옮기지 않나
모델 선택 드롭다운기반 두뇌는 팀 단위로 고정한다는 것이 이미 선 원칙이다 (project_llm_location_choice·에이전트 모델 배정 — 화면마다 모델을 고르게 하면 "어느 모델이 맞는지"라는 새 의사결정을 사용자에게 떠넘긴다). 프로 셸에 그런 선택지 자체가 없다.
마이크(음성 입력)구현돼 있지 않다. 목업에 그리면 "정직한 구현" 원칙(동작 안 하는 버튼을 동작하는 척 그리지 않는다)을 첫 화면에서부터 어기게 된다.
채팅/Cowork 모드 토글셸 전환(표준↔프로)은 로그인·설정(settings.html) 몫으로 이미 정해져 있다(설정 › 제품 구성). 대화 화면 안에 또 다른 전환 스위치를 두면 "셸을 바꾸는 곳이 두 곳"이 되어 다음에 셸이 안 바뀌는 사고가 나면 어느 스위치를 봐야 할지 모르게 된다 (project_glossary… 류의 "단일 출처" 반복 교훈과 같은 함정).

⑤폭에 따라 히어로가 어떻게 반응하는가 — 코드를 읽다 발견한 비대칭

app.html의 open()(497-523)을 그대로 읽으면, 메뉴 칩을 눌렀을 때 두 폭에서 다른 결과가 난다 — 이 시안이 새로 만든 규칙이 아니라 이미 구현된 규칙을 그대로 따른 결과다. 위 ①의 폭 토글로 직접 재현된다:

내부 폭메뉴 칩을 누르면chat-home(히어로)은?왜
≥1400px(가로 1920)도킹 — tabs.push를 타는 표준 탭 경로로 흘러 들어간다(open():522 "⑥ 도킹 — return하지 않고 아래 표준 탭 생성 경로") 사라진다 tabs.length가 0→1이 되어 chat-home 클래스가 빠진다 — 콘솔은 700px 옆 칸으로 줄고 옛 3줄 문구로 되돌아간다. tabs 배열이 곧 chat-home 판정 기준(대화홈갱신():977)이라, 화면이 실제로 탭에 실리면 자동으로 꺼진다 — 새 판정 로직을 만들 필요가 없었다.
<1400px(세로 1080)팝업 — openShellPopout만 부르고 return한다(514·517행), tabs 배열을 건드리지 않는다 그대로 남는다 tabs.length는 여전히 0이라 chat-home이 꺼지지 않는다 — 별도 창이 하나 더 뜨는 동안에도 히어로는 화면 가운데 그대로다. 팝업은 셸의 tabs 모델 바깥(별도 BrowserWindow)이라 애초에 chat-home 판정에 안 잡힌다.

이 비대칭을 몰랐다면 "히어로가 도킹된 뒤에도 남아 있어야 하나?"를 새로 설계해야 했을 것이다 — 코드를 먼저 읽어서 답이 이미 정해져 있음을 확인했다(추가 분기 0개).

⑥무엇을 포기했나

  • 진짜 실시간 시계 기반 인사말 — 데모에서는 버튼으로 시간대를 강제한다(setHour). 실제 구현은 new Date().getHours()를 그대로 쓰면 되지만, 자정을 넘겨 대화창을 켜 둔 채로 두는 경우까지 갱신되는지(문서 재로드 없이)는 이 시안이 확인하지 못했다 — 실측이 필요하면 후속으로 남긴다.
  • 메뉴 칩에 실시간 배지(긴급 건수 등) — 절차 띠(.cs-flow)가 화면 안에서는 이미 그 숫자를 준다(renderFlow():1215-1253, /api/workflow/stages). chat-home 에는 활성 화면이 없어 그 API가 참조할 "지금 단계"가 없다 — 억지로 전체 합산을 새로 만들지 않고, 숫자 없는 칩으로 남겼다(정직: 잴 수 없는 값은 안 보여준다).
  • 인사말에 계정 외 개인화(어제 한 일 요약 등) — 원형(Gemini류)도 이 정도는 안 한다는 점을 조사에서 확인했고, project_accumulation_is_zero(축적 자산 실질 0건) 메모와도 부딪힌다 — 실제로 쌓인 이력이 없는데 "어제 이어서…"라고 쓰면 지어내는 것이 된다.
  • 질문 칩의 개인화(사용자마다 다른 질문) — CAN[0]의 고정 3개를 그대로 썼다. 서랍의 "내가 등록한 지시"(사용자별 즐겨찾기)를 칩으로도 노출하는 안을 검토했지만, 히어로가 매번 다른 문구로 보이면 밀도 계산(⑦)이 사람마다 달라져 이 시안의 숫자가 재현 불가능해진다 — 안정된 숫자를 위해 고정했다(개인화는 후속 검토 여지로 남긴다).

function fillGreeting() {
  var el = document.getElementById("ceGreet");
  if (!el) return;
  var h = new Date().getHours();
  var word = h < 5 ? "늦은 시간까지 고생 많으세요"
    : h < 12 ? "좋은 아침입니다"
    : h < 18 ? "안녕하세요"
    : "늦은 시간까지 고생 많으세요";
  el.textContent = word;                          // 이름 오기 전 우선 표시(빈 화면 대신)
  if (!window.gijo || !window.gijo.me) return;
  window.gijo.me().then(function (u) {
    var name = (u && (u.displayName || u.username)) || "";
    if (name) el.textContent = word + ", " + name + "님";
  }).catch(function () { /* 이름을 못 읽어도 인사말은 남는다 — dashboard.html:340과 같은 방어 */ });
}

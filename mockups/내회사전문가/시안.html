시안 — 우리 회사 전문가 만들기 (learnloop.html 재구성)

이미 있는 기능(수집→정제→학습→굽기→등록, learnloop.ts 896줄)을 담당자가 실제로 보고 쓸 수 있게 화면을 다시 짠 시안입니다. 서버에 새 엔진을 만들지 않습니다 — 화면과, 채택 근거를 남기는 자리 하나만 새로 필요합니다(§7).

1설계 전 조사(표준·모범사례)

① 위험한 동작 전 확인창 — "결과를 명확히 보여줘라"
Nielsen Norman Group: "Be specific — inform users about the consequence of their action... describe the requested action and its consequences using clear, concise language." 되돌릴 수 없거나 영향이 큰 동작에는 "friction"(멈춰 생각하게 하는 장치)을 추가하라고 권한다. nngroup.com/articles/confirmation-dialog → 이 시안: 결과(누가 멈추는지·얼마나 걸리는지)를 누르기 전에 단추 옆에 상시 표시하고, 누른 뒤에도 확인창을 한 번 더 둔다(이중 장치 — 기존 확인창은 유지, 위치만 보강).

② 채택 판단에는 구조화된 근거가 있어야 한다 — Model Cards
Mitchell et al., "Model Cards for Model Reporting"(2019): 모델을 실서비스에 들이기 전 평가 결과· 한계·의도된 사용처를 구조화된 문서로 남겨야 검토자가 승인/반려를 판단할 수 있다는 것이 표준 관행이다. arxiv.org/abs/1810.03993 → 이 시안: 이 제품은 이미 전체 모델 교체 채택에는 이 구조(축별 통과율·견고성 점수를 JSON으로 원장에 남김, server/src/engine/modeladoption.ts)를 갖고 있다. 그런데 전문가(LoRA 어댑터) 채택에는 이 구조가 없다(§4에서 실측 확인) — 있는 패턴을 없는 곳에 맞춘다, 새로 발명하지 않는다.

③ 쉬운 말로 — plainlanguage.gov
"Don't use jargon or technical terms when everyday words have the same meaning... when you have no way to express an idea except technical language, define your terms." digital.gov/guides/plain-language/principles/avoid-jargon → 이 시안: 화면 주 라벨은 쉬운 말, 정확성이 필요한 기술값(모델 repo id 등)은 작게 병기하되 뜻풀이 문장은 화면에 안 쓴다(제품 원칙: 설명은 챗봇으로, §8).

2정찰 — 오늘 코드에서 직접 확인한 사실만

지시문이 "이미 있다"고 한 것들을 전부 직접 읽고 줄 번호로 확인했습니다. 지어낸 것 없음.

  • 수집→정제→학습→굽기→등록 전 과정이 실제로 돈다 — server/src/engine/learnloop.ts:565-631 runPipeline. 실패해도 finally에서 엔진을 재기동한다(621-627행).
  • 전원이 멈춘다 — 839-842행 주석 그대로: "이 라우트는 추론 풀·임베딩 서버를 내린다 — 즉 담당자 한 사람이 누르면 그 순간 접속한 전원의 채팅·문서검색이 학습이 끝날 때까지 멈춘다." 화면(learnloop.html:550-556)에도 이미 같은 취지 주석이 있고, 실행 버튼을 누르면 확인창 (674-698행 gijoAsk)에 "진행 중에는 채팅·문서검색이 일시 중지됩니다"가 뜬다 — 단, 확인창은 누른 뒤에만 보인다. 단추 옆 상시 표시는 없다(오늘 화면 실측, 요구사항①의 진짜 빈 자리).
  • 몇 건 남았나 — GET /api/learnloop/topics(learnloop.ts:784-796)가 주제마다 {total, approved, 준비됨, 남은건수}와 TOPIC_TRAIN_TARGET=300(334행)을 이미 준다. 화면에도 이미 있다 — learnloop.html:235-236,364-390 lt-strip이 주제별 진척 칩(승인/목표, 진행바)을 그린다. 다만 위치가 "학습 후보함" 섹션 안 작은 띠(28px)라 화면 중간까지 스크롤해야 보인다 — 이게 이 기능의 연료 게이지인데 첫 화면에 없다.
  • 채택 근거가 없다 — server/src/engine/adapters.ts: note는 자유 텍스트이고(36행 주석 "채택/불채택 판정 근거"), setAdapterAdopted(182-188행)는 "채택엔 note가 비어 있으면 안 된다"만 검사한다 — 내용을 검증하지 않는다. 채택 창구는 대화창 명령뿐이다(agenttools/handlers.ts:3131-3159 runAdapterAdopt, 3140행 안내 문구가 근거 예시를 "게이트 routing 66/66·A/B 통과"처럼 자유 텍스트로 적으라고만 한다). settings.html:442-446, 1617-1646도 등록부를 보여줄 뿐 채택 UI가 없다("조작은 대화창에서"). 반면 같은 제품 안에 이미 구조화된 선례가 있다 — 전체 모델 교체 채택은 server/src/engine/modeladoption.ts(gate 컬럼에 축별 통과율· 견고성 점수 JSON 저장, tools/evalgate/adopt.mjs:93-105가 실제로 게이트 리포트를 그대로 실어 원장에 남긴다). LoRA 어댑터 쪽만 이 구조가 없다.
  • 두 평가 도구는 실재하되 둘 다 CLI다 — tools/evalgate/run.mjs 는 JSON 리포트(verdict·axes[routing/safety/korean/negative].passRate·robustness.score)를 파일로 남기고, server/scripts/lora-ab.mjs:1-6,89-97는 "판정은 자동 점수가 아니라 사람이 읽는다"고 스스로 적고 있고 실제로 markdown 답변 비교본만 파일로 남긴다(자동 통과 기준 없음). 둘 다 API가 아니라 사람이 터미널에서 돌리고 사람이 읽는 도구 — 그래서 이 시안도 "자동 평가"를 그리지 않는다(§4·§7에 명시).
  • 화면 말이 기술 용어다 — learnloop.html: STAGES 라벨 "학습(QLoRA)"·"GGUF 변환"(279-281행), cfg-panel "베이스 모델 (HF repo)"·"배포 접두어"(221-222행), cat-intro "GGUF id가 아닙니다"(218행). 2026-09-01 여정 점검 F5-09가 이미 결함으로 잡은 그대로 남아 있었다.
  • 발견한 결함(요청 밖, 정직하게 적어 둠) — STAGES의 4번째 단계 라벨이 "에이전트 배포" (learnloop.html:281)인데, 실제 코드(learnloop.ts:599-616)는 그 단계에서 "미채택"으로 어댑터를 등록만 하고 배포하지 않는다("자동 부착 금지" 599행 주석). 라벨이 실제 동작과 어긋난다 — 이 시안은 정확한 말로 고쳐 쓴다(§5 용어표).

3핵심 결정 3가지 — 무엇을 노렸고 왜

  1. 연료 게이지를 첫 화면 맨 위로 올린다. 기존 lt-strip을 그대로 쓰되 "학습 후보함" 안 28px 띠에서 꺼내 화면 최상단 큰 카드 4장으로 만든다. 왜: 요구사항②가 "담당자가 자기 👍가 무엇을 만드는지 알아야 계속 누른다"고 못박았고, 실측(진단 200건 중 👍 1건)이 "숨어 있으면 안 쓴다"를 이미 증명했다(learnloop.html:230행 주석) — 같은 실패를 되풀이하지 않으려면 숨기지 않는다. 버린 대안: 작은 띠를 그대로 두고 색만 진하게 — 기각. 색은 위치를 못 이긴다(스크롤 밖은 안 보인 것과 같다).
  2. 시작 결과는 단추 옆 상시 문장으로, 확인창은 그대로 이중 장치로 둔다. 왜: NN/G "결과를 명확히"는 확인창 텍스트가 이미 하고 있었다(learnloop.html:579) — 부족한 건 "누르기 전에도 보이는가"였다. 확인창을 없애지 않고 앞에 한 겹을 더 두는 이유는 "안 지운다"는 이 저장소의 원칙(사전점검 카드 3장을 화면에서 안내로 옮길 때도 "그림 자체는 지우지 않는다" — learnloop.html:182-185 선례)과 같다. 버린 대안: 확인창 문구만 강화 — 기각. 요구사항 원문이 "누르고 나서 아는 일이 없어야 한다"고 명시했다.
  3. 채택에는 구조화된 근거 입력을 요구한다 — 자동화하지 않는다. 기존 자유 텍스트 note를 없애지 않고(하위 호환), 그 위에 "게이트 리포트 원문 첨부"와 "사람이 읽은 A/B 판정"을 구조로 요구하는 채택 절차를 새로 둔다. 자동 채택 버튼은 만들지 않는다 — evalgate·lora-ab는 실제로 사람이 돌리고 사람이 읽는 도구이지 API가 아니다(§2). 버린 대안: "게이트를 API로 만들어 버튼 하나로 돌린다" — 기각, 지시문이 명시적으로 금지("없는 자동 평가를 그리지 마라")했고 실제로 게이트는 10~20분·A/B는 GPU 독점 실행이라 버튼 한 번의 일이 아니다(운영 서버까지 흔드는 일 — 그런 것은 어차피 CLI로 사람이 지켜보며 돌리는 게 맞다, tools/evalgate/adopt.mjs:15-16 스스로 그렇게 경고한다).

4무엇을 포기했는가

✕ 안 그린 것

  • 자동 게이트 실행 버튼 — CLI 도구를 API로 감싸는 서버 작업 없이는 거짓 UI다.
  • 팀원 배정 UI(스캔 팀원에 어댑터 붙이기) — 지금도 대화창 명령뿐이고(settings.html:525 라벨만 있음) 이번 네 가지 요구사항 밖이라 손대지 않았다. 필요해지면 별도 시안.
  • 주제 4종을 늘리거나 바꾸는 것 — TOPICS 상수(learnloop.ts:328)는 코드 규칙 기반 분류와 짝이라 화면만으로 못 바꾼다. 그대로 둔다.
  • 실행 이력·루프 설정을 화면에서 지우는 것 — 접어서(fold) 남긴다. 안 쓰는 사람이 대부분이라 접었을 뿐, 관리자가 필요할 때는 그대로 있다.

✓ 지킨 것

  • 기존 권한 잠금 그대로 — 학습 시작·설정 변경은 관리자만(F5-07), 후보 승인(👍)은 담당자도.
  • 기존 API 그대로 — /api/learnloop/* 어느 것도 요청·응답 모양을 안 바꿨다. 새 화면은 지금 있는 API만으로 90% 그려진다(§7 표 참고).
  • "실패해도 채팅은 자동 복구" 안심 문구 — 이미 있는 사실(learnloop.ts:621-627)을 화면에 정직하게 옮겼을 뿐, 새로 지어내지 않았다.

9챗봇 안내(screenguide)에 쓸 문장 — 화면에서 뺀 설명

아래는 server/src/engine/screenguide.ts "learnloop.html" 항목에 패널로 추가할 것을 제안하는 문장이다(이 세션은 서버 파일을 고치지 않았다 — 텍스트만 제안).

"어댑터가 뭐예요?":
"우리 회사 대화에서 배운 것을 담은 작은 파일입니다. 공통 두뇌(기본 모델)는 그대로 두고
그 위에 얹는 방식이라(베이스 1개 + 전문가 여러 개), 전문가마다 새로 큰 모델을 통째로
만들 필요가 없습니다. 화면에서는 '전문가'라고 부릅니다."

"QLoRA가 뭔가요 / GGUF가 뭔가요":
"QLoRA는 적은 자원으로 전문가를 학습시키는 방식 이름이고, GGUF는 이 제품(llama.cpp)이
읽는 모델 파일 형식입니다. 둘 다 담당자가 직접 다룰 일은 없고, 화면에는 '전문가 학습
중' · '전문가 파일로 저장'으로만 보입니다."

"학습 시작하면 왜 채팅이 멈춰요?":
"이 서버는 GPU 1대(RTX 3090)를 학습과 채팅이 같이 씁니다. 학습이 도는 동안은 GPU를
비워야 해서 그 시간만 채팅·문서검색이 멈추고, 끝나면 자동으로 다시 켜집니다. 학습이
실패해도 채팅은 항상 자동으로 복구됩니다."

"채택은 무슨 뜻인가요?":
"학습으로 만든 전문가는 만들어지자마자 바로 쓰이지 않습니다('미채택' 상태). 담당자가
평가 결과를 보고 '채택'을 눌러야 실제 채팅에 반영되고, 그것도 지금 켜진 채팅에는 바로
안 실리고 다음에 채팅 모델을 다시 켤 때부터 적용됩니다. 검증 안 된 전문가가 실서비스에
바로 실리는 것을 막는 장치입니다."

하드닝 등록 모달에서 인증 방식 칸 안에 숨어 있던 「로컬(서버 자신)」을 모달 맨 위 「대상 종류」 칩 두 개(🖥 원격 장비 / 🏠 이 서버 자신)로 끌어올린다. 고르면 필요 없는 칸(호스트·포트·인증방식·계정)이 통째로 사라지고, 자기점검을 끈 설치본에서는 그 칩 자체가 미리 잠기고 이유가 보인다 — 등록 버튼을 눌러서야 409를 받는 지금과 다르다.

결과 — 세 가지가 동시에 어긋난다. ① 「이 서버 자신」은 개념상 대상 종류인데 인증 방식 목록에 있다. ② 골라도 화면이 그 사실을 반쪽만 반영한다(계정 줄만 숨고 호스트 줄은 남는다). ③ 자기점검이 꺼진 설치본에서는 안내가 사후(등록 눌러야 409)다 — 같은 화면의 다른 곳(관리자 권한)엔 이미 있는 "미리 막는" 원칙이 여기만 없다.

고른 안 vs 기각한 안

안왜 안 골랐나 / 골랐나
대안 1 — 인증 방식 칸에 그대로 두고 안내 문구만 추가 자리는 그대로다. "대상 종류가 인증 방식 안에 있다"는 근본 문제가 안 풀린다 — 다음 사람이 또 "왜 대상이 인증 방식 목록에 있지"라고 물을 자리다.
대안 2 — 등록 없이 즉석 "이 서버 점검" 버튼(카드 자동 생성) 서버가 스케줄·이력·카드를 전부 등록된 target row 기준으로 관리한다 (hardening_targets 테이블). 등록을 건너뛰면 스케줄·이력 파이프라인이 이원화된다 — 새 API·새 데이터 경로가 필요해 이번 항목의 범위(모달 필드 재배치)를 넘는다.
대안 3 — 인증 방식 칸 옆에 체크박스 "이 서버 자신입니다" 추가 위치가 여전히 인증 방식 칸에 붙어 있어 부수적인 옵션처럼 보인다. 위계(대상이 먼저, 인증은 그다음)가 안 드러난다.
대안 4 — 검증 허브에 "자기 점검" 별도 화면/탭 신설 진입로가 이미 3개(등록 모달 · terminal.html 빠른 점검 · lite-scan.html)다. 4번째를 만들면 "같은 것을 여러 곳에 적으면 어긋난다" 계열이 하나 더 생긴다 — 기각.
채택 — 모달 맨 위에 "대상 종류" 칩 두 개 등록·스케줄·이력 파이프라인은 그대로(target row 하나가 늘 뿐). 새 컴포넌트 없이 gijo-ui.css의 .g-chip(이미 approvals.html 등에서 쓰는 부품)을 재사용한다. 관리자 권한과 같은 "미리 안다" 원칙을 자기점검 여부에도 적용한다.

② 무엇을 포기했나

안 한 것왜

「대상 종류」를 3가지 이상으로(예: Windows PC 자신 등) 서버 판정(원격점검인가(), hardeningscan.ts:603)이 이미 둘로만 가른다 (local vs 그 외). 화면이 셋 이상을 보여주면 서버가 못 받는 값을 보여주는 셈이 된다.

입력칸 0(새 화면에 지시 창구를 만들지 않는다)해당 없음 이 원칙은 새 화면 신설을 막는 것이다. 대상 등록 모달은 이미 있는 설정성 입력 폼이고 (gijo-ui.css:288-294 "설정은 화면 성격이 통째로 폼이라 예외"와 같은 계열), 이번 변경은 입력 칸 개수를 늘리지 않는다 — 오히려 로컬 선택 시 4칸 → 0칸으로 준다.

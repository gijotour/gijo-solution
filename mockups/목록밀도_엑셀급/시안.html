「엑셀급 촘촘 목록」 전역 규격

시각화(그림띠·카드·KPI)는 그대로 둔다 — 목록 행만 조인다. 대상: 표 8화면 + div행 8종(7클래스) · mockups/목록밀도_엑셀급/시안.html
핵심 결정 3줄
  1. 행높이 — 표는 패딩만 5px→3px(폰트·줄간격 그대로)로 배지 있는 행 ≈27px·순수 텍스트 행 24px. div행(카드형)은 패딩 10~11px→6px + 줄간격 1.7→1.45로 44~69px → 29~53px(2줄 유지 항목은 49~53px 하한).
  2. 홀짝·고정 헤더·.num을 gijo-ui.css 한 곳에 신설/승격한다 — 화면별 CSS 복제 없음. 단 .frow는 loganalysis(목록)와 approvals·hardening(폼 줄)이 이름이 겹쳐 loganalysis만 data-screen으로 좁혀야 한다.
  3. 토글 없이 무조건 적용을 추천한다 — 이 밀도(24~27px)는 업계 "진짜 촘촘"(28~32px) 기준보다도 낮은데, 그건 임의 선택이 아니라 배지 높이(≈20px)·폰트 하한(11px)이 만드는 바닥이라 화면마다 켜고 끌 여지가 별로 없다.

ⓐ vulnscan 호스트 표 — 현재 vs 규격 (같은 데이터 15행, 실제 렌더)

과제 지시의 「현재 ≈45px」와 다른 점을 먼저 밝힌다. 소스를 직접 읽어 보니 표는 이미 2026-08-02 nav.js 목록양식CSS()가 .main table td{padding:5px 10px;line-height:1.35}를 적용해 둔 상태다(vulnscan.html 자체 CSS td{padding:13px 10px}보다 특이도가 높아 이긴다). 이 값으로 계산하면 배지(취약점 심각도 뱃지, 실측 ≈20px)가 바닥을 잡아 ≈31px — 실측 견적서 범위의 최솟값(31.3px)과 거의 정확히 일치한다. 45px는 2026-08-02 이전(주석에 남은 옛 값 "34~48px")에 더 가깝다. 아래 「현재」 패널은 지금 실제로 적용 중인 규칙으로 그렸다 — CDP 재접속이 금지된 시안 에이전트라 실화면 재측정은 못 했으니, 구현 착수 전 getBoundingClientRect로 한 번 더 확인해 달라.

line-height 1.45 조정의 부작용 검토(요구사항 ⑤)

1.7은 2026-08-01 "가독성" 조치였다(gijo-ui.css 320행 주석: 그 전엔 31개 화면 중 30개가 브라우저 기본값(약 1.2)으로 촘촘해 눈이 피로했다). 그런데 같은 조치 안에서 이미 배지·칩· 버튼·표 th/td·input/select는 1.45로 "되돌려" 뒀다(같은 파일 324~326행 — "촘촘해야 하는 것은 되돌린다"). 즉 1.45는 이번에 새로 발명한 값이 아니라 같은 결정이 이미 UI 컨트롤류에 승인해 둔 바닥값이다. div행(카드행)을 여기에 포함하는 건 새 예외가 아니라 기존 예외 목록을 정합하게 넓히는 것 — "표 안 글자는 1.45가 괜찮은데 표 밖 카드행 글자만 1.7을 유지할 이유"가 없었다.

남는 위험은 하나: 2026-08-01 조치가 잡은 대비 문제(흐린 글자 #a49d95 = 3.5:1, 읽기 기준 4.5 미달)는 색 대비였지 줄간격이 아니었다 — 그건 이미 화면별 :root 색상으로 고쳐져 있어(같은 파일 317행) 이번 line-height 조정과 무관하다. 다만 approvals·analysis·sessions의 부제 줄 (.rv-rs/.rr-sub/.sr-sub, 흐린 색 var(--muted))은 1.45에서도 여전히 눈이 가늘게 뜨는 텍스트라 — 실제 화면에서 "너무 빡빡하다"는 반응이 나오면 이 세 클래스만 1.5~1.55로 살짝 올리는 것을 예외로 열어 둔다(다른 5개 클래스는 그럴 이유가 약하다 — 부제가 없거나 이미 1줄이다).

왜 이 안인가 — 다른 길을 왜 안 골랐나

① 폰트 축소 대신 패딩·줄간격만

uireadability 시험이 11px 미만을 실패로 잡는데(견적서 §제약) --g-t-xs=11px가 이미 그 문턱이다. 폰트를 더 줄이면 시험이 막거나, 통과해도 실제로 안 읽힌다. 남은 손잡이는 패딩·줄간격뿐이라 그것만 썼다.

② 화면별 CSS 복제 대신 gijo-ui.css 한 곳

nav.js가 이미 표 8종에 자체 규칙을 갖고 있는데(2026-08-02) 화면마다 또 손대면 반년 뒤 다시 흩어진다(gijo-ui.css 자체 주석의 반복된 경고). 표는 .g-ui.g-ui table td/th (특이도를 확실히 올려 nav.js 규칙을 이긴다), div행은 클래스 나열 — 두 벌이 끝이다.

③ 토글(body.g-dense) 대신 무조건 적용

사장님 지향이 "엑셀처럼"이 기본이고, 이번 목표(24~27px)는 업계 "컴팩트"(40~44px)는 물론 "진짜 촘촘"(28~32px)보다도 낮다 — 콘텐츠(배지 20px·폰트 11px)가 정한 바닥이라 화면마다 켜고 끌 실익이 적다. 토글을 두면 "이 화면은 켤까"를 또 결정해야 하는 새 분기점만 생긴다.

④ 표 zebra는 tr에, 카드행 zebra는 :not()으로

표는 hover/선택이 td 배경을 따로 칠해 tr 배경(zebra)과 자연히 안 겹친다. 카드행은 hover· .on/.sel이 같은 요소의 배경이라 특이도 싸움이 난다 — :nth-child(even):not(:hover):not(.on) 으로 그 상태에서만 얼룩말을 아예 안 먹이는 쪽이 특이도 셈보다 안전하다.

무엇을 포기했나

  • hardening(카드그리드)·products(CRUD 카드) — 표 개념이 아니다. 억지로 행 규칙을 씌우면 카드 레이아웃이 깨진다. 견적서 원안 그대로 제외.
  • .pk-row(assets) 추가 조임 — 이미 34px로 규격 근접. 더 조이면 이 화면만 특별 취급하는 예외가 생겨 "화면별 복제 금지" 원칙과 부딪힌다.
  • 2줄 카드행을 1줄로 합치는 안 — approvals·analysis·sessions 모두 제목+부제가 서로 다른 정보다(예: finding 종류 vs 자산·근거). 합치면 26px는 나오지만 정보가 준다 — 지시("2줄 유지하며 몇 px 가능한지")를 따라 기각.
  • 표 컴포넌트(.g-table) 재활용 — 실제 화면 어디도 안 쓴다(소비 0곳, 견적서 확인). 있지도 않은 걸 고치느니 실제로 쓰이는 bare <table>/nav.js 규칙을 겨눴다.

구현 참고 — gijo-ui.css에 그대로 넣을 규칙

함정: .frow 이름 충돌. loganalysis.html의 .frow(파일 대장 목록 행)와 approvals.html·hardening.html의 .frow(폼 필드 줄, flex/grid 레이아웃)는 같은 이름 다른 뜻이다. 전역으로 .frow{padding:…}를 걸면 폼 줄에 없던 패딩이 번진다. loganalysis만 body[data-screen="loganalysis"]로 좁혀야 하고, 그러려면 loganalysis.html <body>에 data-screen="loganalysis" 표식을 먼저 붙여야 한다(지금은 없음 — settings.html에 이미 있는 선례와 같은 패턴).
함정: 특이도 동률. nav.js의 기존 .main table td{padding:5px 10px}는 특이도 (0,1,2)다. gijo-ui.css에 .g-ui table td{…}(0,1,2)로만 넣으면 동률이 되어 나중에 로드되는 쪽이 이기는데, 로드 순서가 항상 gijo-ui.css 나중이라는 보장이 없다(적용 지점이 두 곳: 독립 실행 injectCss()/임베드 applyEmbed()). 그래서 아래 규칙은 .g-ui.g-ui로 두 번 적어 특이도를 확실히 올린다 — gijo-ui.css 자신도 .kpi-strip.kpi-strip.kpi-strip (192행)·.app.app(167행 주석)에서 이미 쓰는 같은 수법이다.

uireadability(11px 폰트 하한 시험)와의 무충돌 확인

이번 규칙은 font-size를 단 한 곳도 바꾸지 않는다(패딩·line-height·배경·position만). uireadability는 견적서 §제약에 따르면 font-size만 검사하므로 이 시안은 그 시험과 근본적으로 겹치는 속성이 없다 — 통과/실패 여부에 영향을 줄 수 없다. 유일하게 남는 변수는 sticky 헤더(position:sticky)가 레이아웃 시험(있다면)과 부딪히는지인데, 그런 시험은 이 저장소에서 못 찾았다 — 구현 시 한 번 확인 권장.

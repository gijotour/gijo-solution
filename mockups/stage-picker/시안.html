무대 「고르기 모드」 — 자산·우선순위 「선택」 작업의 허브 다이어트

프로 셸 무대(stage-on)에 자산·우선순위 허브를 그대로 띄우면, 「하나 고르기」라는 짧은 용무에 KPI·필터·탭이 딸린 업무 화면 전체가 따라온다. 이 시안은 고르기 전용의 얇은 공용 화면 (검색 1줄 + 목록 + 얇은 상세)을 만들고, 고르는 순간 대화로 자동 복귀시키는 안 1개를 제안한다. 기존 「자산 고르기」「우선순위」 허브는 그대로 둔다 — 분석·필터가 필요한 업무는 거기서 하고, 이 화면은 "대화에 값 하나를 넘기는" 짧은 용무 전용이다.

2026-08-20 사장님 프로 QA 실측 — 원문 요지
① (자산 카드 「자산 열기」) "자산 열기를 별도 창에 띄워야 하나, 거기서 클릭된 게 대화창에 나오긴 하는데, 흠. 고민해줘."
② (우선순위 허브) "저렇게 별도 창에서 선택하는 게 맞는지 고민이야."
결론 3줄
  1. 별도 OS 창은 이미 이 저장소가 같은 날 걷어낸 패턴이다(app.html:1233-1236 — "팝업 및 옆에 붙는 메뉴를 없애는" 사장님 지시로 무대 머리의 ⧉ 창으로 버튼을 삭제) — 되살리지 않는다.
  2. 지금 무대는 「고르기」에도 허브 전체가 뜬다 — 우선순위는 첫 행을 보기까지 458px의 KPI·탭·표머리를 지나야 한다(아래 §3 실측). 고르기 모드는 이걸 110px로 줄인다.
  3. 고르는 순간 대화로 자동 복귀한다 — 단, 2026-08-20 검토관 상1이 이미 한 번 막은 "자동 무대 내림"과 같은 사고를 피하려고 기존 gijo:select 채널(18개 발신처, 그중 확인창 등 10곳)은 손대지 않고, 고르기 화면만 쓰는 새 신호 하나로 좁힌다(§6).

7왜 이 안인가 — 대안 비교

안문제판정
① 허브 그대로 띄우기(오늘) §2·§3에서 실측한 458px chrome·클릭 2회. KPI·탭·필터는 "고르기"에 무관한 정보라 오히려 원하는 항목을 찾는 시간을 늘린다(NN/g Progressive Disclosure 위반 — §1). 기각
② 별도 OS 창(팝업) 같은 날(2026-08-20) 사장님 지시로 무대의 ⧉ 창으로 버튼이 이미 삭제됐다(app.html:1233-1236, "팝업 및 옆에 붙는 메뉴를 없애는"). 창 관리 부담이 추가되고, "거기서 클릭된 게 대화창에 나오긴 하는데" — 별도 창에서 고른 결과가 대화로 오는 우회 경로 자체가 배경 피드백 ①의 불편함이다. 기각(이미 걷어낸 패턴)
③ 고르기 모드(이 시안) 기존 무대·탭 모델·iframe embed·선택카드 규격을 한 글자도 안 바꾸고 그 위에 얇은 화면 1개를 얹는다. Microsoft List/details 패턴이 상정하는 정확한 쓰임("빠르게 오가며 맥락으로 복귀")과 일치한다. 추천

8무엇을 포기했는가

  • 한눈에 훑어보기(KPI) — 고르기 화면엔 없다. 현황을 보려면 여전히 「우선순위」 허브를 연다(대체가 아니라 병행이므로, 화면이 하나 더 생기는 비용을 감수).
  • 한 화면이 두 역할(분석+선택)을 다 하는 단순함 — 지금은 triage/assets가 "보다가 고르는" 한 화면이었다. 이 시안은 그걸 "보는 화면"과 "고르는 화면" 둘로 가른다 — 진입점을 잘못 고르면(예: 카드 버튼 문구) 사용자가 헷갈릴 여지가 새로 생긴다(§9에서 구현 시 재검토 필요로 표기).
  • 목록 안 풍부한 정보 — vulnscan 표의 EPSS·VPR·상태 칩 등은 행에서 뺐다(Progressive Disclosure). 필요하면 상세 패널이나 원래 화면에서 본다.
  • 검색칸의 편리한 확장 — "이 안에서 바로 지시까지 치면 편하지 않을까"는 명시적으로 포기한다. 「메뉴는 보기용, 지시는 대화창에서만」 원칙을 지키려고 검색칸은 필터 전용으로 못 박는다(Enter를 눌러도 지시가 나가지 않음).

10구현 메모(승인 후 참고 — 이 시안이 정하지 않는 것)

이 문서는 그림이다. 아래는 승인 시 구현자가 참고할 자리일 뿐, 이 시안이 코드를 정하지 않는다.

  • 새 화면(가칭 pick.html?kind=vuln|asset)을 열 때 「카드는 dock 5곳」 계약 (wiringcontract.test) 표에 새 진입 경로가 등록돼야 한다 — 안 하면 screenCard 이중 열림 부류의 사고가 재현될 수 있다(MEMORY: 프로 확정 계약 5.41.0).
  • 대화창의 "🗔 자산 열기"/"🗔 취약점 열기" 카드 버튼이 pick=1 트리거를 쓸지, 별도 문구("🎯 고르기")로 분기할지는 진입점 UX를 별도로 확인해야 한다(§8의 "역할 두 갈래" 비용과 직결).
  • API는 새로 만들지 않는다 — 자산은 window.gijo.assetHub()(assets.html:288 그대로), 취약점은 listAssets()를 평탄화(현재 vulnscan/triage가 이미 쓰는 자료 재사용).
정직한 구현 고지 — 각 절의 실측 산식 표(§2·§3·§4)는 client/src/renderer/pages의 실제 CSS 수치 (패딩·마진·폰트 크기·border 두께)를 그대로 계산·합산한 값이다. 바로 위 구성 재현 그림은 같은 값을 문서 폭에 맞춰 압축해 그린 것이라 그림 자체의 픽셀은 자로 잰 근거가 아니다 — 근거는 항상 표다. 클릭 가능해 보이는 요소는 전부 정지 그림이다. 제품 코드는 이 작업에서 읽기만 했고 한 줄도 고치지 않았다. 900px 기준 창 높이 가정 등 계산 전제는 각 표에 명시했다 — 실제 화면 배율·해상도에 따라 절대값은 달라질 수 있으나, 오늘 대비 줄어드는 방향과 비율은 같은 CSS 규칙을 쓰는 한 유지된다.

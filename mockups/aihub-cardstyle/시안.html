§5. 왜 이 안 — 기각한 대안

대안기각 이유
A. dc-card(chatparts.js)를 화면에 그대로 이식(JS 재사용) dc-card는 "말풍선 안에 붙는 답변 부속품" 계약 위에 있다(붙일자리()가 .cs-row 전제). 독립 페이지 최상위 레이아웃에 그대로 꽂으면 안 쓰는 채팅 계약을 억지로 끌고 온다 — 그래서 시각 언어(CSS)만 옮기고 JS는 새로 짰다.
B. 전 화면(176곳) CSS 일괄 스윕 자동화 이 저장소의 전수 스윕 사고 계보(테마 감시가 denylist라 새 hex를 못 잡음·"하루에 8화면에서 같은 병") — 검증 없이 한 번에 176곳을 바꾸면 게시 후에야 깨진 자리를 발견한다. 이번엔 지식 창고 1개 화면만 먼저 하고, 승인·실사용 확인 후 §9에서 확산 순서를 제안한다.
C. 요약 카드 4장만 고치고 폼은 그대로 둔다 사장님이 지적한 "폼 덩어리"가 스샷의 절반이다. 카드만 고치면 위(카드)·아래(옛 폼)의 톤이 갈라져 더 어색해진다 — 그래서 배너·수집·보강 2·문서 목록까지 화면 전체를 통일했다.
D. 카드마다 「🗔 열기」 버튼 추가(2번째 이미지 그대로) 지식 창고의 요약 카드는 이미 카드 전체가 클릭 가능한 판 전환 스위치다(grouphub.js:132-135, 기존 동작 유지). 버튼을 얹으면 "카드를 눌러도 되고 버튼을 눌러도 되는" 두 클릭 표적이 생겨 오히려 헷갈린다 — 표(문서 목록)가 있는 카드에만 필요한 목록|히트맵 토글을 얹었다.
E. 좁은 폭 대응을 @media(뷰포트 전체)로 이 화면은 iframe 안에 있어 @media도 사실 동작은 한다(iframe 자체 뷰포트를 따름). 그러나 카드가 "이 화면 전용"이 아니라 나중에 다른 폭의 자리(예: 대시보드 슬롯)에 재사용될 수 있어 컴포넌트가 자기 폭에 반응하는 @container가 더 맞는 도구다(§7 근거).
F. 사이드바 축소를 자동 폭 판정 없이 수동 토글로만 유지 기존 gn-left-collapsed(nav.js:929-949)는 사용자가 직접 누르는 기억형 토글이다. 420px처럼 스스로 좁아지는 상황엔 사용자가 매번 누르게 하는 것이 더 나쁘다 — 폭 자동판정으로 같은 시각 언어(아이콘 레일)를 트리거하는 것을 이 시안이 새로 제안한다(기존 로직 재사용 아님, 명시).

§6. 무엇을 포기했는지 · 표 vs 시각 판 반응형 대비

⏸지식 관계도(그래프)·학습 데이터셋 만들기· 파인튜닝·정리 점검 접기 구역은 이번 범위 밖이다 — 사장님 스크린샷에 없었고, 그래프처럼 이질적인 시각화는 카드 틀을 씌우면 오히려 좁아질 위험이 있어 별도 라운드로 미룬다.
⏸자산 관리 「지도」 탭(추가 지시 C에서 캡처로 언급)은 다른 화면이다 — 이 목업은 만들지 않는다. 다만 규칙(e)는 그 화면에도 그대로 적용되도록 일반화해 아래 표에 남긴다(메인 에이전트가 그 화면에도 같은 규칙으로 반영할 근거).
⏸카드 헤더 버튼은 2번째 이미지처럼 모든 카드에 넣지 않았다(§5-D) — 표가 있는 카드에만.
표(엑셀형 · .g-rows)시각 판(히트맵 · 지도)
정보 보존 원칙말줄임 + title(원문) — 셀 하나가 진실의 단위 반응형(리플로우) — 축소·재배치. 말줄임 대상이 아니다(숫자·색은 잘려도 뜻을 모른다).
좁을 때 동작컨테이너 overflow-x:auto로 통째로 옆으로(표는 안 접는다) auto-fill/minmax로 열 수 자체가 준다(§3 실측 — 6열→3열)
겹침 레이어해당 없음(표는 원래 겹칠 요소가 없다) 절대배치(position:absolute) 금지 — dc-tile은 전부 문서 흐름(stacking) 배치라 구조적으로 안 겹친다(chatparts.js 실측, 이 시안도 그대로 유지)
실패 판정잘리는 글자(title 없이) > 0 절대배치 글자가 다른 글자 위에 얹힘, 또는 타일이 카드 폭을 벗어나 가로 스크롤 생김 (히트맵은 스크롤이 아니라 재배치가 정답)

§7. 적용 규칙 — 공용 부품화 + 좁은 폭 계약

공용 부품화(단계적, 일괄 스윕 아님 — §5-B)

2pro-white.css는 무변경 — .g-scard*가 --g-surface/--g-text/--g-muted* 토큰만 쓰므로 흰 바탕은 이미 올바른 색으로 뒤집힌다(§8에서 대비값 확인).
3aihub.html 요약 띠부터 적용 → memory.html 폼 → 승인 검증 후 다른 화면(discover 등)에 화면 단위로 확산(한 커밋에 여러 화면 금지).

§9. 제품 원칙 자가점검

⚠메뉴는 보기용 · 지시는 대화창 — 이 화면은 기존 예외다(원본 memory.html이 이미 입력 폼 화면). 수집 경로·장애노트·매뉴얼 보강은 파일시스템 경로·자유서술 구조화 입력이라 대화형 지시로 대체하기 어렵고, 이번 시안은 그 예외를 그대로 유지한 채 껍데기(카드 언어)만 바꿨다 — 새로 입력칸을 늘리지 않았고 폼 개수도 원본과 동일(수집1 + 장애노트1 + 매뉴얼1). 대화 이관은 이번 범위 밖.
✅자체완결 HTML — 외부 CDN·웹폰트·원격 이미지 0개. 더블클릭으로 열린다(이모지·순수 CSS만 사용).
✅다크톤 기본 — aihub.html·memory.html의 실제 :root 값을 그대로 복사(색 하나도 새로 정의 안 함).
✅11px 하한 — 본문·배지·타일 라벨 전부 ≥11px(.ac-tv 11px가 최소, chatparts.js와 같은 이유로 10→11px 유지).
⚠정직한 구현 — 문서 목록·요약 숫자는 전부 예시값이다(실제 API 연결 없음). 목록|히트맵 토글만 실제로 작동(§2·§4, 순수 DOM 전환, 서버 호출 없음) — 나머지 버튼·입력칸은 눌러도 반응하지 않는다(상단 배너에 명시).
✅흰 바탕 대비(프로 라이트 대응) — 이 시안은 --g-* 토큰만 쓰므로 pro-white.css가 이미 계산해 둔 대비값을 그대로 물려받는다(주석 111-119행 실측 인용): teal-ink 6.57:1(흰) / 5.73:1(패널2) · amber-ink 6.50:1/5.66:1 · blue-ink 8.14:1/7.09:1 · purple-ink 8.98:1/7.83:1 · muted-ink 5.97:1/5.20:1 — 전부 WCAG AA(4.5:1) 통과. 새 hex를 하나도 안 써서 themecolors 감시(denylist 함정)에 걸릴 여지도 없다.
✅같은 것을 한 곳에만 — 히트맵 색사전· 타일 배치·11px 규칙은 chatparts.js를 그대로 인용(재정의 없음). 등급 색(공개/민감/기밀)은 memory.html의 .dm-grade를 그대로 인용.
⚠@container 신규 의존 — 이 저장소에서 처음 쓰는 CSS 기법이다(§7 근거는 있으나 실물 코드에 전례 없음). 실제 반영 전 gijo-architect 검토에서 "Electron 번들 Chromium 버전이 105+ 확실한가"를 확인받을 것을 제안한다(이 목업은 조사 근거만 남기고 확정은 사장님·설계관 몫).

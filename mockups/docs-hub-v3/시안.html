1. 왜 이 안인지 — 편집기 내장 vs 창 왕복(Smart MD) 비교

지금(왕복) 흐름 — 담당자가 절차 메모 하나를 고치려면: 내 문서에서 문서를 찾는다 → 고칠 수단이 없어 ✍ Smart MD로 쓰기를 누른다(창 전환 1회) → 새 창에서 처음부터 다시 쓴다(기존 내용을 못 불러온다 — Smart MD는 personalDocs를 모른다, smartmd-preload.ts에 서버 통로가 없으므로 원리상 못 읽는다) → 내보내기(파일 저장, 다운로드 폴더 경유) → 내 문서로 돌아와 📥 .md 가져오기로 다시 올린다(파일시스템 왕복 1회) → 결과물은 새 문서다(옛 문서는 그대로 남아 중복). 창 전환 2회 + 파일시스템 왕복 1회 + 문서 중복 1건.

새안(내장) 흐름 — 행 상세에서 ✏ 고치기 → 같은 화면 안에서 원문을 고치고 →💾 저장(personalDocsUpdate, 이미 있는 라우트) → 목록으로. 창 전환 0회, 파일시스템 경유 0회, 문서 중복 0건. 새 문서 작성도 같다 — + 새 문서 → 템플릿 서랍(선택) → 저장.

그렇다고 Smart MD를 없애지 않는다 — 역할이 다르다. Smart MD는 로그인 없이도 쓰는 무료 독립 도구(2026-08-14 사장님 결정)로, personalDocs의 제약(문서 200건·20만자, §4)이 없고 PDF 내보내기·워드 모드 등 이 허브가 갖지 않을 기능이 있다. 바깥으로 낼 문서를 정성껏 다듬을 때는 여전히 Smart MD가 낫다 — 이 화면은 "회사 안에서 관리·수정하는 내 문서"를 위한 것이고, Smart MD는 "바깥으로도 낼 수 있는 독립 산출물"을 위한 것이다(§4에서 다시 점검).

왜 문서함(창)을 없애나 — 세 가지 증거가 겹친다. (1) nav.js:81에서 문서함은 이미 hidden:true다(2026-08-02부터 메뉴 목록에 없다, 하단 📚 한 곳으로만 닿음) — 구조적으로 이미 "곁다리" 취급이었다. (2) docbox.html의 mine 트리와 mydocs.html의 👤 내 것 탭이 같은 personalDocsList()를 이중 호출한다(docbox.html:260, mydocs.html:271) — 같은 목록이 두 곳에 따로 있는 실제 중복이다. (3) docbox.html의 인라인 편집기(openMine/ editMine/saveMine)는 이미 잘 동작하는 코드지만 👤 내 것 탭에는 없다 — 그 코드가 가야 할 자리가 애초에 여기였다. 세 증거 모두 "문서함이 따로 있을 이유"가 아니라 "문서함의 내용물이 제자리를 못 찾았다"를 가리킨다 — 그래서 창을 없애고 내용물만 옮긴다.

2. 무엇을 포기했는지

  • △ WYSIWYG(위지위그) 리치 편집은 없다 — 원문(마크다운)+ 미리보기 분할만 제공한다. Smart MD의 "워드 문서 모드"는 이번에 옮기지 않았다 — 업무 템플릿 7종은 전부 ###/- 수준의 단순 구조라 굳이 리치 편집이 필요하지 않다고 판단했다(§외부4 조사 — 마크다운 편집은 분할 뷰가 표준이지 리치 편집이 표준이 아니다). 필요해지면 별도 라운드.
  • △ 이미지 붙여넣기(Ctrl+V)는 편집 스테이지에 없다 — 요청 만들기 컴포즈에는 있다(문서함 기능 그대로 이전, docbox.html:502-538). 개인 문서 편집기는 이번 라운드에 포함하지 않았다 — personalDocs 본문은 20만 자 제한(personaldocs.ts:43) 이고 이미지 Base64를 담기 시작하면 금방 그 한도에 부딪힌다. 필요성이 확인되면 별도 결정.
  • △ 템플릿을 회사 지식으로 공유하는 기능은 없다 — 7종 템플릿은 코드 상수로 고정하고 담당자가 바꿔 쓰지 못한다(팀마다 다른 템플릿을 만들고 싶어 할 수 있다 — 이번 범위 밖).
  • △ 산출물 탭(리포트·공식 인수인계)은 자리만 예약했다 — §7. 이번 구현 범위가 아니다.
  • △ docbox 창 폐지는 이 시안의 판단이지 실행이 아니다 — 실제 제거(main.ts의 docboxWindow 코드, titlebar.js:371 리다이렉트)는 승인 후 구현 단계 몫. 이 시안은 mockups/ 밖을 건드리지 않는다.
  • △ 검색은 필터 전용 — 자유 명령어 없음(지시는 대화창 원칙), docs-hub-v2 승계.

5. 제품 원칙 자가점검

  • ✓ Smart MD 격리 유지 — smartmd-preload.ts를 한 글자도 안 건드렸다. Smart MD 창은 여전히 별도 BrowserWindow·서버 통로 0(gijoDesktop만). 이 시안은 그 창을 iframe으로 품지 않는다 — 헤더의 "✍ Smart MD로 쓰기" 버튼은 지금과 똑같이 별도 창을 연다.
  • ✓ 격리 원칙(내 것) — 편집 스테이지의 저장은 personalDocsUpdate/Create 그대로(userId로 거름, 남의 문서는 404). 화면을 합쳐도 서버 격리 계약은 안 바뀐다.
  • ✓ 읽기전용 경계(제품 안내·회사 지식) — 편집(✏ 고치기·＋새 문서)은 👤 내 것 탭에서만 나온다. 📘 제품 안내·🏢 회사 지식 행 상세에는 편집 버튼이 없다(제품 안내는 docboxRead 그대로 읽기전용, 회사 지식은 기존처럼 "AI 지식에서 관리"로 안내만).
  • ✓ 보기·올리기는 창구, 위험한 관리는 전용 화면 — 위험수용· 인수인계 공식 기록은 여전히 전용 화면 몫이다(§3 겹침 주의에 명시). 이 허브의 템플릿은 그 공식 기록을 대신하지 않는, 사전 초안일 뿐이다.
  • ✓ 지시는 대화창 · 새 입력칸 금지 — 단, 편집기는 예외 — 본문 작성 자리(제목 input·편집 textarea·요청 만들기 textarea)는 저작 행위이지 지시가 아니다 (Smart MD와 같은 지위, 과제 원칙 §4). 검색은 여전히 필터 전용.
  • ✓ 자체완결 HTML — 외부 CDN·웹폰트·원격 이미지 없음.
  • ✓ 정직한 구현 — 저장·파일로 저장 버튼은 가짜 완료 표시일 뿐이라고 배너에 적었다. "산출물" 탭은 클릭해도 예약 문구만 뜨고 데이터인 척하지 않는다.
  • △ 화면 설명은 챗봇/ⓘ로 — 탭 안내줄·hub-sub 문구는 이 시안 설명을 위한 장치다. 실제 구현에서는 screenguide 패널 + ⓘ로 옮겨야 한다(CLAUDE.md 원칙) — 시안 단계에서만 예외로 화면에 그렸다.

6. 신고 시한 연계 계약 (사장님 추가지시 — 이 시안이 정의하는 부분만)

신고 시한 기능(카운트다운 카드) 자체는 미착수·범위 밖이다. 이 시안이 지금 확정하는 것은 그 기능이 이 허브를 여는 방식뿐이다:

  • ✓ 진입 계약 — window.top.postMessage({type:"gijo:newDocFromTemplate", templateId:"incident_report"|"breach_notice", prefill:{...}}, "*"). 기존 화면열기()(mydocs.html:136-138)와 같은 postMessage 방식을 확장한 것이라 새 IPC 채널이 필요 없다.
  • ✓ 받는 쪽 — 허브가 이 메시지를 받으면 👤 내 것 탭으로 전환하고 편집 스테이지를 열어 지정 템플릿 골격을 채운 뒤, prefill로 넘어온 값(예: 발생 일시·대상 자산)을 해당 항목 줄에 채운다(§흐름 1컷 데모 버튼이 이 동작을 그대로 재현).
  • △ 이 시안 범위 밖 — 카운트다운 카드의 존재·D-day 계산·"신고 완료" 기록·신고 이후 상태 추적은 신고 시한 기능 쪽에서 별도 설계해야 한다. 이 허브는 "최종 보고서를 쓰는 자리"만 제공한다.
  • ✓ 템플릿 본문에 "법률 자문 아님" 문구 포함(§3) — 신고 의무·기한의 최종 판단은 정보보호책임자·법무팀 확인이 필요함을 명시했다.

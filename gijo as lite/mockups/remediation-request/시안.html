「조치 요청서」— 대화창에서 만들고, 보안제품 화면에서 회신을 추적한다

담당자·벤더에게 나가는 조치 요청은 새 화면이 아니라 이미 있는 픽리스트→결재판→내 문서 계약을 한 걸음 더 쓰는 것이다. 만드는 순간(대화창)·다듬는 자리(mydocs.html 내 문서)·추적하는 자리(products.html 유지보수 이력)를 분리한다. 결재판 승인은 md 초안만 만들고, 사람이 문서함에서 검수·수정한 뒤 "⬇ PDF · Word 내보내기"를 눌러야 실제로 보낼 문서가 나온다(2026-08-21 사장님 정정 — 위 방향 정정 참고).

⚠ 정직한 구현 고지 — 이 파일은 정지 그림이며 JS가 없습니다. 아래 대화창·엑셀형 표는 실제 console.js·products.html·gijo-ui.css의 클래스명·값을 그대로 복사해 모양만 재현합니다. 클릭해도 아무 동작도 하지 않습니다. "결재판 대기 중"과 "승인 후"는 같은 대화의 두 스냅샷이지 실제로 전환되는 것이 아닙니다.
핵심 결정 3줄
  1. 새 화면을 만들지 않는다. 취약점 목록에서 체크→기존 픽리스트 조치 버튼에 "📨 조치 요청서 만들기" 하나를 더한다(picklist.ts PICK_ACTIONS에 원소 1개) → 기존 결재판(cs-ap)이 필드 3개(수신처·기한· 재점검조건)를 보여준다 → 승인하면 내 문서(mydocs.html)에 md 초안 1건이 만들어진다(2026-08-21 정정 — 즉시 DOCX/PDF 확정 발급이 아니다).
  2. 다듬기·내보내기는 이미 있는 「내 문서」 편집기를 그대로 쓴다(Scene C, 신설). 업무 템플릿이 7종에서 8종으로 늘고, 저장된 문서 상세 칸(.dbt)에 "⬇ PDF · Word 내보내기" 버튼 하나가 더 붙는다(지금은 .md 내려받기만 있다) — 엔진은 리포트 엔진(report.ts) 재사용, 새 변환기 없음.
  3. 추적(products.html 유지보수 칸)은 "초안→보냄→회신" 3단계로 표기한다. "초안"은 아직 문서함에서 편집 중이라는 뜻이고, 자동 발송은 이번에도 하지 않는다 — 내보내기 이후 전달은 사람이 한다.

§1왜 이 안인가 — 기각한 다른 길

버린 안왜 버렸나
❌ 전용 새 화면(요청서 작성 폼) 「지시는 대화창에서만」 원칙(2026-07-25 이래 반복 확립) 정면 위반 — 새 화면에 입력칸을 두면 "메뉴는 카드가 전부"(2026-08-20 확정 계약)와도 어긋난다. 취약점을 고르는 동작은 이미 대화창 픽리스트가 하고 있어, 폼을 새로 두면 같은 "고르기"를 두 번 만들게 된다.
❌ 벤더에게 자동 이메일/포털 발송 폐쇄망 배치가 기본인 제품이라 SMTP 설정이 없는 사이트가 있고, 벤더마다 창구(이메일·자체 포털·전화)가 다르다. 잘못된 채널로 자동 발송하면 실제 사고가 된다. 표준 조사(위 §근거 2번)도 자동 발송을 요구하지 않는다 — 문서까지만 만들고 전달은 사람이 하는 편이 "안 되는 자동화를 되는 척"하지 않는 정직한 선택이다.
❌ 별도 칸반/트래킹 보드 products.html이 2026-08-21 같은 날 엑셀형(.g-rows)으로 개편되며 "그 제품의 유지보수 이력"이라는 자리가 이미 확립됐다. 새 보드를 만들면 "같은 것을 여러 곳에 적으면 어긋난다" (CLAUDE.md 반복 원칙)가 재발한다 — 있는 자리에 접기 판 하나를 더한다.
❌ 결재판 승인 즉시 DOCX/PDF 확정 발급

§2무엇을 포기했는가

· 벤더 포털/이메일 자동 발송 — 문서함에서 다듬어 내보내기까지만. 담당자가 다운로드해 직접 보낸다.
· 회신 자동 파싱 — 벤더 답장 이메일을 읽어 상태를 자동으로 바꾸는 것은 하지 않는다. 상태(초안→보냄→회신)는 담당자가 확인창으로 직접 확인한다(사장님 결정①) — 대신 깜빡함을 줄이려고 회신 없는 요청은 다음날 아침 브리핑이 안내한다(자동 재촉·재발송은 아니다, Scene A③). 안 되는 걸 되는 척 하지 않는다(2026-08-21 하지 않은 일을 했다고 말하는 결함 재발 방지 원칙과 같은 결).
· 수신처 자동 채움 — 등록부 벤더명·자산 담당자를 결재판이 자동으로 채우지 않는다 (사장님 결정② — 정확도를 담보 못 하는 자동 채움보다 사람이 직접 적는 편이 낫다고 판단).
· 벤더별 서식 다양화 — 일부 벤더가 자기 포털 전용 양식을 요구할 수 있으나, 1단계는 표준 서식 한 가지(리포트 엔진 기본 DOCX 틀)만 지원한다.

§7제품 원칙 자가점검

✅지시는 대화창에서만 — Scene B(products.html)· Scene C(mydocs.html)엔 지시용 입력칸이 없다. "요청서 만들기"는 Scene A(대화창)에서만 시작된다. mydocs.html의 편집기 텍스트영역은 예외로 본다 — 이미 있는 저작 행위 자리(Smart MD와 같은 지위, mydocs.html 주석 "자유 텍스트 입력칸 0(지시는 대화창) — 단 편집기·요청 만들기는 예외")라 새로 어긴 게 아니다.
✅회신 상태 전환 — 확정(사장님 결정①) 상태(초안→보냄→ 회신)는 확인창(다이얼로그)을 거쳐 사람이 바꾼다 — products.html 기존 제품삭제 확인창과 같은 성격. 자동 파싱은 없다. 대신 "보냄" 뒤 회신이 하루 넘게 없으면 다음날 아침 브리핑이 안내한다(Scene A③) — 자동 재촉·재발송이 아니라 사람에게 알려줄 뿐이다. 구현 시 정확한 확인창 문구·타이밍은 gijo-architect 검토 대상.
✅수신처 자동 채움 — 확정(사장님 결정②) 등록부 벤더명·자산 담당자를 자동으로 채우지 않는다. 결재판 필드는 "자리만" 만들고(비어 있어도 승인됨), 실제 값은 문서함에서 담당자가 자유 텍스트로 적는다 — 정확도를 담보 못 하는 자동 채움보다 사람이 직접 적는 편을 택했다.
✅메뉴는 보기용, 새 화면 금지 — 새 페이지·새 탭 0개. 기존 제품 상세 접기(Scene B)와 기존 문서함 3단 작업공간(Scene C)에 얹을 뿐이다.
✅자체완결 HTML — 외부 CDN·웹폰트·원격 이미지 0개, JS 0줄. 더블클릭으로 바로 열린다.
✅다크톤·색 토큰 — products.html·console.js·mydocs.html의 :root 값을 그대로 복사(글자 하나 안 다름).
⚠11px 하한 — Scene C만 실제로 아래로 내려간다 Scene A·B는 실제 화면 CSS 값을 그대로 복사해 11px 이상을 지킨다(.tag-off 10.5px는 이 시안 전용 주석 태그일 뿐 제품 화면이 아니다). 그런데 Scene C는 mydocs.html의 3단 작업공간을 문서 폭에 맞추려고 값을 통째로 줄였다 — .viewseg button 10.75px(실제 12px)· .tpl-lead 10.5px(실제 11.75px)·.detail .dm 11.5px(실제 12.5px, 명시 안 됐던 것을 명시)까지 내려갔다. 실제 구현은 mydocs.html의 원래 크기(12px대)를 그대로 쓴다 — Scene C의 작아진 글자는 "축소 재현"의 부작용이지 제안이 아니다. 본문에도 CSS 주석으로 밝혔다.
✅같은 것은 한 곳에서만 센다 — 요청 건수·상태는 리포트 사이드카(.json, 내보내기 시점에 생성) 한 곳이 진실이고, "초안" 판정은 사이드카 없이 personal_docs 존재로 판정한다(둘이 겹치지 않는 배타적 소스). 요청 이력 판은 그 값을 읽기만 한다.
⚠정직한 구현 — 문서 카드의 "문서 열기"·픽리스트 체크박스·결재판 승인 버튼·업무 템플릿 칩·내보내기 버튼·상태 칩은 전부 정지 그림이다(클릭 핸들러 없음). Scene A "① → ②"·Scene A③(다음날)·Scene C "① → ②" 전환은 실제 애니메이션이 아니라 같은 화면의 두 스냅샷을 나란히 배치한 것 — 코드 주석과 본문에 명시했다.
✅개인 격리 vs 업무 산출물 — 확정(사장님 결정③) mydocs.html의 개인 문서는 기본이 격리다(personaldocs.ts:142 시스템 기본값 shared:false — 명시 옵트인 전엔 "내 것"만 서버가 준다, 남의 것은 404). 그런데 조치 요청서는 다른 담당자·products.html "요청 이력"이 참조해야 하는 업무 산출물이라 성격이 다르다. 결론: 이 템플릿으로 만든 문서만 shared:true를 기본으로 켠다(끌 수 있음) — 시스템 전체 기본값을 바꾸는 게 아니라 이 템플릿 생성 경로 하나의 예외다. 비밀번호·계정 정보 자동 가림은 기존 공유 규칙 그대로 적용된다(personaldocs.ts:93 maskSecrets — shared 켜진 문서만 거친다, 새 마스킹 로직 아님).

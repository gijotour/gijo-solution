# 시안 — 프로 셸 팝업 배치

파일: `mockups/프로_팝업배치/시안.html` (자체완결, 더블클릭으로 열림 — CDN·웹폰트·원격 이미지 0개)

사장님 지시(2026-08-19): "프로에서 대화창이 메인이되고 내용은 팝업으로 안될까? 나눠서 보이는것보단" /
"지금 팝업 기능 있으니 그거 적용하면되고" / "팝업이 안뜨는건 대화창이 없어지고 보여줘도돼" /
"설정같은거?" / "전부 팝업 기능 있으니 가능할것 같은데" — **프로 전용**이다. 표준·라이트 셸은
그대로 둔다.

추천 1개 원칙 준수 — 대안(결재판이 가려지는 문제의 세 갈래)은 시안 안에 표로만 남기고 화면은 하나다.
아래는 시안.html의 결론만 옮긴 요약이다. 근거(파일:줄)·표·조사 인용은 전부 시안.html 본문에 있다.

## 핵심 결정 3줄

1. **화면을 고르면 탭이 아니라 처음부터 별도 창(팝업)이 뜬다** — 이미 있는 통로 넷(office:open·
   docbox:open·smartmd:open·shell:popout, 전부 `client/src/main.ts`에서 직접 확인)을 그대로 쓰고,
   그 결과 본창은 `body.chat-home`(app.html:66-76, 이미 있는 상태)이 **영구히 유지**되어 대화가
   항상 폭 95.5%다 — 새 상태를 만들지 않고 있는 상태를 상시화한다.
2. **결재판은 가려지지 않는다** — 원본이 본창 한 곳에만 있고(복제 안 함), 다른 창에 가려지는
   위험은 강제로 앞세우지 않고 `flashFrame`(작업표시줄 깜빡임, Electron 공식 API — 오늘 코드엔
   없어 추가 필요)로 완화한다. "팝업이 물러난다"(강제 포커스 이동)와 "결재판 복제"는 각각 포커스
   강탈 안티패턴·"같은 것을 두 곳에 적으면 어긋난다"는 이유로 기각했다.
3. **기술 난제를 정직하게 밝혔다** — 화면에서 고른 항목이 대화로 되먹임되는 `gijo:select`/
   `gijo:view`/`gijo:scope`는 전부 `window.top`/`window.parent` postMessage에 의존하는데, 별도
   BrowserWindow에서는 `window.top === window`(자기 자신)라 오늘 코드로는 **전혀 안 된다**(코드
   10곳 전수 확인 — `grouphub.js:103`의 주석이 스스로 "셸 밖이면 없던 일로"라고 적어 뒀다). 화면
   맥락 알약(어느 화면 얘기중인지)도 "얕은 겹"에서 이미 어긋나 있다(`app.html:564-575`가 팝업이
   보낸 라벨을 도킹 상태에서 버린다). 이 시안은 이 배관을 새로 만들지 않는다 — 데모의 "선택
   버튼"은 기본적으로 "오늘은 안 됩니다"를 그대로 보여주고, 켜야만 "구현됐다면"을 보여준다.

## 밀도(요지)

- 대화 폭: 오늘은 화면을 보면 380px(30.6%)로 줄지만, 이 시안은 **항상 1184px(95.5%)** —
  팝업이 몇 개 떠 있든 본창 폭은 나뉘지 않는다.
- 세로: 오늘 화면-봄 상태(636px) 대비 **+40px(+6.3%)**를 상시 확보(하단 탭줄이 영구히 필요 없어짐).
- 상시 클릭 표적: 오늘 화면-봄 10개 → 이 시안 **6개(-40%, 팝업 개수와 무관)**. 단 레일 구성 변경(💬→🗔)은
  이 시안의 제안이며 아직 코드에 없다.

## 정직하게 남긴 것 (구현 전 더 정할 것)

- 부팅 첫 화면(대시보드 자동 오픈을 대신할 것) — 답을 안 냄.
- gijo:select/view/scope IPC 중계, 맥락 알약의 "얕은 겹" 수정 — 시안 범위 밖, 다음 작업으로 명시.
- flashFrame 연결, 팝업 상한 정책 — 실측(버릴 조건 표) 후 결정.
- "팝업이 안 뜨는 화면" — 조사 결과 **오늘 기준 0개**(모든 화면이 파일 직접 로드 방식이라 렌더링
  자체는 막히지 않는다). 사장님 지시③의 "대화창이 없어지고 보여줘도 된다" 경로는 안전망으로
  시안에 만들어 뒀지만(가상 시나리오 토글), 지금 당장 필요한 화면은 확인되지 않았다.

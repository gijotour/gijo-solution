대화 데이터 카드 「보기 전환」 — 표 옆에 [목록|히트맵] 토글을 더한다

새 화면·새 API를 만들지 않는다. 지금 도는 chatparts.js dataCard()의 표 자리에 렌더 방식을 하나 더 얹는다 — 서버가 내려주는 dc.table 데이터는 그대로, 클라가 그것을 표로 그릴지 색 타일로 그릴지만 고른다. 기본은 지금처럼 목록이다.

①배경

사장님(2026-08-19): 「리스트 나올 때 히트맵이라든지 디자인이 가능한 것은 추가로 선택해서 볼 수 있게」 — 대화창 데이터 카드(같은 날 승인·구현된 mockups/대화_데이터카드)를 보고 나온 다음 요청이다. 지금 카드는 표 하나뿐이라 항목이 10줄 가까이 차면 어디가 빨간불인지 훑어보는 데 표를 한 줄씩 읽어야 한다 — 색으로 된 요약 보기가 있으면 그 훑어보기가 빨라진다.

②실제로 눌러보기 — 토글·행/타일 클릭(📌 선택)은 이 문서 안에서 실제로 동작합니다. 🗔·"외 N건"은 이 시안에서는 비활성입니다(§⑨).

요구된 예시 2개를 카드 폭 660px로 나란히 둔다 — 취약점 카드(치명 47 · 높음 116 · 중간 30) · 관제 카드(P0 5 · P1 159 · P2 29). 머리의 목록히트맵 을 눌러 보기를 바꾸고, 행/타일을 눌러 📌 선택해 보라.

예시 A — 취약점 카드(우선순위 — 조치할 취약점)
예시 B — 관제 카드(발견·수집 — 통합 관제 현황)
예시 A(취약점)의 표는 지금 운영 응답에는 없다 — findingListAnswer (picklist.ts:202-204)가 "목록이 이미 두 벌(본문 텍스트+체크칸)"이라는 이유로 표를 안 준다고 이미 결정했다(2026-08-19 2차). 여기서는 "표가 붙는다면 이런 모양"이라는 예시로 실었다 — 실제 컬럼 구성(심각·유형·자산·담당)은 그 화면의 텍스트 답(picklist.ts:191-194 [severity] finding_type @ assetName — 담당)과 같은 항목을 그대로 옮긴 것이다. 예시 B(관제)는 실제로 지금 응답하는 카드(datacard.ts:230-247 opsStatusAnswer)와 같은 컬럼·같은 정렬 규칙이다(P0 먼저, 그다음 P1 — 10줄 중 실제로 5+5가 되는 것도 그 규칙의 결과다).

③핵심 결정

  1. 토글은 카드 머리(같은 줄)에. 새 줄을 만들지 않는다 — 제목 … [목록|히트맵] … 🗔의 순서로 .dc-head 한 줄 안에 넣는다(§⑥에서 높이 증가 +1px로 확인).
  2. 기본은 목록. 2026-08-19 승인 원칙("표는 익숙한 형태가 먼저") 그대로 — 히트맵은 선택해서 보는 둘째 보기다.
  3. 상한(10줄)은 보기와 무관하게 그대로. 히트맵도 dc.table.shown 그 10건만 타일로 그린다 — 보기를 바꿨다고 서버에 더 달라고 하지 않는다(새 API 없음).
  4. 행 클릭과 타일 클릭은 같은 콜백. opts.select(row, dc.pickKey) 하나를 공유한다 — 두 보기가 "선택"이라는 다른 개념을 갖지 않는다.
  5. 토글은 표가 없으면(또는 1줄뿐이면) 안 만든다. KPI만 있는 카드(예: 지금 운영 중인 진짜 우선순위 카드)나 1건짜리 표는 보기를 바꿀 이유가 없다 — 안 쓰는 조작을 얹지 않는다.

④색 매핑 규칙 — 컬럼 값 기반, 결정적

서버는 색을 보내지 않는다(DataCard 타입 무변경). 클라가 표의 컬럼 이름에서 "판정성 열"을 찾고(정규식 하나), 그 열의 값을 고정 사전과 대조해 색을 정한다 — LLM도, 새 필드도 없다. 팔레트는 지금 카드가 이미 쓰는 4색 그대로다: #1eb980(ok)·#f0a020(warn)· #f5928a(bad)·회색(muted, --muted-2).

색값 사전(정규식, 대소문자 무시)쓰인 예
■ bad 치명|매우\s*심각|critical|P0취약점 「치명」 · 관제 「P0」
■ warn 높음|high|경고|P1취약점 「높음」 · 관제 「P1」
■ ok 정상|양호|통과|compliant검증 카드의 상태 열 「정상」(§⑦ 확장 시)
■ muted 위 어느 것도 안 걸림(기본값)취약점 「중간」 · 관제 「P2」 · 나머지 모든 값

판정성 열 찾기: cols.find(c => /심각|우선|상태/.test(c.label)) — 못 찾으면 전 타일이 muted(회색)로만 그려진다(글자는 그대로 보인다, §⑨ "열 손실"과는 다른 상황). ⚠ 색만으로 구분하지 않는다 — 타일에는 항상 그 열의 원문 글자(예: "치명"·"P0")가 같이 찍힌다(safe.security 근거, §조사 2).

⑤왜 이 안 · 검토한 대안

대안내용판정·근거
A. 진짜 2차원 히트맵
(가로=심각도, 세로=자산 등 행렬)		 전통적 리스크 매트릭스처럼 두 축을 교차해 "칸마다 건수"를 색으로 채운다. 기각 우리 표는 이미 개별 항목(행) 하나하나가 고를 수 있는 대상이다(📌 선택). 매트릭스는 칸이 "여러 건의 집계"가 되어 한 칸을 클릭해도 어떤 개별 건을 골랐다는 뜻이 안 선다 — opts.select(row) 계약과 정면으로 어긋난다. 집계하려면 서버가 새로 세야 해서 "새 API 없음" 원칙도 깬다.
B. 색만 다르게, 표는 그대로
(행 배경색만 심각도로 칠하기)		 표 형태를 유지한 채 tr 배경을 심각도색으로. 기각 "선택해서 볼 수 있게"라는 지시는 다른 보기를 요구한다 — 표에 색만 칠하면 보기가 하나뿐이라 지시에 못 미친다. (단, 이 색칠 자체는 좋은 아이디어라 §⑧에서 "포기하지 않고 표 안에도 작게 반영"으로 남긴다.)
C. 타일 그리드(심각도/우선순위 색) 채택 표의 각 행을 그대로 색 타일 하나로 그린다 — 진짜 2축 행렬이 아니라 "색으로 태그된 카드 그리드"다(용어는 사장님 말대로 "히트맵"을 쓰되, 정확히는 심각도 타일 그리드). 개별 행=개별 타일이라 📌 선택 계약이 그대로 유지되고, 서버 계산도 필요 없다. 세그먼트 컨트롤(외부 표준 ①)로 표와 나란히 두는 것이 "레이아웃 전환"의 정석 활용이다.

⑥밀도 숫자 — 머리 높이 증감 · 목록 vs 히트맵 세로 총합

⑦구현 계약(메인 에이전트용 — 승인 후)

1) 서버 — 변경 없음

server/src/engine/datacard.ts의 DataCard 타입·세 카드 함수 (hardeningStatusAnswer·assetStatusAnswer·opsStatusAnswer)는 그대로다. 색은 서버가 안 보낸다 — 클라가 §④의 사전으로 컬럼 값을 보고 정한다.

2) 클라 — chatparts.js dataCard() 안에서만

var 색사전 = [
  { re: /치명|매우\s*심각|critical|P0/i, cls: "bad"  },
  { re: /높음|high|경고|P1/i,             cls: "warn" },
  { re: /정상|양호|통과|compliant/i,       cls: "ok"   },
]; // 못 걸리면 "muted" — 새 서버 필드 없이 컬럼 값만으로 결정

function 판정열(cols) { return cols.find(function (c) { return /심각|우선|상태/.test(c.label); }); }
function 타일색(row, col) {
  if (!col) return "muted";
  var v = String(row[col.key] || "");
  for (var i = 0; i < 색사전.length; i++) if (색사전[i].re.test(v)) return 색사전[i].cls;
  return "muted";
}

function buildTiles(dc, 판정, opts) {

3) 선택 배관 — 새로 안 만든다

타일 클릭도 표 행 클릭과 같은 함수 opts.select(row, dc.pickKey || 첫컬럼키)를 부른다(console.js:1497-1503 이미 있는 콜백). 보기를 바꿔도 "무엇을 골랐는지"의 의미는 하나다.

⑧무엇을 포기했나

  • 진짜 2차원 히트맵(행렬) — §⑤ 대안 A에서 기각. 우리 데이터는 "고를 수 있는 개별 행"이라 집계형 매트릭스와 맞지 않는다.
  • 타일에서 나머지 컬럼 보기 — 표는 4개 컬럼을 다 보여주지만 타일은 판정열+라벨+보조 3개까지만 싣는다(§⑥). 나머지(예: 담당·기한)는 목록으로 돌아가거나 타일을 클릭(📌)해 이어서 물어야 한다.
  • 보기 상태 기억(localStorage) — 카드마다 새로 뜰 때 항상 목록부터다. 기억하면 "서버는 무변경"이 클라 저장소로 슬쩍 새는 것이고, 카드 하나짜리 토글에 영속 상태까지 두는 건 과하다고 판단했다 — 필요해지면 그때 따로 시안.
  • 정렬·필터를 히트맵에 추가 — 두 보기 다 서버가 이미 정렬해 보낸 순서(급한 순)를 그대로 쓴다. 다시 정렬하려면 🗔로 화면을 여는 것이 기존 원칙(대화_데이터카드 시안 §⑨)이다.
  • 표 안 행 배경색(§⑤ 대안 B) — 완전히 버리진 않았다. 목록 보기의 <tr>에도 §④ 사전으로 왼쪽 4px 띠 정도는 얹을 수 있다 — 다만 이번 시안의 범위는 "두 보기 전환"까지라 별도 판단으로 남긴다.

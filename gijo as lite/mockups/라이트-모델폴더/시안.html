왜 이 안인가

이 카드가 막혀 있으면 라이트는 첫날부터 못 쓴다(lite-settings.html:18~19 "이 화면이 안 되면 제품이 아예 안 돈다"). 그런데 지금 화면은 정확히 그 순간 필요한 값(폴더 경로)을 안 주고 "설치 안내서를 보라"고 미루는데, 안내서를 열면 다시 이 화면을 가리킨다 — 실제로 어디서도 경로를 못 얻는다(검토관 지적). 게다가 productName을 방금 "GIJO AS Lite"로 고쳐서(userData 분리 수리) 예전에 안내서 어딘가 적혀 있었을 값이라도 이제 틀렸을 것이다.

그래서 이 시안은 값을 화면이 직접 계산해 보여준다(NN/g 휴리스틱 #1 시스템 상태 가시성 · #6 회상이 아닌 인식 — 근거는 파일 상단 주석). preload가 그 순간 그 PC의 실제 경로를 내려주고, 「폴더 열기」로 탐색기까지 한 번에 연다 — 이미 같은 파일(main.ts)에 있는 shell.openPath·shell.showItemInFolder를 새 용도로 한 번 더 쓸 뿐, 새로 배우는 API가 아니다. 그리고 지금까지 안내서에도 화면에도 없던 결정적 규칙 — 폴더 이름과 파일 이름이 완전히 같아야 인식된다(localengine.ts:249 확인) — 을 그림 하나(트리)로 보여준다. 이 규칙을 몰라서 "넣었는데 안 뜬다"는 문의가 나올 텐데, 지금 화면은 이 규칙을 언급조차 안 한다.

다른 길을 왜 안 골랐나

안왜 안 골랐나
안내서(설치 가이드) 문서의 그 문장만 고쳐 실제 경로를 적는다 문서는 요청받을 때만 갱신이 원칙이고, 무엇보다 이번 사고 자체가 "문서 값이 코드와 어긋난다"(productName 변경)였다 — 문서는 또 낡는다. 실행 중인 앱이 스스로 계산해 보여주는 값만 항상 맞는다
첫 실행 때 파일 선택 창(드래그앤드롭)으로 폴더 개념 자체를 없앤다 gguf는 수 GB~수십 GB라 앱이 다시 복사하면(업로드 다이얼로그) 디스크를 두 번 쓰고 진행률·재시도까지 새로 만들어야 한다 — "안내를 고친다"는 이번 범위를 넘는 별도 기능이다. 여러 모델을 두는 상황에도 폴더 구조가 더 명확하다(차기 개선 후보로는 남겨둔다 — 아래 "포기한 것")
「폴더 열기」 버튼만 두고 경로 글자는 화면에 안 보여준다 폐쇄망 현장 지원은 전화로 경로를 불러주거나 화면을 캡처해 IT 담당자에게 보내는 일이 흔하다 — 버튼만 있으면 그 PC 앞에 있는 사람만 쓸 수 있다
이 정보 전부를 ⓘ(챗봇) 뒤로 감추고 화면엔 배지만 둔다 안내서로 떠넘기던 것을 챗봇으로 떠넘기는 것과 본질이 같다 — 첫날 반드시 끝내야 하는 조작에 필요한 값을 클릭 한 번(챗 열기)+응답 대기 뒤에 두는 셈이다. 아래 "화면 vs ⓘ 판단" 참고

무엇을 포기했나

  • 드래그앤드롭 업로드(파일 선택 다이얼로그로 통째로 복사) — 위 이유로 이번 범위 밖. 폴더 방식이 남는 한 이 시안으로 첫날 관문은 풀리지만, 차기 개선 후보로 남긴다.
  • Windows·Mac 두 경로를 나란히 큼직하게 보여주는 것 — 실제 화면은 한 OS만 쓰므로 큰 글자는 감지된 쪽 하나에만 주고, 다른 OS는 보조줄로 작게만 병기했다(그래서 Mac은 이 시안에서도 작은 글씨 1줄뿐).
  • "왜 하필 이 폴더인가"·"여러 모델 관리하기"·"등록했는데도 안 뜰 때 로그 보는 법" 같은 심화 설명 — 전부 ⓘ(챗봇) 서랍으로 밀었다. 화면엔 "이번에 당장 해야 하는 것"만 남긴다.
  • 복사 버튼은 요청엔 없었지만 넣었다 — 경로를 원격 지원 담당자에게 구두·메모로 전달할 일이 실제로 있을 것 같아서다. 비중은 최소화(작은 보조 버튼)했다 — 투명하게 밝혀 둔다.

화면에 둘 것 vs ⓘ(챗봇)로 뺄 것 — 판단

이 제품 원칙은 "화면엔 정체성 한 줄 + ⚠경고만, 설명은 챗봇(screenguide)+ⓘ로"다. 이번 정보들이 그 원칙의 어느 쪽인지 항목별로 판단했다:

정보화면 / ⓘ근거
모델 폴더 경로화면(항상 보임)조작에 직결 — 복사해 탐색기 주소창에 붙이거나, 전화로 원격 지원에 불러주는 데 쓰인다. 클릭 한 번(챗 열기) 더 거치면 이 카드가 있는 이유(첫날 완결)를 해친다
「폴더 열기」 버튼화면(항상 보임)경로와 쌍을 이루는 조작 자체 — approvals.html "폴더 열기"와 같은 급의 전례가 이미 제품에 있다
하위 폴더 구조(트리 그림)화면(항상 보임)이걸 몰라서 "넣었는데 인식이 안 된다"가 나온다 — 사용법 설명이 아니라 정확한 값의 형식(스펙)이라 화면에 있어야 한다
"인터넷 없이도 된다"화면(배지 1개로 압축)폐쇄망 고객이 "이거 인터넷 필요한가?"를 안 물어도 되게 — 문장 대신 배지로 밀도는 지켰다
안 될 때 진단(폴더 안에 또 폴더인지, 이름이 정말 같은지 등)ⓘ(챗봇, 접힘)첫날 대다수는 안 겪는다 — 겪는 소수에게만 열리는 게 맞고, 매번 화면에 늘어놓기엔 무겁다
여러 모델 동시 등록하는 법ⓘ(챗봇, 접힘)부가 시나리오 — 기본 플로우(모델 1개 등록)가 아니다
HF에서 받은 파일명이 길 때(-Q4_K_M 등) 이름 바꾸는 법ⓘ(챗봇, 접힘)②(받아서)를 쓰면 앱이 자동으로 맞춰 배치한다(hfmodels.ts:190-198 확인) — ①로 직접 옮긴 소수만 필요한 예외

  1. 경로 조회 다리 — 클라이언트 main.ts가 이미 dataRoot를 안다(191~199행). 서버 왕복 없이 path.join(dataRoot,"models")를 바로 계산해 window.gijo.getModelsFolderPath()로 내려준다 — 서버가 아직 안 떠 있어도 화면에 값이 뜬다.
  2. 「폴더 열기」 IPC — shell.openPath(MODELS_DIR)(main.ts:1054가 이미 같은 API를 다른 용도로 쓰는 중). 라이트는 클라이언트·서버가 항상 같은 PC이므로(스탠다드/프로처럼 원격일 수 없다) 이 버튼은 라이트 전용으로 둔다.
  3. OS별 표시 분기 — 렌더러가 getAppInfo().platform(titlebar.js가 이미 쓰는 값)로 Windows/Mac을 갈라 경로 문자열 하나만 보여준다.
  4. screenguide.ts FAQ 3문항 추가 — 이 시안의 「💬 안 될 때는」 내용을 초안으로 재사용 가능. 클릭 시 gijoExplain('챗 모델 파일로 등록')이 셸 콘솔에 이 질문을 던지도록 연결(chatwidget.js:31의 기존 다리 재사용 — 화면마다 새 챗 위젯을 또 만들지 않는다).
  5. 모델 폴더는 서버가 부팅마다 자동 생성한다(env.ts:53) — "폴더가 없어서 못 연다" 예외는 사실상 안 나지만, openPath 실패 시 에러 문구 정도는 필요하다(main.ts:1054-1056의 doc:open-temp 패턴과 동일하게).

색·아이콘·순서 모두 analysis.html의 graphChain()(전체 연관성 모드)을 그대로 가져왔다 — 새 시각 언어를 만들지 않았다. 배지(KEV·인터넷 노출)는 겹칠 위험이 있어 요약판에서는 뺐다(전체 화면에서만 보인다 — 아래 「포기」 참고).
이 시안은 정적 HTML입니다 — "열기 →"를 눌러도 실제로 이동하지 않습니다. 구현 시 discover.html?panel=analysis로 이동합니다(아래 「클릭 동선」 참고).

1. 왜 이 안인가 — 3종 미니어처가 아니라 대표 1종, "크게"가 아니라 "작게"

  • 고른 길: 공격경로 1종, 작게(카드 226px). 고객 문구 "연결 관계를 EDR 프로세스 트리처럼"이 가리키는 것은 셋 중 공격경로뿐이다 — 4소스 겹침은 "겹침 집계"(2열 대응), 온톨로지는 "개념 간 관계"(원형 배치)라 트리처럼 안 읽힌다. 실사 조사(SentinelOne Storyline·CrowdStrike Threat Graph)도 "1선 분석가가 설명 없이 근본 원인을 그림만 보고 이해"하는 것이 값어치라고 말한다 — 정교함이 아니라 압축이 핵심.채택
  • 버린 길 ①: 그림 3종 미니어처를 나란히. 그림마다 범례·모드 전환이 따라와 조작 개념이 3배가 된다 — "첫 화면 단순화"와 정면 충돌. 하나만 작게 얹고 나머지 둘은 상세 화면(분석·AI 기억) 제자리에 둔다 — 그쪽은 분석가가 파고들 때 보는 그림이지 매일 여는 첫 화면용이 아니다. 기각
  • 버린 길 ②: 질문이 제시한 대로 "크게". Few의 원칙(대시보드는 스크롤 없이 한 화면)과 정면 충돌한다 — 실측(아래 밀도 표)으로 이미 여유 220px 중 196px를 쓴다. "크게" 그리면 나머지 24px마저 없어져 급한 것 1건만 늘어도 스크롤이 생긴다. 고객의 둘째 요청("복잡하지 않게")이 첫째 요청("그림으로")을 이긴다고 판단했다.기각(부분)
  • 모드 선택: 방사형(소스별)이 아니라 체인(전체 연관성). 방사형은 자산 1개의 상세(원형이라 정사각형에 가까운 면적 필요, 노드 3~4개면 세로 ≈220~260px)라 여러 자산을 동시에 못 보여준다. 체인은 가로로 눕는 행이라 자산 여러 개를 나란히 쌓기 쉽고(오늘의 "여러 경로"를 보여줌), 손으로 그린 좌표가 겹칠 위험도 낮다(직선 배치 — 이 문서를 만들며 스스로 검증할 수 있는 유일한 형태였다).

2. 자리 다툼 — 무엇을 내리고 무엇을 지켰나

  • 내린 것: 글 한 줄 #glanceGo(42px). 그림 카드가 같은 자리·같은 "열기 →" 동작을 그대로 이어받는다 — 1:1 교체라 화면에 새 개념이 생기지 않는다. 보안 태세·위협 인텔·자산 요약을 가리키던 부분은 잃지만, 그건 그림 카드 자체가 다루는 영역(통합 관제 안의 공격경로)이 아니므로 원래도 이 카드가 대신할 수 없다 — 발견·수집 허브에서는 여전히 다 보인다.
  • 지킨 것: 「오늘 할 일 — 계획 짜기」 판은 손대지 않았다. 급한 것·하던 일·그 외·오늘 내 계획, 행 구조·상한(각 8건)·"담기" 동작 전부 그대로다. 이 판은 실제 조치가 시작되는 자리라 건드릴 이유가 없었고, 이 시안의 요청 범위(관계 그림 얹기)를 벗어난다.
  • 건드리지 않았지만 중요한 발견: 스크롤을 만드는 진짜 변수는 이 판이다. 급한 것·하던 일·그 외가 각각 상한(8건)에 가까워지면 이 판 혼자 최대 약 761px까지 늘어난다 — 그림 카드를 넣기 전에도 상한 근처에서는 이미 1,132px로 1,040px를 넘는다(아래 표). "취약점이 4,833건이 되며 다시 빽빽해짐"이라는 고객 지적은 바로 이 지점이지, 이 시안이 만드는 문제가 아니다. 이 판의 표시 상한 조정은 이 시안의 범위 밖이라 손대지 않았다 — 별도 결정이 필요하면 그때 다룬다.

3. 클릭 동선

  • 그림(또는 "열기 →")을 누르면 discover.html?panel=analysis로 이동한다 — 실제로 이미 있는 경로다(grouppanels.js:41 analysis 패널이 analysis.html을 그대로 품는다). 대시보드의 기존 go(page) 함수를 그대로 쓰면 된다(현재 #glanceGo가 go("discover.html")를 부르는 것과 같은 방식, 쿼리스트링만 ?panel=analysis 추가).
  • 도착한 화면에서 바로 "공격경로 분석" 탭이 열리며 같은 자산이 선택돼 있는 것이 이상적이지만, 지금 analysis.html은 위험 항목을 먼저 눌러야 탭이 나타난다(anaTabs가 선택 전엔 숨어 있다). 이 자동 선택은 화면 간 상태 전달이 필요한 별도 구현 작업이다 — 이 시안은 "그림을 얹는다"까지이고, 이 부분은 승인 후 구현 범위에 명시해 둔다(아래).

4. 무엇을 포기했나

  • 배지(KEV·인터넷 노출)를 요약판에서 뺐다 — 손으로 배치한 작은 그림이라 배지까지 넣으면 글자가 겹칠 위험이 있고(직접 렌더 확인 수단이 없는 정적 시안이라 안전한 쪽을 골랐다), 전체 화면(analysis.html)에는 이미 있다.
  • 경로 3개 이상은 안 보여준다 — 카드가 더 커진다(1개 늘 때마다 svg 세로 +76px 추정). "전체 7개는 열기에서"라고 캡션에 적어 잘랐다는 사실은 숨기지 않는다(memory.html의 관계 그래프가 쓰는 것과 같은 원칙).
  • 화면 간 자동 선택 연동(그림 클릭 시 해당 자산의 공격경로 탭이 바로 펼쳐지는 것)은 이번 시안에 안 넣었다 — 발견·수집 허브로 이동하는 것까지가 이 시안의 몫이다.
  • 오늘 계획 판의 상한 조정 — 진짜 밀도 위험은 여기 있다는 것을 밝혔을 뿐, 손대는 것은 범위 밖이라 포기했다(위 「자리 다툼」 참고).

6. 제품 원칙 자가점검

✅ 화면엔 정체성 한 줄+⚠만 — 그림 카드는 "설명"이 아니라 기존에도 있던 데이터 시각화(vizStrip·overlapPanel과 동급)다. "이게 뭔가요" 풀이는 넣지 않았다.
✅ 설명은 screenguide+ⓘ — 카드 캡션은 범례(색=무엇)만이고, "왜 위험한지" 설명은 안 넣었다. screenguide.ts에 패널 추가가 구현 범위에 있다(아래).
✅ 모든 텍스트 한글 — CVE 번호·CVSS류 코드값 외 전부 한글.
✅ 새 입력칸 금지 — 버튼·체크박스 0개 추가. "열기"는 기존 #glanceGo와 동일한 이동 전용 클릭이다.
✅ 정직 — 그림이 "관측 신호 기반(침투테스트 아님)"이라고 실제 문구를 그대로 옮겼다. 잘라낸 5개는 "전체 7개는 열기에서"로 숨기지 않았다.
✅ 제품 룩앤필 — 색·클래스·SVG 구조를 analysis.html에서 그대로 옮겼다. 새 색·새 아이콘 0개.

7. 구현 범위(승인 시)

  • dashboard.html — #glanceGo 블록을 그림 카드로 교체. 데이터는 window.gijo.analysisAttackPaths()(이미 있는 API, analysis.html이 쓰는 것과 동일)를 재사용 — 새 서버 API 0개. 상위 2개 선정 기준은 reachability(확인됨·높음 우선)·severity.

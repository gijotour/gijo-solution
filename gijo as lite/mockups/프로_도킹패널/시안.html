프로 셸 — 「접는 패널(도킹)」 + 가로세로 모니터 대응

화면(26종)을 항상 별도 창(팝업)으로 여는 지금 방식에, 넓은 본창에서는 대화를 가리지 않는 도킹 패널을, 좁은 본창(세로 모니터)에서는 팝업을 보조 모니터로 자동 배치하는 것을 더한다. 하나의 규칙이 두 고객을 맞춘다 — 사장님의 세로+가로 듀얼 모니터도, 고객 다수의 노트북 1대도 설정 없이 각자에게 맞게 동작한다.

① 배경(실측 환경) ② 핵심 결정(요약) ③ 규칙 — 도킹·팝업·보조모니터·기억 ④ 왜 이 안인가 · 최초안에서 무엇이 바뀌었나 ⑤ 밀도 숫자(두 시나리오) ⑥ 실제로 눌러보기(시연) ⑦ 공존 규칙 · 기술 근거 ⑧ 무엇을 포기했나 ⑨ 제품 원칙 자가점검 ⑩ 구현 참고(메인 에이전트용)

①배경(실측 환경)

사장님 책상 — 주모니터 세로 1080×1920 + 보조 가로 1920×1080 듀얼. 본창은 보통 세로 모니터에 있다. 고객 다수 — 노트북/가로 모니터 1대. 두 환경은 서로 반대다: 사장님은 모니터가 둘이라 "화면을 다른 데로 보낼" 여지가 있고, 고객은 모니터가 하나뿐이라 그 여지가 없다.

실측: 세로(내부 폭 1024)에서 화면·대화를 나란히 두면 644px + 380px, 둘 다 좁다 — 이게 프로 셸이 애초 팝업을 택한 이유(app.html:186-195). 반대로 가로(내부 폭 1864)에서는 대화 700 + 패널 1150 정도로 성립한다 (사장님 실측 근사치 — §5에서 정밀화).

②핵심 결정(요약)

  1. 안전 하한(절대 규칙) — 본창 내부 폭(창폭−레일56) < 1400px이면 화면은 무조건 팝업이다. 이 하한은 사용자의 「기억된 선택」으로도 못 뒤집는다 — 세로 모니터 스퀴즈 재발을 막는 마지막 방어선.
  2. 보조 모니터 자동 배치 — 본창이 좁은 디스플레이(세로 등)에 있고 다른 디스플레이가 있으면, 팝업은 그 다른 디스플레이(가로 쪽 우선)의 작업영역에 뜬다. 모니터가 하나뿐이면 지금과 동일(같은 화면 절반 분할).
  3. 내부 폭 ≥ 1400px이면 도킹이 기본이다 — 화면(패널)은 유동폭, 대화는 고정 700px (표준 셸의 .work.console-side 그리드를 그대로 재사용, §10). 도킹 슬롯은 1개.
  4. ⧉ 창으로 / ⇤ 붙이기로 언제든 반전할 수 있고, 이 반전은 기억된다(안전 하한 위에서만 적용 — 폭이 부족해지면 기억이 있어도 팝업으로 되돌아간다).
  5. "하나의 규칙이 두 고객을 맞춘다" — 사장님(듀얼, 세로 본창)은 무설정으로 세로=대화 전용·화면은 보조 가로 모니터에 자동으로 뜬다. 고객(가로 1대)은 무설정으로 도킹이 기본이라 창 관리 부담이 0이다. 같은 코드 한 벌, 같은 폭 규칙 하나가 두 경우를 각자 맞게 처리한다 — 프로필을 나누지 않는다.

③규칙 — 도킹·팝업·보조모니터·기억

☰(Ctrl+K)에서 화면을 고를 때마다 이 순서로 판단한다:

1. 그 화면이 이미 도킹돼 있다            → 그 패널을 강조(포커스)만 한다.
2. 그 화면이 이미 팝업으로 떠 있다         → 그 창을 포커스한다(기존 동작, 무변경).
3. 도킹 슬롯이 다른 화면으로 차 있다        → 팝업으로 연다(안내 토스트).
4. 내부 폭 < 1400px                     → 팝업으로 연다. ★기억이 있어도 이 규칙이 이긴다(안전 하한).
5. 내부 폭 ≥ 1400px, 기억된 선택 = "팝업"   → 팝업으로 연다(사용자가 마지막에 그렇게 반전했다).
6. (그 외 — 폭 충분 + 기억 없음 또는 "도킹") → 도킹한다.

  ※ 팝업을 열 때(1~5의 어느 경로든), 본창이 있는 디스플레이가 "좁은" 쪽(내부 폭 <1400 상당)이고
    다른 디스플레이가 있으면 그 디스플레이(가로 쪽 우선)에 배치한다. 없으면 기존과 동일(같은 화면 절반).

1400px 근거: 대화 고정폭 700(사장님 실측 근사 + MD3 medium 등급 상단) + 화면 최소 유용폭 ≈700(경계에서는 팬널·대화가 동률, §5의 경계값 caveat 참조) — 정확히는 main.ts의 기존 상수 760과 약간의 여유차가 있어 §8에 캐벗을 남겼다.

④왜 이 안인가 · 최초안에서 무엇이 바뀌었나

정직한 정정 — 최초안(이 파일의 이전 버전)은 "선택을 기억하면 좁은 모니터에서 다시 스퀴즈가 재발한다"는 이유로 기억을 아예 없앴다(모드 C로 분류해 기각). 사장님 지시로 실제 사용 환경 (듀얼 모니터, 보조 모니터로 화면을 돌려보낼 수 있음)을 반영하니 그 우려가 다르게 해소된다는 것을 확인했다:

기억이 위험했던 이유는 "폭이 부족해도 기억된 값이 그걸 덮어쓴다"는 데 있었다. 그래서 이번 개정은 안전 하한(폭<1400 → 항상 팝업)을 기억보다 우선순위가 높은 절대 규칙으로 못박았다 — 기억은 그 하한 위에서만 작동한다. 이러면 "기억하되 재발하지 않는다"가 동시에 성립한다. 최초안의 우려 자체는 틀리지 않았다(그래서 하한을 없애지 않았다) — 다만 "기억 자체를 금지"가 아니라 "기억의 적용 범위를 좁히는" 해법이 있었다는 것을 놓쳤었다.

대안기각 이유(근거)
A. 항상 도킹만 세로 1080에서 56+644+380=1080 스퀴즈 재현(app.html:186-195, 실측과 동일) — 애초 팝업을 택한 이유를 정면으로 되살리므로 기각.
B. 항상 팝업만
(현재 5.27.0)		 업계 최신(사이드카·지속형 사이드바)과 가장 벌어진 지점을 방치. 듀얼 모니터가 있어도 사용자가 매번 수동으로 창을 다른 모니터로 끌어야 한다 — 자동배치가 없으면 사장님 환경의 이점을 못 쓴다.
C. 기억을 아예 안 둔다
(최초안의 결정)		 안전하지만 "⧉ 창으로/⇤ 붙이기"를 매번 눌러야 해서 "마지막 선택을 존중한다"는 상식적 기대를 저버린다. 위 정정 카드에서 설명한 대로, 하한을 지키면서도 기억할 수 있음을 확인해 폐기.
D. 안전 하한 + 그 위에서 기억 + 보조모니터 자동배치 채택 A의 재발 위험(하한으로 차단) · B의 업계 격차(도킹+자동배치로 메움) · C의 불편(기억으로 해소)을 모두 만족한다. "하나의 규칙이 두 고객을 맞춘다" — 프로필 분기 없이 폭과 디스플레이 배치만 본다.

⑦공존 규칙 · 기술 근거

도킹 슬롯 = 1개 (탭 부활 금지)

프로 셸은 2026-08-19 P2 수리로 "탭 개념 없음"을 명문화했다(app.html:56 주석). 도킹 패널을 여러 개 허용하면 그 결정을 조용히 뒤집는 것과 같다. 슬롯이 차 있으면 새 화면은 팝업으로 보낸다(§3 규칙3).

접기 = 숨김, 버림 아님

✕ 접기는 iframe을 지우지 않는다 — 기존 탭이 쓰는 .screen{display:none}과 정확히 같은 메커니즘. 사이드카 패턴(MS Security Copilot: "숨겨도 백그라운드 유지")과 일치한다.

기술 장점 — 배관이 "그대로" 통한다(코드로 확인함)

app.html:706-707의 활성탭안인가()는 active.frame만 보고 postMessage 출처를 판정한다. 도킹 화면을 표준 탭과 같은 방식으로 열면 📌 선택칩·🗂 범위·gijo:view가 코드 수정 없이 그대로 동작한다.

팝업(별도 OS 창)은 onShellBridge로 메인 프로세스를 거쳐야 한다(오늘 P4로 수리한 다리) — 보조 모니터 자동배치를 써도 이 배관 자체는 그대로다(창 위치만 바뀔 뿐, 메시지 경로는 안 바뀐다).

같은 화면을 도킹 + 팝업 동시에?

금지한다. 이미 도킹된 화면을 다시 고르면 패널을 강조만 한다. 서로 다른 화면을 하나는 도킹, 하나는(자동배치로 다른 모니터에) 팝업으로 동시에 여는 것은 허용한다 — 상태 충돌이 없다. NN/g 원칙 ("새 창은 비교·결합·추적이 명확할 때만")과 일치.

⑧무엇을 포기했나

  • 다중 도킹 슬롯 — 여러 화면을 동시에 나란히 도킹(탭 부활과 같아지므로).
  • 손잡이로 폭 조절 — 표준 셸 콘솔의 기존 이유(app.html:604-608, iframe이 매번 다시 그려져 버벅임) 그대로.
  • 1400px 근처의 정밀 조정(경계값 caveat, §5) — 1460으로 올리는 안을 검토했지만, 사장님이 준 "~1400"에 가장 가깝게 우선 맞췄다. 실사용 데이터가 쌓이기 전에는 더 다듬지 않는다.
  • 3개 이상 모니터의 정밀 매칭 — 보조 디스플레이가 여럿이면 "가로 쪽 중 가장 넓은 것"까지만 고른다. "본창과 나란히·특정 위치" 같은 세밀한 배치는 하지 않는다(우선 자동배치가 되는 것 자체가 개선).
  • 동시 도킹+팝업(같은 화면) — §7에서 금지로 결정.
  • 창 크기 변경 중 자동 재판정 — 이미 도킹된 화면은 창을 좁혀도 도중에 뺏지 않는다. 판정은 여는 순간에만 한다(작업 중 놀라게 하지 않는다).

⑨제품 원칙 자가점검

원칙점검
정직한 구현§6의 모든 상호작용은 "(시연)"으로 표시했다. 동작하지 않는 것을 동작하는 척하지 않았다.
입력은 대화창에서만도킹 패널·보조모니터 팝업 모두 새 입력칸을 추가하지 않는다 — 대화창이 유일한 지시 창구라는 원칙이 그대로 유지된다.
단일 출처도킹 가능 여부·기억 판단은 함수 하나(§10)에서만 읽는다. 화면 이름은 지금과 같이 nav.js GROUPS에서만 읽는다(새 이름표를 만들지 않음). 디스플레이 판정은 이미 쓰이던 screen.getDisplayMatching 하나를 재사용한다(새 판정 로직을 따로 안 만듦).
무변경 원칙(요청 준수)레일 56px·아이콘 4개, 결재판, 📌 선택/🗂 범위 배관 — 전부 그대로다.

5) "다른 모니터에 열림 ↗" 표시

새로 추적 코드를 만들지 않는다 — 기존 window.gijo.listWindows()(app.html:826-834)가 이미 각 팝업 창 정보를 준다. 그 창의 getBounds()가 속한 디스플레이가 본창의 디스플레이와 다르면 "↗ 다른 모니터"로 표시하고, 클릭 시 기존 focusWindow(id)를 그대로 호출한다.

6) 저장 키

  • 신규 gijo:pro:dockpref:v1 = "dock" | "popup" (없으면 자동/폭규칙). 불변식: 내부 폭<1400이면 이 값이 무엇이든 무시하고 팝업(§3 규칙4가 규칙5보다 먼저 검사됨 — 순서가 안전성의 전부다).
  • gijo:tabs:v1·gijo:console:side(SIDE_KEY) — 프로 미사용, 무변경(기존 결정 계승).
  • 도킹 자체의 열림/접힘 상태 — 세션 한정, 재시작 시 초기화(app.html:912 "프로는 저장 탭을 복원하지 않는다" 결정과 같은 방향). 기억되는 것은 오직 "도킹 vs 팝업" 선호 하나뿐이다.

7) 시험(제안)

  • 폭 경계(내부 폭 1399/1400/1460) × 기억값(dock/popup/없음) 조합 소스 감시 — 규칙4가 항상 규칙5보다 먼저 검사되는지(안전 하한 우회 불가) 회귀로 고정.
  • popoutBounds는 Electron 앱 전체 기동 없이, 순수 함수로 분리해 가짜 디스플레이 배열 [{width:1080,portrait},{width:1920,landscape}] 두 벌을 넣어 유닛 시험(가능하면 vitest).

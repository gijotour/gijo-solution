대화 안 「데이터 카드」 — 검증 현황처럼 화면급 데이터를 대화 안에서 답한다

화면 전체를 대화에 밀어 넣는 대신(기각, §②), 이미 있는 "결정적 목록 답 + 그 자리에서 고르기" (picklist) 패턴을 KPI 숫자까지 함께 담는 표 카드로 넓힌다. 카드 머리의 🗔 화면으로 열기는 지금 있는 도킹/팝업 배관을 그대로 쓰고, 카드 숫자는 전부 서버가 규칙으로 계산한다 — 모델이 표를 지어내지 않는다.

①사장님 지시 · 스크린샷

「가능하면 대화창 안에 데이터를(팝업 내용을) 나오게 가능할까? 고민해줘. 안 되면 왼쪽 패널에 붙이는 게 맞을 것 같긴 해.」 — 검증(하드닝) 화면 스크린샷과 함께(2026-08-19).

스크린샷에 보인 값: KPI 4개 — 등록 장비 0 · 활성 스케줄 0 · 평균 준수율 57% · 점검 이력 16회. 그리고 절차 띠(workflowrail)의 「미점검 대상 29」.

정직 고지 — 두 수치는 실제로 서로 다른 서버 계산에서 나온다. 「등록 장비 0」은 grouppanels.js:169-195가 hardeningTargets.list()로 직접 세는 값이고, 「미점검 대상 29」는 workflow.ts:106-117가 같은 원천 (listTargets())에서 "한 번도 점검 안 한 대상"만 골라 센 값이다. 등록 장비가 0인데 미점검 대상이 29라면 두 계산이 서로 다른 시점이거나 서로 다른 조건을 보고 있다는 뜻이다 — 이 시안이 지어낸 오차가 아니라 스크린샷에 실제로 찍힌 값을 그대로 옮긴 것이다. 이 어긋남 자체는 이 시안의 범위 밖(서버 계산 로직 점검 필요)이라 고치지 않았지만, 숨기지 않고 §④ 시연에 그대로 담았다 — §⑦에서 "계산을 한 곳(서버)으로 모으면 이런 어긋남이 구조적으로 줄어든다"는 이유로 다시 다룬다.

②검토한 대안 · 왜 이 안인가

대안내용판정·근거
A. 화면 전체를 대화에 임베드
(사장님이 물은 원안)		 verify.html 같은 화면(사이드바·스크립트·모달까지 포함한 완결 문서)을 대화 말풍선 안에 iframe으로 통째로 끼운다. 기각 대화 로그가 살아있는 화면(자체 폴링·모달·이벤트 리스너)들로 무거워진다 — 대화를 스크롤할 때마다 그 화면들이 백그라운드에서 계속 돈다. 외부 사례 22개 중 이 패턴을 쓰는 곳이 한 곳도 없다(§ 근거 1). Claude Artifacts·MS Security Copilot 모두 "대화 안=요약, 전체는 분할·별도 자리"로 정착했다.
B. 왼쪽(도킹) 패널에 늘 붙이기
(사장님의 백업안)		 mockups/프로_도킹패널/시안.html의 도킹 슬롯에 화면을 열어 대화 옆에 상시 배치. 유지 — 이미 별도로 승인됨 도킹은 "화면을 펴서 보는" 수단이라 파고들 때 쓴다. 이 시안과 경쟁 관계가 아니다 — 카드 머리의 🗔로 넘어가는 목적지가 바로 이 도킹(또는 팝업)이다. §③에서 "대화가 1차, 패널은 2차"로 역할을 나눈다.
C. 데이터 카드(표+KPI) 채택 화면급 KPI·목록을 대화 안에 정적 표 카드로 답하고, 상한을 넘으면 🗔로 도킹/팝업을 연다. A의 무게 문제(살아있는 화면 없음, 정적 데이터라 끝) · B만으로는 못 푸는 것("물어본 즉시 대화 안에서 바로 보인다")을 동시에 해결한다. 이미 있는 picklist 패턴의 확장이라 구현 위험이 낮다 (§⑦).

③핵심 결정

  1. 대화가 1차, 패널은 2차. "검증 현황 보여줘" 같은 물음은 카드로 대화 안에서 바로 끝난다. 더 파고들 때(장비 하나씩 스케줄 걸기·등록 등)만 🗔로 검증 화면(도킹/팝업)을 연다.
  2. 카드 = KPI 줄 + 목록 표. 새 시각 언어를 만들지 않는다 — KPI는 .g-kpi의 색 의미를, 표는 gijo-ui.css:342-369의 엑셀급 밀도 값을 그대로 축소해 쓴다(§⑥).
  3. 표는 상한 10줄, 나머지는 🗔로. picklist의 기존 상한(20, MAX_PICK) 철학을 표에 맞게 절반으로 좁힌다 — 근거는 §⑤.
  4. 행 클릭 = 📌 선택. 이미 있는 "화면에서 고른 것이 「이거」가 된다" 배관(sel, console.js:1091-1101)에 카드도 올라탄다 — 새 상태를 안 만든다.
  5. 숫자는 전부 서버산. LLM은 카드를 만들지 않는다 — 서버가 결정적으로 계산한 값을 r.dataCard로 내려보내면 부품이 그대로 그린다(§⑩).

④실제로 눌러보기 — 전부 (시연)입니다. 진짜 서버 응답이 아니라 고정된 자리표시자입니다.

⑤긴 목록 처리 규칙 — 왜 10줄인가

표는 상위 10줄만 그리고, 넘치면 "외 N건 — 화면에서 보기"로 잇는다. 넘친 나머지를 "잘라서 보여주는" 짓은 하지 않는다(끝의 19건을 자르면 담당자가 그 19건이 사라진 줄 안다 — picklist.ts:387-391의 "잘린 절반을 대상으로 삼지 않는다"는 원칙과 같은 이유).

근거내용
내부 선례(상한을 절반으로) picklist.ts:37 MAX_PICK = 20("스무 개가 넘으면 고르는 것보다 조건이 낫다"). 표는 목록보다 한 눈에 덜 읽힌다 — 한 줄이 여러 칸(이름·기준·접속·등록) 으로 나뉘어 시선이 칸마다 오간다. 그래서 기존 문자 목록 상한의 절반(10)을 표의 상한으로 잡았다.
외부 표준 — 점진적 공개 IxDF·Primer 공통 원칙: 처음엔 일부만 보여주고 나머지는 다음 층으로 미룬다 (ixdf.org/literature/topics/progressive-disclosure · primer.style/product/ui-patterns/progressive-disclosure). "외 19건 — 화면에서"가 바로 그 다음 층이다.
외부 표준 — Adaptive Cards Microsoft 가이드: 표가 카드 payload 상한을 넘으면 페이지를 나누거나 더 큰 화면(탭)으로 안내하라(learn.microsoft.com/adaptive-cards/schema-explorer/table). 우리 "🗔 화면으로 열기"가 그 "더 큰 화면"이다 — 새 개념이 아니라 이미 있는 도킹/팝업이 그 자리다.
세로 예산 10줄 카드 실측 세로합은 §⑥에서 ≈410px — 일반적 노트북(1080p) 화면에서 콘솔 표시영역 (대략 500~650px, 근사치·실측 아님)에 한 화면으로 들어오는 크기를 목표로 잡았다.

1) 새 부품은 chatparts.js에 — 지시문의 "console.js에 추가"를 정정한다

2) 아이콘 정정 — 🗔(화면 열기) vs ⧉(별도 창으로 빼기)

지시문은 "⧉ 화면으로 열기"라 했지만, 제품에서 ⧉는 이미 다른 뜻이다 — "지금 보고 있는 것을 별도 창으로 뺀다"(app.html:279 #tbPopout "⧉ 창으로", app.html:1015 도킹 패널 헤더의 "⧉ 창으로"도 같은 뜻). 반대로 "다른 화면을 새로 찾아 연다"는 이미 chatparts.js:284-287의 🗔 <화면명> 열기 문구를 쓰고 있다 ("가서 하기" 버튼). 같은 글자를 다른 뜻으로 겹쳐 쓰면 담당자가 "이 창을 빼는 건가, 다른 화면을 여는 건가"를 헷갈린다 — 그래서 이 시안은 🗔로 통일했다. 이 시안(§④)이 그 정정을 실제로 쓰고 있다.

4) 검증 현황 — 새 결정적 함수 하나(기존 패턴 그대로 복제)

findingListAnswer(picklist.ts:154-205)와 같은 모양으로 만든다: 트리거 정규식 → 실데이터(listTargets·listSchedules·listRuns, 이미 grouppanels.js:169-195·hardening.html:171-182가 같은 API로 계산 중인 바로 그 자료) → KPI 4개 + "미확인" 대상 10줄 자르기 → { output, dataCard } 반환. LLM은 트리거만 거치고 숫자에는 손대지 않는다(§⑩ 원칙 그대로).

계산을 서버 이 함수 한 곳으로 모으면, §①에서 정직 고지한 "0 vs 29" 같은 어긋남이 구조적으로 줄어든다 — 지금은 같은 계산이 클라(grouppanels.js)와 서버(workflow.ts) 두 곳에 따로 있어서 벌어질 수 있는 틈이다. 이 시안이 그 틈을 고친다고 약속하지는 않는다(범위 밖) — 다만 새 함수를 서버에 하나 더 만드는 김에 세 번째 사본을 늘리지 않는다는 것만 확인한다.

5) 행 클릭 → 📌 선택 — 새 배관이 필요 없다

console.js는 카드와 sel 변수(1091행)가 같은 문서 안에 있다. iframe 화면의 선택은 postMessage(app.html:684 gijo:select)를 거쳐야 하지만, 데이터 카드는 콘솔 자신이 그리는 DOM이라 그 자리에서 바로 setSelection(...)을 호출 하면 된다 — 오히려 화면(iframe) 쪽 선택보다 배관이 더 짧다.

⑧1차 적용 화면 3곳 — 비용순

지시문은 "검증(하드닝 현황)·보안설정점검·자산 현황"을 예로 들었지만, 코드를 확인하니 검증과 보안설정점검은 지금 같은 화면이다 — verify.html은 허브 껍데기이고 실제 패널은 grouppanels.js:169-195의 hardening 패널 하나뿐이다 (verify: [{ id: "hardening", … }]). 그래서 "3곳"이 되려면 실제로 서로 다른 화면 셋이 필요하다 — 아래는 이미 결정적 답 함수가 있는지를 기준으로 구현 비용순으로 다시 골랐다.

순서화면비용근거
1우선순위(triage.html, 취약점 목록)가장 낮음 findingListAnswer(picklist.ts:154)가 이미 결정적으로 KPI급 숫자(총건수· 미배정·초과)와 행 데이터를 만든다. dataCard로 옮기는 건 같은 값을 표로 다시 포장하는 일뿐 — 새 계산이 필요 없다.
2검증(하드닝 현황 — 사장님 시나리오)중간 결정적 자료(listTargets/Runs/Schedules)는 이미 있지만 대화 쪽 트리거 함수가 없다 (§⑦-4에서 새로 만듦). 자료 원천은 재사용, 로직만 새로 필요.
3자산 현황(inventory.html)중간 list_assets 도구(agenttools/handlers.ts:239 runListAssets)가 이미 결정적으로 자산을 나열한다(LLM은 도구 호출만 고른다) — 다만 지금은 문자열 한 덩어리를 돌려주므로 KPI+표로 나누려면 그 함수의 반환 구조를 손봐야 한다.

⑨무엇을 포기했나

  • 화면 전체 임베드(대안 A) — §②에서 기각. 폭·성능·이중 스크립트 실행 문제.
  • 표 안 정렬·필터·페이지네이션 — 대화 카드는 보는 자리다. 정렬·필터가 필요해지는 순간이 바로 "🗔로 화면을 열 때"라고 판단했다(화면엔 이미 있는 기능).
  • 표 안 다중 선택(체크칸) — 이미 picklist(attachPicks)가 그 역할이다. 데이터 카드의 행 클릭은 단일 📌 선택만 한다 — 두 선택 방식을 한 카드에 섞으면 "체크한 게 이건데 📌는 저건가"가 된다.
  • "이 장비 점검해줘"의 실제 실행 — §④ 시연은 📌 선택까지만 보인다. 그 뒤 실제로 점검을 돌리려면 hardening 대상을 대화에서 지시하는 서버 도구가 새로 필요하다(agenttools.ts에 아직 없음, 확인함) — 이 시안의 범위 밖이다.
  • 0 vs 29 어긋남 수정 — §①에서 정직 고지만 하고 고치지 않았다. UI 시안의 범위가 아니다.

# GIJO AS — 디스패치 사전 라우팅(온톨로지 도구 축소) 설계 가이드

> P3 설계 가이드 (2026-07-25). **지금 구현하지 않는다** — 도구가 늘어 임계에 닿을 때 이 가이드대로 착수한다.
> 짝: P1(골드 few-shot 동적 주입, `orchestrator-dataset.ts` — 구현됨) · P2(회귀 하네스, `tools/regress/` — 구현됨).

## 1. 배경 — 왜, 그리고 왜 "아직"인가

도구 카탈로그가 커지면 LLM 도구 선택은 실제로 붕괴한다:
- 도구 10개→100개에서 선택 정확도 78%→13.6%로 추락, 검색 기반 축소(RAG-MCP)로 43.1% 회복 — [arXiv 2505.03275](https://arxiv.org/html/2505.03275)
- 프롬프트에 도구를 다 부으면 "context rot"로 기능이 서로 뭉개짐 — [WRITER 엔지니어링](https://writer.com/engineering/rag-mcp/)
- 실무 권장 후보 수는 **5~15개** — 라우팅 계층으로 축소 후 결정

**우리 현황(2026-07-25)**: 도구 13개 + 이미 2중 방어가 있다 —
1. `toolDomainsForScreen(screen)` — 화면 업무영역으로 후보 축소 (agentloop `ToolScope.domains`)
2. `forcedToolFor` — 대표 문구는 LLM 결정 자체를 건너뜀 (FORCED_INTENT)

즉 **현재는 임계 이하**다. 실측(2026-07-25, 7B vs 14B A/B)에서도 도구선택 4/4 완벽이었다. 지금 추가 라우팅을 넣으면 복잡도만 늘고 이득이 없다.

## 2. 착수 트리거 (이 조건이 오면 시작)

- 도구 수가 **20개를 넘어설 때**, 또는
- 회귀 하네스(P2)·dispatch 벤치에서 **도구 오선택이 재발**할 때, 또는
- MCP 연동(mcp.html)으로 **외부 도구가 대량 유입**될 때 (이때가 가장 유력 — MCP 도구는 수십 개 단위로 들어온다)

## 3. 설계 원칙 — 하드 필터 금지, 랭킹·확장만

제안서(2026-07-25 검토)의 "온톨로지 키워드 매칭으로 3~4개만 노출"은 **그대로 쓰면 위험**하다:
키워드가 정답 도구를 후보에서 제외하면 회복 불가(모델이 아무리 똑똑해도 없는 도구는 못 부른다).

**원칙:**
1. **제외가 아니라 랭킹** — 전 도구에 점수를 매겨 상위 N(8~12)개를 카탈로그에 올린다. 단, 안전망으로 `cross` 도메인 도구(검색·설명·브리핑)는 항상 포함.
2. **신호 3원 결합** (모두 결정적·오프라인, LLM 비용 0):
   - ① 화면 도메인(기존 `toolDomainsForScreen`) — 가장 강한 신호, 유지
   - ② 온톨로지 엔티티 매칭 — 지시문에서 온톨로지 노드(CVE-·KEV·오탐·배정·하드닝 등)를 잡아 그 노드와 연결된 도구에 가점. `ontology.ts`의 `ontologyContextFor`가 이미 엔티티 추출을 하므로 재활용.
   - ③ 골드 유사도(P1 재활용) — `findSimilarDecisions`의 상위 결과가 가리키는 도구에 가점. 승인 골드가 쌓일수록 라우팅이 현장 문구에 맞게 자가 개선된다(P1과 같은 데이터, 같은 bigram Dice — 추가 인프라 0).
3. **few-shot과 카탈로그 일치** — P1의 `allowedTools` 필터가 이미 이 계약을 지킨다(카탈로그 밖 도구 예시 주입 금지). 라우팅 도입 시 같은 Set을 넘기면 된다.
4. **폴백 유지** — 라우팅 후 결정이 `final`이거나 파싱 실패면 기존 폴백(전체 카탈로그 재시도 또는 채팅)으로. 라우팅이 새 실패 모드가 되면 안 된다.

## 4. 구현 스케치

```
dispatcher → runAgentLoop(instruction, context, scope)
              ├─ scope.domains  (기존: 화면 도메인)
              └─ [신설] rankTools(instruction):
                    score(tool) = w1·domainMatch + w2·ontologyEntityMatch + w3·goldSimilarity
                    → 상위 N + cross 도구 = 카탈로그
                    → listToolsFor 결과를 이 순서로 정렬·절단
```
- 위치: `agenttools.ts`에 `rankToolsFor(instruction, domains, role)` 신설, `agentloop.ts`의 `toolCatalogText`·`allowedTools`가 이를 소비.
- 가중치 초기값 w1=3, w2=2, w3=2 — 벤치로 조정.
- 온톨로지 매칭은 트리플의 subject/object 문자열 인덱스를 시작 시 1회 빌드(수천 건, Map 조회 <1ms).

## 5. 측정 — 켜기 전·후를 반드시 잰다

1. **결정 벤치**: SEED_DECISIONS 34건(+골드)을 실 LLM에 라우팅 on/off로 돌려 도구 선택 일치율 비교. (Phase 4에서 쓰던 held-out 방식 재활용 — 파인튜닝은 폐기했지만 측정 틀은 유효)
2. **회귀 하네스(P2)**: `tools/regress/run.mjs` — 라우팅이 답변 품질을 건드리지 않는지.
3. **합격 기준**: 도구 선택 일치율이 기존 대비 **저하 0** + 프롬프트 토큰 감소. 저하가 1건이라도 있으면 가중치 조정 또는 N 확대 후 재측정.

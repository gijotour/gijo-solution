## 1. 하려는 일

담당자와 우리 사이의 **문서 통로가 양쪽 다 막혀 있다.** 창 하나로 둘을 연다.

| 방향 | 지금 상태 | 만들 것 |
|---|---|---|
| **← 읽기** | **출하 문서가 이미 있는데 담당자가 읽을 화면이 없다.** AI 답변의 근거(RAG)로만 쓰인다 | 목차로 펼쳐 읽기 |
| **→ 쓰기** | 통로 없음. 불편을 느껴도 구두로 흘러가고 **어느 화면에서 무엇을 하다 그랬는지**가 사라진다 | 스크린샷 붙여 요청 작성 → **파일로 저장** |

**왜 한 창인가**: 둘 다 마크다운이다. 렌더링·이미지 처리·목차 생성이 같은 코드다. 조작 개념 하나로 두 가지 일을 한다.

## 2. 어떤 문서를 보여줄까 — "필요한 것만"

`docs-manifest.json`에 고객사 출하 문서 **13건**이 이미 선별돼 있다. 그런데 그 13건은 **AI가 답할 근거**의 목록이지, 사람이 읽을 문서의 목록이 아니다. 갈라야 한다.

### 보여줄 것 (7건)

| 분류 | 문서 | 담당자가 왜 읽나 |
|---|---|---|
| **📚 사용 안내** | 사용자 매뉴얼 | 로그인·화면·권한·일일 루틴 |
| | 보안담당자 실무매뉴얼 | 실제 업무 순서 |
| | 보안담당자 활용가이드 | 잘 쓰는 방법 |
| | 제품 소개 | **상급자에게 설명할 때** 그대로 씀 |
| **📐 업무 지침** | AI-BOM 검토 가이드 | 담당자가 직접 하는 일 |
| | 취약점관리 지침 | 〃 |
| | 보안제품관리 지침 | 〃 |

### 안 보여줄 것 (6건 — `knowledge/*`)

거버넌스 표준·취약점 식별체계·유지보수절차·로그체계·콘솔 메뉴맵·릴리즈노트 —
**AI가 답할 때 쓰는 지식 재료**다. 사람이 목차에서 펼쳐 읽을 문서가 아니다.
담당자가 이 내용이 궁금하면 **챗봇에 물으면 된다**(그게 이 제품의 방식이다).

> ⚠ **아키텍처 문서는 지금 출하 목록에 없다.** `GIJO_AS_RAG_아키텍처_LLM연동.md` 같은 것은
> 내부 구조(소스 경로·미구현 기능)가 드러나 매니페스트가 **의도적으로 제외**한 계열이다.
> 보여주려면 **고객용 아키텍처 개요를 새로 써야** 한다 — 그건 별도 작업(9절 결정사항).

## 3. Smart MD Studio에서 가져올 것 / 안 가져올 것

### 가져올 것 — 로직만 (~40줄 + 템플릿)

| 조각 | 위치 | 왜 |
|---|---|---|
| **Ctrl+V 스크린샷 → Base64 내장** | `js/app.js` `processImageFile()` + paste 가로채기 | 파일 첨부 없이 문서 하나에 그림이 들어간다. **폐쇄망에 딱 맞다** |
| **요청 유형 템플릿 4종** | `js/templates.js` — bug/feature/ui/refactor | 이미 `[버그 수정 요청]`·`[신규 기능 요청]` 형식이다. 빈 칸 앞에서 막막하지 않게 |
| **.md 내보내기** | `btnExportMd` | 결과물이 마크다운 한 파일 → 클로드가 그대로 읽는다 |

### 안 가져올 것

- **Electron 셸(`main.js`)** — 우리 클라가 이미 Electron이다. 창만 하나 더 띄우면 된다
- **⚠ 디자인 전부** — 그쪽은 "프리미엄 테마 + A4 워드 용지"다. 그대로 넣으면 **혼자 다른 앱처럼 보인다**. 껍데기는 우리 것으로 새로 입힌다(6절)
- **자동 저장(localStorage)** — 강제 종료 시 유실 이력이 있다. 초안은 서버에 둔다
- **워드 모드·테마 전환** — 조작 개념을 늘리면 3.5.0 직관성 개편에 역행한다

MIT 라이선스 + 우리 제품이라 차용에 문제 없다.

## 5. 사례 조사 (설계 근거)

업계 표준은 **인앱 피드백 위젯**(Marker.io·Usersnap·BugHerd). 공통 패턴과 우리 적용:

| 사례의 패턴 | 우리 적용 |
|---|---|
| 위젯 → **스크린샷 자동 캡처** → 주석 | Ctrl+V 붙여넣기로 대체 — 폐쇄망에선 **담당자가 무엇을 넣는지 통제**하는 편이 낫다 |
| **기술 정보 자동 첨부**(버전·URL·콘솔 로그) — "개발자와의 왕복을 줄인다" | **가장 중요한 차용점.** 6-③ |
| 이슈 트래커 전송 + 양방향 동기화 | 채택 안 함 — 폐쇄망에서 나갈 통로가 없다. **파일 저장이 우리 방식** |
| 세션 리플레이(최근 30초 녹화) | **채택 안 함** — 화면 녹화는 폐쇄망 보안 검토를 통과하기 어렵다 |

> 핵심 교훈: 사례들이 한결같이 강조하는 건 **"기술 정보를 자동으로 붙여 왕복을 줄인다"**는 점이다.
> 담당자에게 "어느 버전 쓰세요?"를 되묻지 않는 것이 이 기능의 값어치다.

## 6. 설계안

### ① 어떻게 띄우나 — 별도 창

**팀 사무실 창과 같은 패턴**을 그대로 쓴다(이미 있는 길):
- 사이드바에 **`📚 문서함 (창)`** — "팀 사무실 (창)" 바로 아래
- `main.ts`에 `docbox:open` 추가 → 독립 `BrowserWindow`
- 제품 화면 셸(탭) 안에 **안 들어간다** → 팝업 높이 규약·28화면 스윕과 무관
- 창이라서 **문서를 옆에 띄워두고 제품을 조작**할 수 있다(모니터 2대면 특히 좋다)

### ② 담당자가 보는 흐름

**읽기**
```
문서함 창 → 왼쪽 목차에서 문서 고르기 → 오른쪽에 렌더 → (필요하면) 검색
```

**쓰기**
```
① 왼쪽 맨 아래 [✏ 요청 만들기]
        ↓
② 유형 칩 고르기   [버그] [기능 요청] [화면·사용성] [기타]   → 템플릿이 채워진다
        ↓
③ 쓰기 + Ctrl+V    스크린샷 붙여넣기 · 드래그&드롭 (썸네일로 표시)
        ↓
④ 미리보기         ⚠ 나갈 내용 전체 + 자동 마스킹 결과("가려짐 3곳")
                   ⚠ "그림 속 내용은 검사할 수 없습니다 — 직접 확인하세요"
        ↓
⑤ [파일로 저장]    GIJO요청_버그_20260730-2340.md  → 담당자가 직접 전달
```

### ③ 자동으로 붙는 기술 정보 — 이 기능의 핵심 값어치

담당자가 안 적어도 클로드가 재현할 수 있게, **묻지 않고** 붙인다:

| 항목 | 왜 |
|---|---|
| 클라 버전 (예: 4.7.0) | "그건 지난 버전 버그예요"를 즉시 판별 |
| 서버 커밋 해시 | 코드의 정확한 시점 |
| **직전에 보던 화면** | 재현의 출발점 |
| 최근 오류 로그 5줄 | 조용한 고장을 드러낸다 |
| OS·Electron 버전 | 환경 차이 |
| 자가 진단 요약(암호화·백업·모델) | 시스템 상태가 원인인 경우 |
| 발생 시각 | 감사 로그와 대조 가능 |

> **별도 창이라도 이건 다 된다** — 우리 클라가 띄우는 창이라 preload로 같은 정보에 닿는다.
> (완전 독립 실행 앱이면 이걸 못 모은다 — 9절 결정사항)

### ④ 산출물 — 클로드가 바로 처리 가능하게

이미지가 Base64로 내장된 **마크다운 한 파일**:

```markdown
# [버그] 설정 화면에서 저장이 안 됨

| 항목 | 값 |
|---|---|
| 유형 | 버그 |
| 직전 화면 | 설정 > 관리자 |
| 클라 버전 | 4.7.0 |
| 서버 커밋 | f1c0334 |
| 발생 시각 | 2026-07-30 23:40 |
| 보낸 사람 | (담당자명) |

## 무엇을 하려 했나
...

## 무슨 일이 일어났나
![캡처_20260730234012](data:image/png;base64,...)

## 자동 수집 정보
- 최근 오류: (5줄)
- 자가 진단: 저장 암호화 켬 · 백업 정상 · 모델 정상
```

### 지켜야 할 우리 규약

| 규약 | 이 창에서 |
|---|---|
| **화면 제목 숨김** (3.5.0) | 큰 제목 안 넣는다. 정체성 한 줄만 |
| **화면엔 정체성 한 줄 + ⚠경고만** | 사용법은 **screenguide(챗봇)**로. ⓘ 아이콘 안 만든다(79개 제거함) |

| **한글 · 쉬운 풀이** | "Export"가 아니라 **"파일로 저장"** |
| 창 크기·중앙 정렬 | 팀 사무실 창과 같은 규칙 |

### 창 레이아웃 (2단 — 자산 화면과 같은 결)

```
┌──────────────────────────────────────────────────────────┐
│ 📚 문서함 — 가이드를 읽고, 개발팀에 보낼 요청을 만듭니다  │ ← 정체성 한 줄
│ [🔍 문서 검색                                        ]   │
├──────────────────┬───────────────────────────────────────┤
│ 📚 사용 안내 (4) │  # AI-BOM 검토 가이드                 │
│  · 사용자 매뉴얼 │                                       │
│  · 실무 매뉴얼   │  AI-BOM은 …                           │
│  · 활용 가이드   │                                       │
│  · 제품 소개     │  ## 1. 구성요소 5영역                 │
│                  │  …                                    │
│ 📐 업무 지침 (3) │                                       │
│  · AI-BOM 검토   │  (마크다운 렌더 · 목차 자동 · 내부    │
│  · 취약점관리    │   스크롤)                             │
│  · 보안제품관리  │                                       │
├──────────────────┤                                       │
│ ✏ 요청 만들기    │                                       │
└──────────────────┴───────────────────────────────────────┘
```

- **왼쪽 목차**: 자산 화면 카테고리 트리와 같은 방식(익숙함 재사용)
- **✏ 요청 만들기**: 왼쪽 맨 아래 — 읽다가 "이거 이상한데"에서 바로 이어지게. 누르면 **오른쪽이 작성 모드로** 바뀐다(창을 또 띄우지 않는다)
- **유형 칩**: 설정 화면 필터 칩(`.filter-chip`)과 같은 모양
- **붙여넣은 이미지**: 테두리 있는 **썸네일** — 본문에 거대한 Base64가 그대로 보이면 담당자가 놀란다
- **미리보기**: **읽기와 같은 렌더러** — 보낼 모습 그대로
- **마스킹된 값**: `--amber` 배지로 "가려짐 N곳"

## 7. 남은 위험 — 하나로 줄었다

메일을 안 만들기로 하면서 난관 3개 중 2개가 사라졌다(반출 경로·고객 동의 — 담당자가 파일을 직접 다루므로 우리가 개입하지 않는다).

### 남은 것: 스크린샷에 고객 보안정보가 찍힌다

담당자가 취약점 화면을 캡처하면 **자산명·사설 IP·CVE·담당자 이름**이 그림에 그대로 들어간다.

**대응:**
1. **미리보기 필수** — 무엇이 파일에 들어가는지 눈으로 보고 저장한다. 자동 저장 없음
2. **본문 자동 마스킹** — 오늘 만든 `secretscan.ts`(비밀번호·API 키)와 `cloudegress.ts`(사설 IP·자산명·담당자명) **재사용**. 새로 만들 것 없음
3. **⚠ 그림은 자동으로 못 가린다** — 정직하게 경고를 띄운다. 이건 코드로 해결 못 한다
4. **첨부 여부를 담당자가 선택** — 그림 없이 글만 저장하는 것도 가능하게

> 파일이 담당자 PC에 저장되고 **거기서 끝난다**. 밖으로 나가는 판단은 전적으로 담당자 몫이다 —
> 오늘 DB 암호화에서 "공급사가 열쇠를 갖지 않는다"고 정한 것과 같은 원칙이다.

`GIJO_AS_시장경쟁력_전중후_계획서.md`에 **이 항목은 없습니다.**

가장 가까운 것은 **중-1 "파일럿 실사용 피드백 루프 — 주간 수집, 오답·미답 지적은 회귀셋으로 흡수"**인데, 중-1은 **AI 답변 품질**에 한정된 항목이고 이미 `answerfeedback.ts`로 구현돼 있습니다.

**제 의견**: **중-1의 확장**으로 보는 것이 맞습니다 — "실사용 피드백을 버리지 않는다"는 같은 목적이고, 대상이 답변에서 제품 전반으로 넓어질 뿐입니다. 파일럿을 시작하면 담당자가 겪는 불편은 답변 품질보다 **화면·조작** 쪽이 훨씬 많을 것이라, 파일럿 전에 이 통로가 있는 편이 낫습니다.

읽기(문서함) 쪽은 계획서 어디에도 없지만, **출하 문서가 담당자에게 안 보이는 상태**는 그 자체로 결함에 가깝습니다.

---

## 9. 단계와 예상 시간

| 단계 | 내용 | 예상 |
|---|---|---|
| **0** | 시안 1개(자체완결 HTML) → 승인 | 30분 |
| **1** | 별도 창 띄우기(`docbox:open`) + nav 진입점 | 40분 |
| **2** | **읽기** — 2단 목차·마크다운 렌더·검색, 문서 7건 노출 | 2시간 |
| **3** | 서버 — 문서 목록·본문 API(매니페스트 기반, 7건 화이트리스트) | 40분 |
| **4** | **쓰기** — 유형 칩·템플릿·Ctrl+V·썸네일·미리보기 | 2시간 |
| **5** | 자동 정보 수집 + 마스킹 재사용 + 요청 원장 저장 | 1시간 |
| **6** | 파일로 저장(파일명 규칙) | 30분 |
| **7** | 챗봇 안내·용어사전·시험·실화면 검증 | 1시간 |
| | **합계** | **약 8시간** |

**쪼갤 수 있습니다** — 0~3단계(**읽기만**)면 **약 3.5시간**. 출하 문서 7건이 담당자에게 보이는 것만으로도 값이 있으니, 여기서 끊고 쓰기는 나중에 얹어도 됩니다.

## 10. 결정이 필요한 것

1. **계획서 편입** — 중-1 확장 / 별도 항목 (8절)
2. **순서** — 읽기 먼저(3.5h) 내고 쓰기를 나중에 / 한 번에(8h)
3. **문서 7건이 맞는지** — `knowledge/*` 6종 제외에 동의하시는지 (2절)
4. **아키텍처 문서** — 고객용 개요를 새로 쓸지, 이번엔 빼둘지 (2절 ⚠)
5. **별도 창 vs 완전 독립 앱** —
   · **별도 창(추천)**: 자동 기술 정보 수집이 된다. 로그인 상태를 쓴다
   · 완전 독립 앱: 클라 없이도 돌지만 **버전·화면·오류 로그를 못 모은다**(이 기능의 값어치가 절반)
6. **요청 이력을 서버에 남길지** — 남기면 "지난달에 뭘 요청했지"를 볼 수 있고, 안 남기면 파일만 생긴다

## 11. 정직하게 남기는 한계

- **그림 속 내용은 자동으로 못 가린다.** 글은 마스킹하지만 스크린샷은 담당자가 직접 확인해야 한다
- **전달은 담당자 손에 달렸다.** 파일이 저장되고 끝이므로, 담당자가 보내지 않으면 우리에게 오지 않는다(의도된 설계)
- **양방향 상태 동기화(고쳤는지 알려주기)는 범위 밖.** 폐쇄망에서 우리가 고객사로 되돌려 보낼 통로가 없다
- **Base64 이미지가 많으면 파일이 커진다**(스크린샷 3~4장에 수 MB). 메일 첨부 한도를 넘을 수 있어 미리보기에 파일 크기를 표시한다
